# UI/UX 设计知识库

供开发中的项目直接采用。这里保存跨项目仍然成立的设计判断，以及需要在具体场景中重新决定的取舍。进入[知识目录](knowledge/README.md)，先看共同条件，再按用户任务查阅相关专题。设计要求、建议及其适用边界在正文中维护。

## 开发新功能或修改已有功能

在确定界面、接口和实现之前，先从需求识别使用者要完成的动作、涉及的对象、状态变化和支持的设备。按这些事实查阅知识。例如“切换业务类型后出现另一组字段”对应条件字段，“一条命令处理多页记录”对应批量范围。项目 AI 主动完成这一步，使用者只需提出要做的功能。

把确实适用的要求落实为该功能的具体结果。遇到多种成立的方案，结合现有使用习惯、风险和维护成本选择，保留项目自己的风格与优先级。若选择改变了用户可依赖的保证，如重试只产生一次结果、批量修改要整体生效，应在实现前与后端明确接口行为及合理代价。库中没有相应条目的问题仍按项目证据判断。

交付时验证实现是否兑现选定的结果。对可重复的高后果失败，可落实到现有项目的公共组件、接口或测试中。比如编辑时本地保留的值，最终是否写入了不适用的业务记录，需要核对实际提交和生效结果。具体字段名、样式值、验收用例留在目标项目。

## 检查一个流程或整个项目

“按这份 README 检查订单编辑”即可启动针对该流程的检查。“按这份 README 检查整个项目”则先由 AI 按用户入口梳理实际任务与共享交互，再逐项覆盖所要求的范围。共用组件的结果可复用，还应检查在不同页面、权限、数据和窗口条件下的差异。

使用现有版本作基线。在适用的状态下实际走流程，例如正常、失败、重复操作或内容装不下时，分别核对用户看到什么、能做什么、系统实际改变了什么。用测试数据核对可能改变业务数据的操作。布局和焦点问题看实际界面，写入范围看实际请求与业务结果，声称目标用户更快或更易理解则需要相应的行为观察。只有代码、静态画面或个人判断时，明确证据能支持到哪一步。

报告指出问题所在的功能、适用条件、复现步骤、实际后果、预期结果和相关条目。基础条件确实被违反时报告缺陷。多个方案都成立时说明项目取舍。缺少权限、环境或真实反馈时标明待验证。全项目审查还需交代已覆盖及未验证的范围，避免以一条流程的结果代表整个产品。

## 项目问题如何反馈

- 条目适用且结论正确，错误发生在实现或验收中，修目标项目并验证该场景。
- 规则正确但按任务无法找到，更新知识目录中描述触发条件的文字。
- 在原条目的前提下出现反例，带回最小例子，修订原条目的结论、范围或例外。
- 新观察先在项目内解决。能说明可复现的后果及跨项目成立的条件，经采纳后再加入这里。一次性的接口限制或品牌选择保留在项目内。

## 接入其他项目

把下段放入目标项目会持续提供给 AI 的协作说明。公开仓库是本地知识库不可用时的备用读取来源。

```markdown
## UI/UX 设计与审查

涉及界面、交互或用户可见行为时，主动读取 `D:/project/uiux/README.md`。本地副本不可用时，读取 [UI/UX 知识库](https://github.com/yangcunqiu/uiux) 的根 README.md，并从同一来源查阅相关专题。

开发或修改前，先判断知识的适用条件，将明确要求落实到设计、必要的接口行为和验收。对有多种合理方案的地方，按本项目的任务、收益和代价选择。

收到局部或全项目审查任务时，主动梳理指定范围内的用户任务，核对实际界面、交互和业务结果。报告可复现的问题、依据、覆盖范围及待验证项。
```

维护本知识库时使用[协作规则](AGENTS.md)。
