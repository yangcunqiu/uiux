# 填错的时机

错误不是一句话，是一个时刻和一个位置。什么时候判、判在哪、判完怎么交代，决定了用户是「改一下」还是「从头找」。

这篇讲四件事：校验的三个时刻、错误和说明抢位置、汇总该写什么、提交按钮该不该置灰。标签本身的位置、必填标记和说明载体在[标签在场](../标签在场/README.md)。

## 先看演示

上半部分四个密码框：输入即判 / 失焦才判 / 提交才判 / 进度 + 失焦。点「在每个密码框里输入 a」，再点「让当前输入框失焦」：

- 第一个框在输入第一个字符时就红了；
- 第二个框输入时没有任何提示，失焦才红；
- 第三个框失焦后仍然是干净的，提交才红；
- 第四个框输入时只有进度（「还差 11 位，还要有数字」），失焦才红，改的时候进度回来。

下半部分同一个手机号字段的三种位置：说明在框下、错误也在框下；说明在框上、错误在框下；一个槽位、错误替换说明。三张卡都停在出错状态；改对，错误会退；改回 138 再离开，错误又回来。

汇总的重复问题在[必填标记](../标签在场/必填标记.html)：勾「汇总里重复错误原文」，看汇总把字段下的「请填写姓名」再抄一遍是什么感觉。同一页的 ⑨ 是置灰提交的对照。

## 一、三个时刻

- **输入中：帮助，不判决。** 强度、字数、可用性、去重检查可以实时更新；「错了」留到失焦或提交。密码输入一个字符不判错——用户还没交出这个值；这时候红，是在惩罚「还没输完」。
- **失焦：判这个字段。** 格式在这里判；前提是用户真的动过它。只是 Tab 穿过、没输入的空字段，别提前报——空字段的必填错误留到提交。
- **提交：判整张表。** 全量校验，聚焦第一个错误；后端错误也在这时落到字段上。长表单不能只靠提交，用户会白填很多；短表单可以只靠提交，少打扰。
- **修正时清错。** 用户开始改，旧错就退；改完仍可再报。清错不等于判对。
- **后端/异步检查**去抖，先给「检查中」，结果落到字段；保留用户输入；不要只在顶部写一句「提交失败」，用户不知道改哪。

「提交时统一校验」和「失焦后校验」不是二选一：失焦负责单个字段，提交负责整张表和后端。演示里的第二、第三种是两种失败模式：一个什么提示都不给，一个把问题攒到最后；第四种是折中。

## 二、错误和说明的位置

三种排法，演示里可直接对比：

1. **说明在框下，错误也在框下**：错误隔着一句说明，离输入框最远；出错时行高跳得最多。
2. **说明在框上，错误在框下**：两个槽位。说明是「问题的一部分」，在填之前就在；错误紧贴输入框。代价是多一行高度。
3. **一个槽位，错误替换说明**：最紧凑；修的时候说明不见了，所以错误文案必须自带规则（「应为 11 位数字」），不能只写「格式不对」。

倾向：说明放框上，错误放框下；两者不要叠在框下同一条线上。空间紧就用替换，但错误要能独立成立。错误出现会让行高跳，就给它留一行，或者用替换。

错误文案说「怎么改」，不要只说「错了」；不要只靠颜色（红边框 + 文字）；提交时聚焦第一个；错误和字段用 `aria-describedby` 关联——这些是低成本部分，默认做。

## 三、汇总：地图，不是复读

字段下写「怎么改」（请填写手机号 / 应为 11 位数字）；汇总写「还有几项、在哪」（还有 3 项：姓名、手机号、所属部门）。

它的价值在长表单：错误可能在视口外，汇总是一张地图，还能跳。短表单可以不要，第一个错误聚焦就够了。把错误原文抄进汇总才是重复——[必填标记](../标签在场/必填标记.html)里的开关就是让你看这个。

汇总要在提交失败后出现、能被看见；用 `role="status"` 之类的通道播报，并聚焦第一个错误。不要只写「有错误」。

## 四、提交闸门：置灰的代价

有些表单在必填项没填完时把提交按钮置灰。它默认不好：**置灰不是更严格的校验，是更沉默的校验。**

提交按钮要回答四个问题：能不能按、指到的是它吗、收到了吗、成了吗（[受理与交代](../受理与交代/README.md)第一节）。置灰只回答第一个，而且答案是「不能」，没有原因。它把校验结果持续显示在按钮上，用「点不了」替代「点了告诉你哪里错」。

它有一个真实的好处：用户不用先点一次才知道没填完；短表单里，按钮亮起来就是「可以了」的信号。但代价更大：

- **一个状态位表示多种原因**：没填完、格式错、没权限、正在处理、后端不允许——都是灰。用户分不清「再填两格」和「你没权限」。
- **它拿走了唯一能问的通道**：按钮是表单说「哪里不对」的入口。禁用后点不了（原生 `disabled` 还会移出 Tab 顺序），用户只能自己扫表单找缺项；长表单或隐藏/条件字段里，缺的那一项可能在视口外。
- **它可能说谎**：只检查「非空」，按钮亮了不等于值有效；连格式、后端一起检查，按钮可能因为用户看不见的原因一直灰着。灰是「就绪」的代理，不是「有效」的保证。
- **它把「未完成」读成「被拒绝」**：一进来就是灰的按钮，很容易被读成「我没权限」或「这表单坏了」，而不是「还差两项」。
- **它会打断主路**：禁用的主按钮会让 Enter 的默认动作消失（[一条主路](../一条主路/README.md)）。

### 什么时候可以

不是一律不行，但它是最后手段：

- 表单短、必填项全在视野里、缺的原因单一且明显（向导的「下一步」、勾选协议后的提交）。这时灰按钮是个进度指示，扫描成本低。
- 置灰同时，原因写在不禁用的载体上：「还差 2 项」「请先选择审批人」，而且最好能点过去补。原因必须能定位，不能只有一个数。
- 不是表单校验，而是「没有可执行对象」：空搜索、金额为 0 的支付。这不是「你没填对」，是「现在没东西可做」。
- 「处理中」用 loading/锁，「没权限」用隐藏或申请，不是灰。三种原因不能共用一个灰——[拆组件](../拆组件/README.md)第六节、[受理与交代](../受理与交代/README.md)第五节。

### 更好的做法

- **默认保持可用**：点击 → 校验 → 字段下报错 → 聚焦第一个。按钮就是提问的入口。
- **想给就绪感，把数量写在按钮上**：`提交（还差 2 项）`，保持可点；点它聚焦第一个未填。这是[必填标记](../标签在场/必填标记.html) ⑧ 的做法：既有信号，又能问。
- **必须禁用时，原因放到旁边**：状态行、清单、可点的链接；不要指望禁用按钮自己的悬停/聚焦——它可能收不到这些事件。
- **长表单**：粘性汇总/进度 + 可用提交；错误在视口外时，汇总就是地图。

按钮位置、保存/提交的边界在[提交边界](../提交边界/README.md)。

## 为什么这样判断

- 四个时刻的行为在演示里可直接观察；位置三张卡的差异也是。没有做用户测试。
- 置灰的结论来自按钮的可供性：它回答「能不能按」，但不回答「为什么」；这与[受理与交代](../受理与交代/README.md)的四问一致，不是从「用户会困惑」推的。
- 汇总的必要性取决于错误是否在视口外；短表单里它是冗余的。
- 24×24 是 WCAG 的最小目标（有例外）；`aria-describedby` 是低成本做法。主证据是行为和后果，不是读屏。
- 演示里的密码规则（12 位、字母 + 数字）是演示值，不是安全建议；也没有测用户多久会注意到错误。

## 适用条件和取舍

- 短表单可以只靠提交；长表单要失焦 + 提交；异步检查要去抖。
- 失焦只判「动过」的字段；空必填留到提交；Tab 穿过不报。
- 说明在上/错误在下适合「填之前就要知道」的规则；替换适合空间紧且错误自带规则。
- 汇总在长表单需要，短表单可省；不要复读。
- 置灰只在最后手段；短、全可见、原因单一。否则保持可用。
- 演示不测人；「输入 a」是脚本状态，不是用户行为。

## 还没定

- 异步校验的去抖时长、pending 文案。
- 错误位置留白 vs 替换的量化差异。
- 汇总的播报/聚焦细节（`aria-live`、`role="alert"`、焦点移动）。
- 后端多字段错误怎么映射到字段，尤其是跨字段规则。
- 置灰在向导/长表单中的实际效果，没有测。
- 错误文案的长度和写法（R 簇）。
- 触摸端图标提示的可达性。
- 侧排里说明/错误的位置，没有演示。
- 「置灰 + 报数」的组合没有单独做。
