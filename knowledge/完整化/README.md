# 完整化

「不要过度设计」常被提起。一位做 UI 的工程师在定义品质时（[《用户界面的品质》](https://wxad.design/abc/quality-of-ui)，作者自注为个人叙事）给过相反方向的提醒：真正的挑战往往在于**设计得太少**——搞特殊、做一个并不难，难的是把这种特殊贯彻。本条说清「完整」指什么、为什么不完整的新颖只是装饰、做满的例外在哪。

## 我们的理解

> **完整化值在应用范围，不值在枚举长度。**

- 一个形式只做一处，是**装饰**；做满系统，才从「特殊」变成**语言**。分开看每个应用都不新鲜，价值产生在应用彼此呼应的位置上——用户对产品的感受随之完整（同上出处；[Family 的动态托盘](https://benji.org/family-values)是文中转引的例子，原文未读）。读法上的对照：一个控件单独换了新动效，读作「这里改了」；同一动效铺满全站，读作「这家换了一套语言」——变的是归属感，「能不能用」没动。
- 与它易混的另一种「完整」是**枚举完整**——把清单写长。字体栈是最好的反例：14 个具名字体的回退清单随系统老化、越长维护越贵，后来被 `system-ui` 两个词取代，枚举交给标准、负担清零。详见[约束与调性](../约束与调性/README.md)的字体栈一节。
- 由此「过度设计」多了一种解法：**有时做得足够完整，就是解决过度设计的方法。** 单点的新颖用户才会「察觉到设计」；做满的形式成为体验的无形骨架。

## 为什么这样判断

- 三合一（体验、打磨、完整化）是作者标注过的个人叙事；本条只收完整化——它是三条里唯一既有机制、又能举出正反例的一条。另两条的处置见「还没定」。
- 「应用/枚举」之分是讨论提出的表述：两个「完整」记的账本不同——枚举的成本记在维护账上（清单老化），应用的收益记在认知账上（形式呼应）。
- 「单点读作特殊、做满读作语言」是讨论接受的经验感受，不是定律——按[约束与调性](../约束与调性/README.md)的判据，这里坏的不是功能，只是味道；但完整化关心的正是味道这一侧。

## 适用条件和取舍

- **做满的前提是形式本身站得住**：一致性让坏东西更自信地坏。应用范围放大的是形式的既有成色，不提供成色。
- **「用户察觉到了设计，就意味着过度」只在日用工具里成立**：高频使用中形式应当退为骨架；初见场景（官网、活动页）里察觉设计恰恰是目的——两本账见[美即好用的边界](../美即好用的边界/README.md)。
- **做满有维护代价**：每一处应用都是一处维护面；选简单形式（一条缓动、一种圆角）做满，比选复杂形式便宜得多——[约束与调性](../约束与调性/README.md)的具名值（定义一处、处处引用）就是让「做满」便宜的生产方式。
- 「设计得太少才是问题」是对「不要过度设计」的补充，不是否定：约束类的省略（少一个必填标记、少一个焦点样式）不归本条管。

## 例子

- 正例：动态托盘铺满全 App（转引自上文出处）。
- 反例（枚举）：14 字体栈——枚举完整，老化成维护负担，被 `system-ui` 一词接管。
- 反例（坏形式做满）：全站给每个可点元素加同一个 500ms 回弹——一致地烦人，做满放大的是「慢」。

## 和其他主题的关系

- [约束与调性](../约束与调性/README.md)：完整化是让调性可感知的途径——单点的调性选择用户察觉不到，做满才读作性格；字体栈一节是枚举完整的反例。
- [美即好用的边界](../美即好用的边界/README.md)：「察觉到了设计=过度」的边界用两本账切开：日用成立，初见不成立。
- [感受与论据](../感受与论据/README.md)：这个形式要不要铺，多数落在调性一侧——立场声明，翻译不出参数。

## 还没定

- 「做满」没有可数的下限（几处应用算成语言）：讨论没有给出数。
- 三合一的另两条未独立成条：体验的测量接同一作者的《制作流畅界面》，已由动效那批条目覆盖；打磨对 AI 的观察是 2025 年时点的经验判断，能力边界移动快，决定不沉淀。
