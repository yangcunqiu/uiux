# 黑盒与源码

组件库有两种持有方式：装进 node_modules 依赖它，或者把源码放进自己的项目。选哪种，决定了你能在哪一层做设计决定——这不是「哪个更好」，是两个条件各管一段。

## 先看演示

无演示。这是选型与持有方式的判断，没有可以直接观察的界面现象；两个条件本身可检验——拿一个真实项目的约束往里套就行。

## 我们的理解

**黑盒**：组件长什么样、行为是什么，库说了算；你通过 Props（库预留的口子）和 CSS 覆盖（绕过口子）来改。

- 成立条件：时间预算紧、界面不是产品差异所在、接受默认样子。
- 价值：省时间。这是正当选择，不是偷懒——把时间留给真正差异化的地方。
- 代价：定制是**隔墙改**。Props 是墙上的门，门后没有的改动做不了；CSS 覆盖越积越多，库升级的时候一起塌。

**源码持有**（如 shadcn/ui 的模式）：组件代码直接在你的项目里，改它就是改自己的代码。

- 成立条件：调性要自己拨（见[约束与调性](../约束与调性/README.md)——主色、圆角这些轴你要自己做主），或者你需要理解和掌控交互行为。
- 价值：设计决定权完整地在你手里。
- 代价：每个组件的维护归你。你同时成了组件库团队——升级、安全修复、浏览器兼容都要自己跟。

**同一项目里两种可以并存**：内部工具页黑盒、对外产品页源码持有，是正常配置。

## 为什么这样判断

- 隔墙改的「墙」是可指认的：改黑盒组件只有两个通道，Props 和样式覆盖；通道之外的改动不存在，通道之内的每次覆盖都是对库默认值的一次偏离记录，改得越深，偏离越多。
- 源码持有时「改自己的代码」和「覆盖别人的代码」是两种心智状态：前者敢动、能学；后者一直在确认自己有没有越界。
- 「交互属于设计，不只是实现」与本库一致：受理要锁、提交中只能收起不能放弃这类判断，离开实现无法讨论——这也是每条知识配可运行演示的原因。
- 成色说明：前两条来自 shadcn/ui 一文的立场论证，不是实验结论；但「隔墙改」的墙可以从任何一次 CSS 覆盖经历里直接指认。

## 适用条件和取舍

- 条件随项目约束变，不随品位变：换一个「界面就是产品」的项目，同一批人该从黑盒切到源码持有。
- 中间路线「黑盒 + 局部 CSS 覆盖」本次讨论决定不展开；按黑盒的隔墙改理解它即可。
- 源码持有的维护成本没有实例核对——没有在真实项目里数过它比黑盒多花多少时间，只有结构上的判断：维护责任转移到了你。

## 案例记录：天花板与三本账

「如果单说组件的开发……上限是存在的，而且不高……UI 本身没有意义。有意义的是 UI 背后的业务逻辑，以及其实际影响的用户体验。组件库需要摆在其服务的业务中被衡量。」——这是立场，功能是防一种坑：**组件做完了就完了的工艺自足**（只打磨库本身，忘了它服务谁）。对单人开发者尤其有用，因为没人拦着你无限打磨。

但同一位作者的语料自己构成张力：Best Hearts（为留住设计师伙伴的动画而做的站）不是任何业务需求——「比起完成整个项目本身，制作这个站点是我认为更有意义的事。因为我真的很喜欢它们」。

消解：账分开记，一共三本——

| 账本 | 内容 | 语料证据 |
|---|---|---|
| 工具性 | 在服务的业务里衡量 | 「组件库需要摆在其服务的业务中被衡量」 |
| 身份 | 工艺认同 | 「我这个人很简单，只想要做优雅和精致的 UI」 |
| 玩与关系 | 一起做东西的意义 | 「有人陪你玩，才会做出有意思的好东西」 |

Best Hearts 记在后两本上，不推翻第一本——**天花板说法只对工具性那本成立**（单做组件的工艺上限确实不高）；把三本混成一本，才会觉得作者自相矛盾。

成色：立场＋案例，不上升为规则。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 两种持有方式与各自的通道 | 定义 | 写死 |
| 两个成立条件 | 条件 | 写信号，不写偏好 |
| 隔墙改 | 定义（结构性的） | 写死 |
| 两种并存 | 默认 | 可全站统一，代价是个别页面笨重 |
| 交互属于设计 | 立场 | 写死，标明来源是立场论证 |
| 天花板与三本账 | 立场案例 | 三本账写死；天花板不上升为规则 |

## 还没定

- 「黑盒 + 局部覆盖」这条最常见路线的代价没有展开讨论，只按隔墙改记了一笔。
- 源码持有的实际维护成本没有实例核对。
- 库本身的品质（无障碍、浏览器兼容、更新频率）该占选型多大权重，没有讨论。
