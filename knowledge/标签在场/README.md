# 标签在场

标签是表单里最直接同时属于「看」和「填」两个时刻的东西。看的时候，它回答「这是什么」；填的时候，它回答「我在答哪个问题」。位置、对齐、必填、说明，都是在这两个时刻里分配注意力和空间。

这篇讲三件事：标签摆在哪、必填怎么标、说明放哪。校验的时机、错误的位置和汇总在[填错的时机](../填错的时机/README.md)。

## 先看演示

三个页面都双击打开，不需要本地服务。

1. [标签怎么摆](标签怎么摆.html)：同一个表单，顶标签 / 左标签右对齐 / 左标签左对齐。可切标签长短、显隐说明文字。三个读数是页面实测的：表单高、标签末字到输入框的距离、六行标签起点的最大差。

   观察：右对齐的横距恒定，但每行起点在跳；左对齐起点成列，但短标签的横距能到 100px 以上；顶标签两个都不跳，用高度换。切到长标签，侧排开始换行、行高不齐。

2. [必填标记](必填标记.html)：4 个字段、9 种标法。点每张卡的「提交」看错误落在哪些字段；勾「假必填」看标记和校验脱节；勾「汇总里重复错误原文」看汇总变成复读。

   观察：星号在前/后/框右的区别；只标选填；文字「（必填）」；按钮报数；按钮置灰。

3. [说明文字](说明文字.html)：8 个字段、3 条真规则。切四种载体和长短文案；「填入示例值」让它出错；下面有 Tab 停留点计数。

   观察：常驻小字的长短差异；图标提示打开后盖住输入框；占位提示一输入就消失；「只在报错时说」漏掉后果型规则。

## 一、位置与对齐：你让哪一列整齐

侧排（标签在左）常见两种排法（居中对齐很少见，没有展开）：

- **右对齐**：每行标签的末字对齐，末字到输入框的距离恒定；但每行标签的起点在跳，左缘参差。
- **左对齐**：每行标签的起点成列；但末字到输入框的距离随标签长短变化，短标签离框最远。

顶排（标签在上）把两个方向都固定住：起点成列，距离也恒定；代价是每个字段多占一行。

演示里的数（6 个字段、标签列固定 120px、短标签）：右对齐横距 14px、左缘参差 27px；左对齐横距 80–107px、左缘参差 0；顶标签高 481px，侧排高 318px。这些数由当前字体和宽度量出，不是推荐值。它们说明的是机制：**侧排只能保住一列整齐，另一列必须容忍参差；顶排两列都整齐，用高度换。**

长标签把这个机制放大：侧排必须给标签留固定列，标签一长就换行，行高不齐；顶排把长度吃到高度里。对 B 端表单，这是比「哪个更快」更硬的结构约束——尤其多语言或字段名长的产品。

### 500 / 240 / 50ms 是什么

这个数字常被引用：Penzo 2006 的眼动研究（[原文](https://www.uxmatters.com/mt/archives/2006/07/label-placement-in-forms.php)）测到左对齐 500ms、右对齐 240ms（新手）/ 170ms（专家）、顶标签 50ms。条件是 4 个字段、全部必填、没有视觉设计，作者自己说是 ad-hoc 测试。它量的是「标签→输入框的一次扫视」，距离是主要变量之一，不是填完整个表单的时间；同一份研究里右对齐让完成时间减半，但测试条件和场景都很窄。

LukeW 的补充（[Eyetracking Web Forms](https://www.lukew.com/ff/374/eyetracking-web-forms)）是：短表单、全必填时右对齐/顶对齐更快；长表单、很多选填字段时，左对齐的左缘整齐更利于「找我要填的那几个」。

所以：

- 500ms 不能翻译成「左对齐不好」；它说的是标签和框离得远。
- 拿左对齐当刹车（「敏感表单让用户慢下来」）是用布局缺陷承担「谨慎」的职责。要慢，用复核页、二次确认、提交摘要——这些看得见、能验证。
- 有的文章给出「行内标签 10ms」，没有出处；Penzo 没测行内标签。行内标签的问题不是眼动，是填的时候问题从屏幕上消失。

### 怎么选

没有「最好的对齐」，只有「这个表单付得起的代价」：

| 摆法 | 代价 | 什么时候会咬人 |
|---|---|---|
| 顶标签 | 高度 | 字段多、纵向紧 |
| 左标签 · 右对齐 | 标签列占横向空间；长标签换行 | 标签长、多语言、窄屏 |
| 左标签 · 左对齐 | 短标签离框远 | 表单短、标签短，扫视成本白付 |
| 行内 | 聚焦/填完后问题消失 | 字段不通用、需要回看 |
| 浮动 | 多一层小字、标签会动、字号变小 | 字段多、桌面宽屏 |

倾向（有条件）：没有明显约束时，顶标签是最稳的起点；侧排只在「字段多、纵向紧、标签短而稳定」时用，且右对齐、标签列按最长标签定宽；左对齐文字只服务「扫长表单的字段清单」，不服务「让用户慢下来」。行内只给 1–2 个通用字段（登录）；浮动是窄屏的省空间方案，不是桌面默认。

### 冒号

冒号不是分隔符的装饰，是标点。Jarrett 的建议（[Colons at the end of labels](https://www.effortmark.co.uk/colons-end-labels-revisited/)）：标签是完整问句，用问号；是短提示，不加标点。她观察了几百个填表的人，没人抱怨过冒号的有无——这不是「加不加都行」的许可证，而是标点服从句子。

详情页的「姓名：张三」是另一回事：那是句子里的标签和值，冒号有语法作用。表单里标签和值靠位置分开，冒号通常是多余的。条件：左右排、标签和值在同一行、边界不清时，冒号能帮忙；顶排或行内不需要。

## 二、必填：四个部分，不是一颗星

必填由四件事一起构成：**标记、校验、错误文案、提交拦截**。星号只负责第一件。演示里的「假必填」把后三件关掉，星号还在；提交空表单，系统收下——标记立刻变成谎话。

### 九种做法

前七种是标记的不同做法；最后两种把「还差什么」放到提交按钮上，属于提交闸门，不是标记。

- **星号在前**：它自己成一列，最显眼；代价是标签文字的起点不再统一，必填/选填混排时没标的行会突出到左边。
- **星号在后**：起点整齐，星号不打断扫读；最不破坏标签列。
- **星号在框右侧**：标签干净，但星号离开读标签的那条线；输入框等宽时它还能成列，框宽不一时就散。
- **只标选填**：噪音最小；前提是用户知道「没标 = 必填」。
- **顶部一句话**：把要求放进段落，用户得一边填一边记，滚动就丢；混排表单里它说不清「哪几项」。只在「全部必填、一句话」时勉强可用，而且是补充，不是替代。
- **全必填不标**：最安静，但提交前不知道要填几项。
- **文字「（必填）」**：不依赖符号约定，最不容易误解；代价是每行多四个字。
- **按钮报数**：把「还差 3 项」放到按钮上，保持可点；给工作量，不给位置，只能当补充。
- **按钮置灰**：没填完就点不了；它只说「还不行」，不说缺什么。详细分析在[填错的时机](../填错的时机/README.md)的「提交闸门」。

星号常见的理由：短、能成列、用户认识。它的代价是「符号要学」；文字没有这个成本，但更长。没有免费的选择。

### 标少数派，还是固定一个方向

局部规则：3/4 必填 → 标必填；1/4 必填 → 标选填；全部必填 → 一句「本页均为必填」通常比完全不标便宜。

但**跨表一致性 > 单表噪音**。表单 A 标必填、表单 B 标选填，用户看到 A 的「备注」没标会以为选填，看到 B 的「备注」没标会以为必填——同一个「没标」，两种意思。必填项本身不同不是问题，标记规则翻转才是。

所以：要么整个产品固定一个方向（通常「标必填」——星号通用，「没标 = 选填」比「没标 = 必填」更符合「缺席不是信号」）；要么每张表自己写明约定。只有能保证同向时，「标少数派」才成立。

### 位置与语义

- 星号在标签后，不打断标签起点；在前，星号成列，标签起点不再统一；在框右侧，星号脱离标签的阅读线。
- 星号 ≠ 重要。重要但可选的字段不要标；标了就等于告诉用户「不填过不去」。
- 有「保存草稿」时，必填只在提交时生效；草稿不该被它拦住（见[关闭的承诺](../关闭的承诺/README.md)）。这是标记的承诺与校验的边界。
- 错误文案说「请填写手机号」，不要只说「必填」；错误贴在字段下，提交时聚焦第一个（见[填错的时机](../填错的时机/README.md)）。
- 标记要和校验一致；一颗不拦提交的星号是谎话。

## 三、说明文字：同一句话放在哪

四种载体，演示里可切：

- **常驻小字**：规则和后果在填之前就要知道，它承担这个；代价是每个字段多一行。它显丑多半不是小字本身，是三件事叠在一起：句子长、每个字段都说、列又窄。先删再缩，别急着换图标。
- **标签后图标**：省版面，适合少数人偶尔要看的补充；代价是藏起来、每个图标一个 Tab 停留点、触摸端没有 hover、提示会盖住输入框和下一行。目标至少 24×24（[WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)，有例外）；要能用键盘打开。图标常用 `?` 表示帮助、`!` 表示警告；把帮助写成 `!`，用户会先以为哪里出错了。
- **占位提示**：只放得下例子或很短的格式；一输入就消失，回看时也没有了。它不能承担规则，也不能代替标签。
- **只在报错时说**：适合格式错误（错了再改）；不适合「错了会白填」的后果——金额超 5000 要附发票，这种规则不会报错，只会在审批时退回来。

判断一句话放哪：**它会改变用户输入吗？** 会 → 常驻，或写进标签（「金额（含税）」）；不会 → 图标，或者不写。**它会决定提交结果吗？** 会 → 不能藏。

「丑」的处理顺序：先删（它真的会改变用户的做法吗）、再缩（一句话，不超过一行）、最后才换载体。用图标掩盖一段废话，只是把噪音藏起来。

这和[拆组件](../拆组件/README.md)第六节的「说明文字」是同一条：解释控件本身是设计债；解释规则、后果、状态是内容，但要放在需要它的时刻。GOV.UK 的 hint text 是常驻做法的实例，Ant Design 的 `Form.Item extra` 与 label tooltip 是常驻与图标两种做法的实例。

## 为什么这样判断

- 位置与对齐的机制是本页实测的几何（6 个字段、120px 标签列、当前字体）；换字号/列宽会变。500/240/50ms 来自 Penzo 2006，条件很窄；LukeW 的补充是长表单/选填场景。两者都不是「普适定律」。
- 长标签下侧排变差，是演示里直接看到的换行和行高不齐；它比 500ms 更接近 B 端表单的实际失败。
- 「四个部分」来自「假必填」演示：去掉校验、错误文案、提交拦截，星号立刻变成谎话。
- 「跨表一致性 > 单表噪音」是从 A/B 两个表单的「没标」含义不同推出来的；没有做用户测试。
- 说明文字的四种载体和「它会改变用户输入吗」是判断，不是标准。
- 24×24 是 WCAG 2.5.8 的最小目标；冒号是 Jarrett 的观察和建议，不是普遍规范。
- 演示里的 120px、14px、27px 等是演示值，不是推荐值。

## 适用条件和取舍

- 顶标签作为起点，前提是高度不是瓶颈；字段多、纵向紧时，侧排的密度是真实收益。
- 侧排右对齐，前提是标签短而稳定；长标签/多语言要重新算列宽，或者回到顶排。左对齐文字只在「扫读清单」优先于「填写速度」时用。
- 行内只适合字段本身是常识的场景（登录）；聚焦时 placeholder 就消失，不是「填完后」才丢。
- 浮动是窄屏/空间紧的方案；字段多时会挤，标签缩到 11px 左右，桌面宽屏没必要。
- 占位不能承担规则；图标不能藏「决定能不能提交」的规则；常驻小字要短。
- 必填的标记方向要全产品一致；如果做不到「每张表都按少数派同向」，就固定「标必填」。有草稿时，必填只在提交时生效。
- 演示不测人：没有测完成时间、误填率、用户偏好；500ms 是别人的眼动数据，条件与今天的产品不同。

## 还没定

- 跨表约定切换对用户的实际影响，没有做测试；A/B 例子是推理。
- 长表单/条件字段/动态必填的标记方式（字段出现才变必填）没有展开。
- 侧排里说明文字放框上还是框下，没有演示。
- 浮动标签在 8–10 个字段时的拥挤程度、字号下限，没有实测。
- 中文语境下星号在前/后的偏好，没有数据；Jarrett 的冒号建议来自英文。
- 标签文字居中对齐的使用场景，没有讨论。
- 标签列宽与最长标签的关系（按最长定宽 vs 固定宽度换行），没有系统比较。
- 只标选填的约定怎么让用户知道（图例、首次提示、文案），没有定。
- 「顶部一句话」在全部必填的长表单里是否可用，没有测。
- 按钮报数与置灰的组合（置灰 + 报数）没有单独做。
- 标签和读屏/键盘的具体做法（label for、aria-describedby、错误关联）只做了低成本部分，没有系统测试。
