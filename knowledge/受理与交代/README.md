# 受理与交代

一次点击之后、结果回来之前，按钮要回答几句话：指到的是它吗、收到了吗、成了吗。颜色只擅长“指到的是它吗”；“收到了吗”和“成了吗”要靠锁和文字。

## 先看演示

[打开「受理与交代」](受理与交代.html)（双击即可，不需要本地服务）

四节：

1. **颜色只回答“指到的是它吗”**：同一条通道 / 两条通道，以及白字对比度的现场计算。
2. **受理**：转圈不锁、锁住、失败后回到常态，三个按钮各连点三次。
3. **交代**：结果放在按钮上 / 页面上 / 哪里都不放。
4. **不能按**：禁用和“次要”撞车，两种修法。

观察重点：

- 第二节三个按钮各连点三次，请求计数的差别就是“锁”的全部价值。
- 第三节三个按钮都点一下，比较结果出现的位置。
- 对比度表里，哪一行的悬停比常态更差？

## 一、四个问题

| 问题 | 谁在问 | 载体 | 不给会怎样 |
|---|---|---|---|
| 现在能不能按 | 还没点 | 可用 / 不可用，加上原因 | 点了没反应，或者不知道为什么 |
| 指到的是它吗 | 悬停、焦点 | 边框、底色、光标 | 不确定自己点在什么上 |
| 收到了吗 | 按下到结果之间 | 位移、受理态、锁 | 怀疑没按到，重复点 |
| 成了吗 | 结果回来之后 | 按钮文案、页面提示 | 再点一次，或者以为成功了 |

“指到的是它吗”和“按下了没有”在[点击之后](../点击之后/README.md)里讲；这里补的是“按下去之后到结果回来”这一段，以及“成了吗”的交代。

## 二、颜色只回答“指到的是它吗”

同一条通道做两件事，读起来就是“同一件事的亮和暗”：悬停提亮、按下变暗，都是底色。换两个通道——悬停改边框和底色，按下改位移和内阴影——两层信息才分开。“收到了吗”这个问题，颜色只做了半个。

提亮还有一笔账：白字的对比度会掉。演示里现场算的是 WCAG 相对亮度——中蓝常态 4.55:1，悬停加 16% 白之后 3.49:1，低于 4.5:1 的门槛（[WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)）；浅蓝配白字，三档全不合格。深蓝、近黑则安全。

所以“取色阶上相邻的两档”有个前提：**基准色够深**。这个前提比规则本身更重要——浅色品牌色应该反过来用深字。

## 三、受理：锁，不是动画

转圈不拦任何东西。演示里 A 连点三次，请求三次；B 锁住，请求一次。受理态要做三件事：

1. **锁**：拦住重复提交。这是主要价值——它防的是重复提交，不是“让用户不焦虑”。
2. **说**：文案写“保存中…”，不是只有转圈。
3. **不动**：宽度不变，否则旁边的元素跟着挪。

实现上有两种锁：`disabled` 会把按钮移出 Tab 顺序，焦点随之丢失；`aria-disabled` 保住焦点，但要在处理函数里自己拦住重复操作。演示用的是 `disabled`，另一种没有展开。

## 四、交代：结果放在哪

三个位置，代价不同：

| 结果放在 | 什么时候合适 | 代价 |
|---|---|---|
| 按钮上（“已保存 ✓”） | 结果确定、不需要核对 | 信息量小；文案变了宽度会跳 |
| 页面上（横幅、行内、列表刷新） | 需要核对对象、时间、范围 | 离按钮远，用户可能没看见 |
| 哪里都不放 | —— | 用户分不出“成了”和“没点到” |

“恢复了”和“成功了”长得一样，是重复提交的主要来源。失败必须有一个和成功不同的载体：按钮上的文字、页面上的提示，或者两者都有。

结果放在按钮上还是页面上，和[点击之后](../点击之后/README.md)里“数字在按钮里 / 在别处”是同一个判断：中间有没有空间距离。

## 五、不能按：禁用不是一种灰

工具栏上，一个可点的次按钮和一个禁用的主按钮，常常是同一个浅灰底。区别只剩“能不能点”，而这个信息恰恰是禁用按钮自己给不出的——它没有悬停，也没有焦点。

两条修法：

1. **让禁用有自己的形状**：虚线边、更浅的字、光标，原因放在旁边一个不禁用的载体上。
2. **不做禁用按钮**：把“缺什么”变成能点的动作（选择审批人），主按钮等条件满足再出现。

禁用是最后手段。原因分三种（没权限、条件不满足、正在处理），一种灰表达不了三种，见[拆组件](../拆组件/README.md)第六节。

## 六、激活态不是状态

一个显示为“已启用”的按钮，宣布的是“它现在是这个模式”，不是“按下会发生什么”。那是开关、分段控件或当前项，是另一个控件。把它塞进按钮的状态里，会出现“这个按钮能点吗、点了会怎样”都答不上来的情况。语义在[承诺与边界](../承诺与边界/README.md)。

## 为什么这样判断

- 四个问题是从“点击之后”的三时刻推出来的，加上“能不能按”这个前置问题。
- 颜色与对比度是计算，不是评价：WCAG 公式加上具体色值，数字可以复算，也不依赖我的品位。
- 锁的必要性来自演示里的计数差：只转圈 3 次，锁住 1 次。这是行为差异，不是说法。
- 交代的三个位置来自“结果在哪能被看见”；第三行是反例，它的坏处不是不够漂亮，是用户无法判断。
- 禁用与次要撞车是外观观察：两个按钮的底色、字色、边框都落在同一区间，不是“感觉有点像”。

## 适用条件和取舍

- 只适用于“点了会有结果”的动作。纯本地动作（展开菜单、切 tab）没有受理态，不需要锁。
- 网络慢到需要进度时，按钮不是进度的好载体——它太窄，也只能说百分比。长任务属于后台任务或进度条的范畴。
- 结果交代的载体跟着“结果要不要核对”走；不是所有动作都值得一条横幅。
- 演示里的 900ms、1500ms 是演示值；真实时长由后端决定，前端只负责“锁到结果回来为止”。
- `disabled` 与 `aria-disabled` 的取舍依赖产品对键盘用户的要求；这是个未展开的实现选择，不是风格偏好。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 四个问题 | 定义 | 写死 |
| 锁的必要性 | 定义（防重复提交） | 写死 |
| 颜色两通道 | 默认 | 可偏离：极简系统可以只做一层 |
| 对比度门槛 | 标准 | 4.5:1（正常字）/ 3:1（大字） |
| 16% 提亮 | 经验值 | 只在深色基准上可用 |
| 结果放哪 | 场景变 | 按“要不要核对”选 |

## 还没定

- 长任务（超过十几秒）时，按钮状态怎么升级成进度或后台任务，没有讨论。
- 多个按钮同时提交时的顺序、失败回滚，没有展开。
- 失败文案的写法（和 R 簇的状态提示一起看），没有讨论。
- 重试按钮和原按钮是同一个还是另一个，没有定。
- `aria-live` 播报与焦点移动的具体做法，没有实测。
- “不可用”在颜色之外的载体（图标、文案、间距）还没有比较。
