受理与交代

一次点击之后、结果回来之前，按钮要回答的几句话：指到的是它吗、收到了吗、成了吗。

一、颜色只回答「指到的是它吗」 而且不许把字变难读

前两张是静态图（悬停、按下用类名画出来），第三张的读数是现场算的。

同一条通道
正常
悬停：亮一档
按下：暗一档
三张图只有底色亮度在变。悬停在问「我指到的是它吗」，按下在问「收到了吗」——两个不同的问题由同一支笔回答，读起来像同一件事的亮和暗。
两条通道
正常
悬停：边框 + 底
按下：缩一档 + 内阴影
悬停改「这是什么」（边框、底色），按下改「发生了什么」（位移、压下去）。两个通道说两层信息。
按下是叠加态：按下时指针一定还在上面，所以按下要在悬停的那一档上再走一步，不是从基础态重来。
提亮一档的代价：白字的对比度
品牌色常态悬停 +16% 白按下 +16% 黑

二、受理：锁，不是动画 转圈不拦任何东西

下面三个按钮都能点。连点三次，看请求计了几次。

A · 只转圈
请求 0 次
转圈没有拦住任何东西：点三次就发三次请求。转圈在这里只是装饰。
B · 受理态
请求 0 次
转圈 + 文案 + 锁住 + 宽度不变：这是能被读出来的「已收到，还没成」。锁的价值大于动画，它防的是重复提交。
C · 失败后回到常态
请求 0 次
失败后按钮直接变回「保存」，没有一个字说明。用户会再点一次 —— 第二次是重复提交。「恢复了」和「成功了」长得一样，这是失败的来源。
宽度：受理态里最容易漏的一件事

三、交代：结果放在哪 三个位置，一种最坏

三个按钮做同一件事：假装保存成功。区别只在结果放哪。

A · 结果在按钮上
按钮自己变成「已保存 ✓」，一会儿回到常态。位置最近，用户的视线不用移；适合结果确定、不需要核对的动作。
B · 结果在页面上
已保存 · 刚刚
按钮回到常态，结果出现在页面上。能带更多信息（时间、对象、范围），需要核对的动作该用这一种。
C · 什么都没说
按钮回到常态，没有一个字。用户无法区分「成了」和「没点到」，于是再点一次。不交代不是简洁，是把判断成本转给用户。

四、不能按：禁用不是一种灰 它和「次要」撞车

工具栏上最常见的一行：一个能点的次按钮，一个不能点的主按钮。

撞车
两个都是中性灰的浅底、都安静。一个能点、一个不能点，外观没给出区别 —— 而禁用按钮恰恰收不到悬停和点击，解释不了自己。
修法一：让禁用有自己的形状
需先选择审批人
虚线边、更浅的字、旁边一行原因。但原因不能只挂在禁用按钮自己身上：它没有悬停，也没有焦点，得有一个不禁用的载体。
修法二：根本不做禁用按钮
选好之后才能提交
把「缺什么」变成一个能点的动作，主按钮等条件满足再出现。代价是布局会变（按钮多一个少一个），收益是屏幕上没有死的东西。
怎么看：第二节三个按钮各连点三次；第三节三个按钮都点一下，比较结果出现的位置；第四节比较两个灰按钮和两种修法。
数值是演示值，不是推荐值。点击计数、失败路径、对比度计算已在 Chrome 里实际验证。
