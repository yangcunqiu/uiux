# 选项行

一行一个选项。行里有勾选框、名字，可能还有描述、图标、数量或图像。排这一行最容易错的地方是对齐：**勾选框对的不是整行，是它标记的那个东西。**

## 先看演示

[打开演示](选项行.html)（双击即可，不需要本地服务）

上半部分切换文本行的对齐方式：首行 / 整行垂直居中。下半部分切换说明图标的做法：span 放进 label / button 放在 label 外。

观察重点：

1. 单行行两种对齐看不出差别；带描述的行，居中会让勾选框往下漂。三行描述那一行，实测漂了 21px。
2. 首行对齐时，勾选框在每行里离行首的距离一样；居中时，这个距离随行高变化，勾选框不再是一条等距的列。
3. 头像行不跟着切换：它对齐的是图像。两条全局规则各对一半，正确做法是按每行的锚点对齐。
4. 图标做成 span 放进 label，点图标会顺手切换勾选；做成 button 放在 label 外，勾选不变，还能用空格键打开说明。
5. 错误版复选框的读屏名是「安全提醒 登录新设备时提醒我。说明」，正确版是「安全提醒 登录新设备时提醒我。」——图标的 aria-label 被并进了选项名。

## 对齐的是「被标记的东西」

- **文字行**：锚点是名字的首行。
- **图像行**：锚点是图像。
- **单行行**：两种对齐等价，看不出差别。

为什么首行对齐：勾选框本身是一条视觉列。每行都对齐名字首行，这条列在行与行之间保持等距；整行居中会让它随行高抖动，描述越长漂得越多。这是扫描成本，不是审美。

所以没有一条全局规则能同时对付文字行和图像行。实现上按每行的锚点：

- 文字行：`align-items: flex-start`，勾选框再往下挪几个像素，光学居中到首行。
- 图像行：`align-items: center`，勾选框对图像。

## 描述

- 对齐文字列，不跟勾选框列对齐。跟着勾选框列，描述会看起来属于框，而不是属于名字。
- 宽度不超过文字列。太宽会把行撑成一段文章。
- 「控制在两行以内」是经验值。判据是**选择时需不需要读它**：
  - 需要读：它就是这个选项的一部分，也许该用卡片或详情，而不是挤在列表里。
  - 不需要：它是说明，移到图标或详情页，别让所有选项陪它变高。
- 一行有描述、旁边没有，行的节奏会乱。要么统一有，要么只给少数项用图标。

## 变体

**描述**：解释这个选项是什么。位置在名字下，两行以内。

**图标**：补充信息或操作。可点的用 button，放在 label 外；不可点的用 span 加 `aria-hidden`。别让不可点的图标看起来像能点。

**数量**：右对齐成列，方便比较。两个要定的事：0 项是隐藏还是禁用（隐藏省空间，但选项会「消失」；禁用解释得清）；数字是「加上这项后的结果」还是「全量」——勾其他筛选项时数字会变，用户得能看出来。

**图像**：图像是这行的锚点。勾选框与图像居中，文本块与图像上下对齐。图像不能是唯一的标识，名字和替代文本要有。

## 行里的第二个目标

一行里除了勾选框，还可能有说明图标或链接。这里有两个坑。

**坑一：图标会顺手切换勾选。**
label 的默认行为是把点击转给勾选框。图标做成 `span`（非交互内容），点它就会切换勾选。做成 `button` 或 `a`（交互内容），浏览器会跳过 label 的激活行为。

**坑二：button 放进 label 里不合法。**
`label` 的内容模型只允许一个 labelable 元素——被标注的那个控件。`button` 也是 labelable，所以「勾选框 + button」同时放进 label 是不合法的。能跑，但校验器会报错。

正确结构：

```
div.row（相对定位，右侧留 padding）
├─ label.row-label（覆盖勾选框和文字，整行可点）
└─ button.info（绝对定位在行尾，在 label 外）
```

这样三件事同时成立：整行可点、图标不切换勾选、HTML 合法。tab 顺序是勾选框一次、按钮一次。

代价要认：

- 每个按钮都是一个 tab 停留点。20 行选项各带一个说明图标，键盘用户要按 40 次 Tab。说明是次要的，就把内容挂到 `aria-describedby` 或写进描述，别单独做一个控件。
- 触摸端没有 hover。说明要么点击展开，要么直接写出来；弹层要能用 Esc 或点外面关掉。
- 按钮的目标至少 24×24（WCAG 2.5.8）。

## 什么时候用图标

如果这段说明重要到影响选择，它就不该藏在图标后面——hover 在触摸端不存在，点击展开也多了一步。直接写进描述，或者让选项本身说清楚。图标适合放「补充、但不影响选择」的信息。

## 为什么这样判断

- 21px 是演示里那一行的实测漂移，不是普适值；换个行高和字号会变。
- 读屏名字的差异是实测：错误版多出「说明」，正确版没有。
- `label` 的内容模型是标准；24×24 是 WCAG 的最小目标。
- 「描述两行以内」是原文的经验建议；判据（选择时要不要读）是推论。
- 数量与图像的排法是经验，不是标准。

## 适用条件和取舍

- 适用于列表、设置、筛选里的选项行；卡片网格的锚点不同，别直接套。
- 混合行（有的有描述、有的没有）要谨慎；要么统一，要么只给少数项用图标。
- 窄屏上描述会更长；两行的限制要跟着宽度重算，别把阈值当成固定值。
- 行内动作超过一个（说明、删除、跳转）时，先排优先级；不是所有动作都值得占一个 Tab 停留点。
- 控件本身的语义（互斥、集合、承诺什么时候算数）在[承诺与边界](../承诺与边界/README.md)；说明文字该不该加，在[拆组件](../拆组件/README.md)的第六节。

## 还没定

- 描述在窄屏和长文本下的具体阈值。
- 0 项隐藏还是禁用，取决于列表长度和用户预期，没有统一答案。
- 计数的静态 / 动态怎么选，文案怎么写。
- 行内多个动作的布局和优先级。
- 图像尺寸和行高的关系，还没有讨论。
