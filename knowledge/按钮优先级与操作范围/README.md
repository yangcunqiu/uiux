# 按钮优先级与操作范围

设计一组按钮，先确定用户在这个任务里是否有一个自然的下一步。随后分别确定每个动作的优先级、表现形式、后果及当前可用状态。危险操作需要说明后果，红色或实心填充本身不能决定哪个动作应当默认执行。

## 主要操作与默认执行

有明确下一步的表单宜突出一个主要操作。比如“提交审核”推进流程，“保存草稿”保留进度。用户已经了解流程，且“从模板创建”和“从空白创建”确实平级时，可以给两项相同的视觉权重。把同一规则用于有明确主次的任务，会把识别下一步的负担交还给用户。

有键盘默认操作时，视觉主次应与实际执行相符。浏览器支持隐式提交时，HTML 表单的默认提交按钮是按文档树顺序属于该表单的第一个提交按钮。两个实心按钮不会因此都成为默认动作。检查输入框中按 Enter 的结果，尤其留意靠前的删除按钮。在没有隐式提交的界面中，主要按钮的视觉强调只说明推荐路径。[HTML 标准的隐式提交规则](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#implicit-submission)

## 名称、位置与折叠

按钮名称用动作说明后果。多个对象或入口容易混淆时，写“删除 3 个文件”“保存个人资料”。确认对话框的标题已经完整说明动作时，“确定／取消”也可以清楚。用真实文案和支持的语言检查按钮组是否放得下。行级动作靠近对应行，模块级动作靠近该模块，整页动作在同类页面中保持位置稳定。

同类对话框的按钮顺序优先遵循目标平台已有的约定，再采用产品内一致的顺序。例如传统 Windows 对话框常将“确定”放在“取消”之前，Material 的对话框指引将确认操作放在取消操作之后。仅凭阅读方向无法推定所有对话框的按钮位置。[Windows 传统桌面指引](https://learn.microsoft.com/en-us/windows/win32/uxguide/win-dialog-box#commit-buttons) · [Material 的对话框指引](https://m1.material.io/components/dialogs.html)

空间不足时，先审查这些动作是否都属于此处，再折叠次要动作。判断信号包括主要按钮被挤出、文案换行妨碍识别、完成主任务必须反复打开菜单。优先保留主要操作、退出方式和当前任务的唯一下一步，从一侧收起次要项，避免熟悉的主要按钮随数量左右移动。低频但后果重的操作仍需处理误触和对象核对。批量操作与选中摘要相邻时可共用范围说明，浮动工具栏或确认框脱离摘要时应重新写明影响哪一批对象。
