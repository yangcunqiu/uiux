# 一条主路

一个按钮宣布“按下会发生一件事”；一个按钮区宣布“这一段只有一条主路”。前半句是单个按钮的事，后半句是按钮区的事。混在一起，就会在“按钮有几种样式”里找答案——那是找不到的，因为这个问题把四根轴压成了一根。

## 先看演示

两个演示，双击即可，不需要本地服务。

1. [级与关系](级与关系.html)：五档与三种关系；主路就是默认动作（在输入框里按 Enter）；零主按钮、危险占主位两个失败；Windows 和 Material 的排列并排。
2. [收谁](收谁.html)：同一组动作的四种收法，点“更多”看里面；什么时候该收、收的时候哪两件事不要动。

观察重点：

- 五档那排里，有几种东西在说“这是主路”？只有一种。
- Enter 落到过第二个按钮上吗？
- 两个对话框的按钮顺序，你在哪一边更顺手？
- 关着时的四个工具栏，各自还能回答“有几个、哪些”吗？

## 一、级不是音量，是四根轴

| 轴 | 有哪些值 | 回答的问题 |
|---|---|---|
| 关系 | 主路 / 平级 / 旁路 | 这一段该做的一件事是什么 |
| 载体 | 填充、描边、无容器、只有图标 | 它占多少地方、靠不靠字 |
| 后果 | 普通 / 危险 | 做了会怎样 |
| 状态 | 可用 / 受理中 / 不可用 | 现在能不能按、按了之后到哪一步 |

几篇文章里的“类型表”落在这四根轴上：

- **主按钮 / 次按钮**：关系。
- **虚线按钮**：描边的一种样式，常见约定是“这里能加东西”（空位语义）。弱是结果，不是定义。
- **文字按钮 / 链接按钮**：载体。真正的分界是承诺——按钮在本页发生一件事，链接触发一次导航（去哪、能不能开新标签，由浏览器解释）。
- **图标按钮**：载体（不写字）。能不能只用图标另有门槛，见[入口与回执](../入口与回执/README.md)。
- **危险按钮**：后果。
- **加载按钮**：状态。
- **幽灵按钮**：容器与背景的关系。它解决的是“按钮压在图上”这一件事，不是强调度。
- **开关按钮**：另一个控件，宣布的是“它现在是这样”，见[承诺与边界](../承诺与边界/README.md)。

一个分类只装一根轴（[拆组件](../拆组件/README.md)的判据 1，B 簇已经用过一次）。分开之后，“选哪个样式”变成四个独立决定：这段有没有主路、用哪种载体、后果重不重、现在能不能按。

**“激活态”不是第五个状态。** 一个按钮显示为“已启用”，它宣布的就不是“按下会发生什么”，而是“它现在是这个模式”——那是开关或当前项，是另一个控件。混进来之后，状态这根轴就装不下了（见[受理与交代](../受理与交代/README.md)最后一节）。

## 二、主路就是默认动作

“最重要”是感觉，没法验证；“默认动作”是行为：用户只做一件事时做的那件，也是按 Enter 时系统替他按的那个。三个直接的判断：

### 两个主按钮 = 两个默认动作

浏览器只把隐式提交交给表单里第一个提交按钮（演示里按 Enter 可以复现），和它长什么样无关。两个实心并排时，视觉说“都行”，实现说“先按第一个”。这个差异用户看不见，但它每天都在生效。

想要第二条路：做成 `type="button"` 并明确处理。想要两个都可能是默认动作：只能让用户先选，不能靠样式暗示。

### 零主按钮是合法的，条件很窄

合法的零主按钮只出现在**真的平级**的分支上：用模板 / 从空白，两条路都成立，谁都不比谁更该做。条件还有一条：用户已经知道自己处在哪个流程里。

有主流程的表单里，三个同重按钮就是把“该按哪个”丢给用户。

### 危险是后果，不是更强的级

红实心“删除全部”占主位，等于把“注意后果”和“走这条路”叠在同一个位置上；如果它在表单里，Enter 也真的会落在删除上。拆开：主位留给安全的默认动作，红色用描边、或者交给二次确认承担（确认的成本与收益见[拆组件](../拆组件/README.md)的判据 2）。

## 三、文案：按钮上那句话

按钮上的字，是用户按下之前能读到的承诺。这部分能定下来的不多，而且分寸比规则重要。

**默认：写动作，有对象就写对象。** “保存草稿”“删除 3 个文件”比“保存”“删除”多给一点信息；这点信息在用户不确定对象、或者一个区里有几个相似动作时值钱。

**“确定”是正常写法。** 确认框里，标题已经把事说完了（“删除这 3 个文件？”），按钮承担“确认 / 取消”这一对约定——用户熟悉它，不需要它把标题再说一遍。这不是妥协，也不是例外。

什么时候值得把“确定”换成具体动词：

- 动作从按钮上看不出来：提交 / 发布 / 归档，只写“确定”要用户猜；
- 后果重，且需要核对对象：删除 / 停用 / 清空；
- 一组里几个动作并列，要互相区分。

**一个动词贯穿状态。** 保存 → 保存中… → 已保存，比 确定 → 处理中 → 操作成功 少一次拼接。这条接在[受理与交代](../受理与交代/README.md)上，是我的判断，不是标准。

**一组的语法要一致。** 同一组里既有“保存草稿”又有“确定”时，“确定”会显得通用而含混——不是因为它错，是因为旁边有更具体的词，一比就空。要么整组都用具体动词，要么把“确认 / 取消”单独成一对。

**长度不是字数。** 约束是三条：一组里能等宽、窄处不换行、本地化之后还放得下。中文 2–4 字是经验值，不是规则。

## 四、位置与顺序：平台优先，团队次之

同一个问题，两家官方指引给出相反的顺序：

- Windows 的传统指引：从左到右 Help / OK / Cancel / Apply（[Command Buttons: Design Guidelines](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/bb246415(v=vs.85))）。
- Material：affirmative 在右，dismissive 紧挨在它左边（[Dialogs](https://m1.material.io/components/dialogs.html)）。

两家相反，各自都对。能说的只有三条：

1. **对话框里跟操作系统。** 用户在同一个系统里积累的肌肉记忆，一页纸改不掉。
2. **页面内跟本产品。** 一致性优先于“哪个更合理”；用户不会在两页之间切换平台。
3. **团队自己的“靠边原则”是团队约定**——按钮区在左就左边优先，在右就右边优先。它成立的条件是全产品一致，不是有跨产品证据。

还有一条推论，标明是推论：在从左到右阅读的界面里，主路放在先读到的位置（左侧）更顺。但它在对话框里让位给平台习惯；两者冲突时平台赢。

### 按钮区放在哪

位置跟它控制的对象走：

- **行级动作跟行**（表格行末、列表项里），不要集中到页面顶部；
- **模块级动作放在模块的头或尾**，不要放进另一个模块；
- **整页动作放在整页的固定位置**（页头、底栏），换页面时位置不变。

依据是“靠近它控制的对象”，不是 F/Z 浏览模式。F/Z 是阅读研究（长文本页面上的眼动路径），不能直接推出按钮该放哪里；拿它当依据，容易得到“按钮都放左上”这种没有条件支持的结论。

## 五、挤不下时收谁

按钮多到放不下，常见做法是收进“⋯”。这里有个容易滑过去的判断：**折叠是优先级声明，不是布局技巧。** 折进去等于宣布“此刻不需要它”。所以先决定谁可以被降级，再决定怎么塞。

### 不能收的三类

- **主路**：收了就等于这个页面不再宣布自己要做什么。
- **退出**（取消、返回）：随时可能被用到，找不到它的代价比找不到一个导出大。
- **当前任务的唯一下一步**：收了任务就走不下去。

其余可以收。但“低频”只是“值不值得占地方”的理由，不是“能不能藏”的理由：低频而后果重的动作，收起来之后仍然要配确认或说明。

### 收了要还能找到

触发器是入口，要能回答“有几个、哪几个”：只写“⋯”，关着时连“有几个”都答不了。入口怎么写、留痕分几级，在[入口与回执](../入口与回执/README.md)和[藏起来的代价](../藏起来的代价/README.md)。

### 主路不随隐藏数量挪位置

收旁路时，如果剩下的按钮重新居中，主按钮会跟着挪。固定在一端收，主路位置才稳定——用户记住的是位置，不是“第三个”。这就是第四节“靠边”的另一个用途。

### 不给数量阈值

一组几个按钮开始折叠，没有能通用的数字：它取决于这一屏多宽、文案多长、动作的频率和后果分布、平台。给一个数字，在任何一组具体条件下都会错。

能用的是信号：

- 主路开始被挤走、换行，或者要滚动才能看见；
- 关着时回答不了“有几个、哪些”；
- 完成主任务要多走一次菜单。

出现任一信号就该收；收谁按上面三类判断。

### 上游还有一问

折叠是补救，不是设计。按钮多到要折，先问“这些动作是不是都该出现在这里”，再问“收谁”。

## 几条被收窄的说法

**“次按钮永远不出错”。** 只在“不夸大”这一维成立：把不确定的事画成次按钮，不会假装它是主路。但用错时主路没被宣布，用户要在几个同色按钮里挑。所以问题不是“选哪个安全”，是“这里有没有主路”。

**“按 F / Z 模式放按钮”。** 见第四节的「按钮区放在哪」：F/Z 讲的是阅读，不是按钮位置。

## 和「点击之后」的分工

[点击之后](../点击之后/README.md)讲一次点击的三个时刻（悬停、按下、松开）和它的动效；这里讲按钮区宣布什么关系。混着读，会把“主次”和“状态”当成同一件事。

## 为什么这样判断

- 四根轴是从几篇文章的类型表里并出来的：按“回答的问题”归类，同一根轴上的值可以互换，不同轴上的值不能。
- 主路 = 默认动作来自两个可验证的事实：HTML 的隐式提交规则，和平台默认按钮的行为。演示里用 Enter 复现过。
- 排列那一节来自两份官方指引；它们互相冲突这件事本身就是证据——没有跨平台答案。
- “主路在阅读起点一侧”没有实验支撑，是推论，所以只写在条件里，没有当作规则。
- 零主按钮的“窄”来自演示里的对照：平级分支上成立，有主流程时失败。
- 文案那几条里，“确定”在确认框里是正常写法——这个判断来自“确认 / 取消”是一对用户熟悉的约定，不是从标准推出来的；具体动词的三种情形（动作看不出、后果重、并列要区分）都可以在界面上直接指出来。
- 折叠的“不能收三类”来自关着时能回答什么；不给数量阈值，是因为数字依赖布局和动作分布，写死就是错的；三个信号对应演示里能看到的三种失败。

## 适用条件和取舍

- 适用于表单、工具栏、对话框里的按钮区；不适用于导航项（那是位置，不是动作）。
- “主路 = 默认动作”依赖“有默认动作”这个前提。没有表单、没有 Enter 默认的界面里，主路只是一个视觉声明，Enter 不参与——那时两个主按钮的代价小一些，但仍然没有回答“该做哪个”。
- 四根轴的组合不产生唯一答案；每根轴都要回到具体场景。
- 零主按钮的合法条件很窄；拿不准时，先问“这里有没有主路”，而不是“选哪个样式”。
- 排列的平台优先只在系统级窗口成立；网页没有系统默认，跟产品。
- 文案的判据是“用户读这行字能不能知道会发生什么”，不是“字数够不够短”。长文案在窄处换行、在本地化后溢出，比多两个字更贵。
- 折叠的三条规则只在有按钮区的界面成立；移动端底部操作栏、表格行内、卡片里的按钮组，形态不同，没有讨论。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 四根轴 | 定义 | 写死 |
| 主路 = 默认动作 | 定义（由实现决定） | 写死 |
| 一段一个主路 | 默认 | 可偏离：真的平级时为零 |
| 排列 | 平台约定 | 跟平台；团队补充 |
| 文案：写动作、“确定”在确认框里正常 | 默认 | 看场景，不标成例外 |
| 文案长度 | 经验值 | 中文 2–4 字；真正的约束是等宽、不换行、本地化 |
| 折叠：不能收的三类 | 定义 | 写死 |
| 折叠：何时开始收 | 条件 | 写信号，不写数字 |
| 五档外观的具体参数 | 经验值 | 标来源，别当推导 |
| 尺寸档位、圆角 | 系统参数 | 圆角见[约束与调性](../约束与调性/README.md)；档位数值不沉淀 |

## 还没定

- 一个按钮区里有两个危险动作时怎么排，没有展开。
- 移动端底部操作栏和按钮区的关系，没有讨论。
- “主路在阅读起点一侧”在从右到左的语言里是什么形态，没有查证。
- 文案在多语言下的长度策略（英文、德文通常更长），没有实测；“2–4 字”只是中文经验。
- 折叠菜单里的顺序与分组要不要跟工具栏一致，没有讨论。
- 文字按钮和链接在视觉上怎么区分（下划线、悬停、颜色），各团队约定不同，没有讨论。
