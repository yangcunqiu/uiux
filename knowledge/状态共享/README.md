# 状态共享：把 N 个对象变成 1 个对象加 N 个状态

背景的高亮在按钮之间滑动、几个 Tooltip 合成一个、只有第一个弹层等待——这些看起来是不同的技巧，其实是同一个动作：**把 N 个各自出现的对象，重构成 1 个对象的 N 个状态。**

用户看到的不是"一堆东西在换"，是"一个东西在变"。

## 先看演示

- [共享背景](共享背景.html)：同一个工具栏，独立背景 / 组内共享 / 全表共享。
- [共享弹层](共享弹层.html)：四个按钮的说明，各自一个弹层还是共用一个。带隐藏延迟滑块。
- [分页器](分页器.html)：indicator 在数字下面，还是在数字上面。

都是单文件，双击打开。前两个依赖 hover。

## 一、共享的收益有两项，不是一项

| 收益 | 条件 |
|---|---|
| **连续**：没有"消失 → 生成" | 共享任何对象都有 |
| **分组**：这些是一个组 | 只有当被共享的对象是"空"的时候才有 |

背景、indicator、边框是空的，不携带个体信息。共享它们，等于说"这一组只有一个状态"，所以分组感最强。

弹层、卡片有内容。容器合并了，内容还在区分，用户看到的是"一个容器换了内容"，分组感弱很多。

由此得到三种用法：

- 想要**分组** → 共享空对象（背景、indicator、高亮）。
- 想要**连续** → 共享什么都行。
- 两个都要 → **共享容器，内容各自独立**。

分页器就是第三种：indicator 共享（空对象，给分组），页码数字各自不动（内容独立，保留"当前是第几页"的判断）。把数字塞进 indicator 里一起滑，分组感没了，还会出现"数字经过错误位置"。

## 二、适合替换，不适合增删

- **替换**：A 变成 B，还是同一个对象 → 共享，用户看到连贯。
- **增删**：A 没了，或者 B 出现了 → 不共享，各自出现和消失。

因为"消失"和"出现"本身就是信息。删掉一条，用户要看到它消失，才知道删掉了；如果共享成一个对象移走，就看不出"没了"。新增也一样，需要抓住注意力。

## 三、共享延迟：把"确认"变成状态

延迟的目的不是等，是**确认意图**。200ms 是在问"你是真的停在这里，还是路过"。

如果每次都要问一遍，横扫一排就是连续排队——用户已经明确在浏览了，系统还在一个个确认。

共享延迟把"第一次确认"之后的状况记成一个持续状态，后续不再询问。第一个弹层延迟，之后立即。

边界：只在"确认一次就够"的场景成立。危险操作、需要逐个核对的场景，每一次都必须独立确认。

这里延迟是**成本**，共享的目的是只付一次。同一个词在别处是相反的用法：爱心和它撞出的背景，背景晚 0.1s，那个延迟是**信息**——去掉就没有了"谁推谁"。判断方法是把延迟归零，看丢了什么：丢的是重复确认 → 成本型，能共享就共享；丢的是因果 → 因果型，必须保留，方向不能反。见 [点击之后](../点击之后/README.md) 的「延迟的三种用途」。

## 四、共享范围不能由 DOM 决定

材料选择"同父元素自动共享"来换免配置。问题在于 DOM 结构会因布局需要改变——响应式把一组按钮拆进两个容器、把"更多"单独拎出来——语义没变，分组断言却变了。

同一个功能在宽屏上是一组，在手机上变成两组，说不通。

所以共享范围应该由语义决定，代价是要显式声明分组，不能白捡。

## 五、重叠不是"多对象"造成的

容易把"多个弹层互相遮挡"归因于"弹层不能共存"。不是。鼠标同一时刻只能在一个按钮上，如果隐藏是立即的，任何时刻都只有一个弹层。

遮挡的直接原因是**过渡期**：旧的还没消失，新的已经出来。把隐藏延迟调到 0，遮挡就消失。

但延迟也不能真的取消——如果弹层需要鼠标移进去点击，中间的空隙会让它在你到达之前消失。所以延迟是必需的，重叠是它的副产品。

共享解决的不是重叠，是**切换时的连续性**：没有共享，就会看到"旧对象消失、新对象生成"；共享之后，只有一个对象在移动。这个差别在延迟为 0 时依然存在。

## 六、临时合并：空间冲突时合成一个

两个表示在空间上撞到时，还有第三种解法：不强行都显示，也不永久藏掉一个，而是按空间动态合成一个，空间够了再分开。

双滑块是最典型的例子：两个 Tooltip 分开时分别标出两端，重叠时合成「40–50°C」。合并后信息其实更清楚——用户关心的本来就是区间。

它和共享是同一族的两种做法：

- **共享**：N 个对象重构成 1 个对象 + N 个状态，持久、结构性，由语义决定。
- **临时合并**：两个对象在冲突时临时合成一个，可逆、由空间决定。

成立条件：

1. 合并的确实是同一类信息（区间的两端可以合成区间；两个无关的说明不行）。
2. 合并后的表示仍然可读，而且不比分开差。
3. 合并和分开的阈值要错开（滞后）。用同一个距离判断，拖动时会在临界点反复切换、闪烁。

同样的动作也出现在别处：标签挤在一起合并成「3 个」、面包屑空间不够时中间折叠、表格列不够时隐藏次要列。都是「空间不够时，用合并代替都显示或者丢掉一个」。

## 七、层叠：另一种处理「多个」的方式

共享是「只留一个」，层叠是「都留着，但压起来」。演示见 [层叠](层叠.html)。

层叠是一笔交易：**用空间换数量，再用交互换回内容。** 平时压缩成一条缝，需要时展开成平铺。

它成立要三个条件：

1. 数量可能多，但不希望占满屏幕。
2. 平时不需要读全部，只需要知道「有几条」。
3. 有一个可靠的展开方式。

第三条是材料没充分讨论的：hover 展开只对指针设备有效。触摸端没有 hover，层叠的消息就变成「藏起来」——数量靠边缘估、内容读不到、点一下可能是关闭而不是展开。所以层叠要么给不依赖 hover 的展开方式，要么在触摸端退回平铺。

还有一个代价：**丢失是静默的。** 上限三条，第四条进来挤掉最早一条，而最早那条本来就在最底下，被移除时几乎没有视觉变化。所以层叠适合「不重要、可以丢」的消息，不适合「每条都必须被看到」的（错误、警告、需要处理的通知）。

两种层叠要分开：

- **通知型**（材料里的 Message）：任务是知道发生了什么，全部展开是对的。
- **浏览型**（一叠卡里挑一张）：任务是选择，只突出当前项才对。

同样是「一叠」，展开策略相反。浏览型的具体交互还没定，见「还没定的」。

## 适用条件和取舍

- 共享的成本是复杂度和 DOM（材料里的做法要叠两层用 clip-path，DOM 翻倍，而且要求所有变化的运动方式一致）。变化多、组件复杂的系统里，这个成本可能超过收益。
- 共享的前提是"同一时刻只需要看到一个"。需要同时对比两个状态时，共享做不到。
- 元素位置相距很远时，共享的运动时间会变成等待。
- 减少动态效果：共享的运动可以退化成"直接切换"，分组感会消失，但连续性不需要用动画表达。

## 还没定的

- 共享延迟没有单独的演示，现在只在共享弹层里以两种模式对照了一次。
- "切换频率"对共享收益的影响还没有具体数值，只能说高频时收益更大。
- Functional Motion 里的层叠（多条 Message / 嵌套 Dialog）还没讨论，那是"层叠"不是"共享"。
