# 跟手与平滑

拖拽、滚动、跟随这类交互，输入是连续的：手指或指针一直在动。这类交互里有一个很容易说错的判断——响应越快越好。实际上"快"和"顺"是两件事，而且经常互相牵制。

## 先看演示

[打开演示](实时与连续.html)（双击即可；`motion.js` 需要和它放在同一目录）

两行轨道接收同一个拖动输入：

- 蓝色实心块是实际显示的位置。
- 红色虚线框是目标位置，也就是手指在哪。
- 两者错开多少，就是落后多少。

可以调三样：跟随时间（弹簧硬度）、回弹（阻尼比）、输入抖动（模拟采样不均）。松手后还可以选择追赶、吸附、冻结。

观察重点：

1. 慢速拖动时两行几乎一样，虚线框正好套在蓝块上。
2. 快速来回拖时，RAW 的蓝块围着虚线框抖，弹簧的蓝块更顺，但会离开虚线框。
3. 输入抖动归零再快速拖，两行差别明显缩小。
4. 松手时顶栏会记下那一刻的落后量。

## 我们的理解

### 实时和连续是两个问题

- **实时**问的是：输入发生后多久屏幕上出现变化。它由采样、事件合并和帧率决定。
- **连续**问的是：变化过程平不平，每帧走的距离是否均匀。

一比一跟随把实时做到了极致——零延迟，输入在哪画面就在哪。但它同时把输入的每一个不均匀原样搬到屏幕上：采样间隔不均、手抖、掉帧抖动，全部照抄。所以实时不等于连续。

给跟随值加一层弹簧，改变的是第二件事。

### 弹簧不是变慢，是允许落后

从手指动到物体动，响应时间几乎没变——每一帧都在积分。变的是运动过程中物体落后多少。

临界阻尼、匀速拖动时，落后量近似：

```
落后 ≈ 0.32 × 速度 × 跟随时间
```

| 跟随时间 | 慢拖 100px/s | 快拖 600px/s | 快拖 800px/s |
|---|---|---|---|
| 100ms | 3px | 19px | 26px |
| 200ms | 6px | 38px | 51px |
| 300ms | 10px | 58px | 77px |

所以"加一点感知不到延迟"这个说法只在低速下成立。同一个 100ms，慢拖时无感，快拖时能落后二十多像素。

更准确的说法是：**用可感知的跟随误差，换不可感知的轨迹毛刺**。

### 代价是准确度，不是时间

落后意味着物体不在手指底下。同一条代价，对不同目标轻重完全不同：

- 翻页、甩卡片、转盘这类粗粒度目标：落后无所谓，甚至更自然，因为它像有质量的东西。
- 滑块调数值、裁剪、画线这类精确目标：落后是硬伤，用户会觉得"拖不准"。

所以判断标准不是"要不要流畅"，而是：**目标有多粗、错误能不能挽回、输入到底有多不平**。

### 只有输入不平的时候，平滑才有事可做

把输入抖动归零，两行几乎一样。这说明弹簧抹掉的是输入噪声，不是"让画面变好看"。

如果输入本身干净（程序驱动的动画、键盘步进），加这层弹簧就只剩落后，没有收益。

### 松手时如果还落后

按住时产生的落后不会在松手瞬间消失。怎么处理有三种，感觉完全不同：

| 处理 | 看到的 | 感觉 |
|---|---|---|
| 追赶 | 虚线框不动，方块自己滑过去 | 150ms 内像"收尾"；300ms 以上像"还没完" |
| 吸附 | 方块瞬间贴上 | 差距小时像"停得准"；差距大时像"跳了一下" |
| 冻结 | 停在落后位置 | 像"没拖到位"，除非把目标改成落点 |

"冻结"只有在把目标重新定义成落点时才自洽：虚线框跳到方块身上，用户看到的落点就是最终位置，代价是它和手指离开的位置不一致。

还有一个容易漏掉的点：**吸附把落后藏起来，追赶把它暴露出来**。同一个跟随时间，吸附让人觉得"没动"，追赶让人觉得"它还在动"。

### 按住和松手是两套机制

[拆组件](../拆组件/README.md) 那一节讲的是松手之后：可中断性、惯性、越界阻力、回弹。这里讲的是按住的时候：要不要平滑、落后多少、松手瞬间怎么收。

两者容易混，因为都叫"弹簧"。实际用处分得很清楚：按住时的参数决定跟不跟手，松手后的参数决定停在哪、有没有惯性。

用同一组参数管两件事，会出现"一松手东西换了一个"的感觉。正确的约束不是必须同一套参数，而是：**参数可以不同，状态必须连续**——松手瞬间的位置和速度要被继承，视觉上才不会跳。

## 为什么这样判断

- 输入抖动归零后两行差别消失，说明这层平滑的作用对象是输入噪声，不是运动本身。
- 落后的量级可以从弹簧的稳态解复算，表里的数字是按演示速度估的，不是测量值。
- 松手三种处理的判断来自演示里的对照和一次个人观察，还没有用户测试支撑。

## 精确输入的边界：滑块

演示见 [滑块跟随](滑块跟随.html)：两条滑块，一条即时跟随，一条过一层弹簧，可以直接比较游标和目标值差多少。

滑块输出的是一串可比较的数，37% 和 38% 是两回事。所以它的合法误差是 0——任何平滑都会让「我看到的数」和「我手指的位置」对不上，用户会犹疑、反复微调。

这条正好检验前面的判断：**精确目标不加平滑**。滑块要的「丝滑」是响应及时、数值清楚，不是运动顺滑。原生 `input[type=range]` 从来不做平滑，就是这个原因。

由此还能推出两条：

- 滑块适合「粗略调节 + 需要看到整体范围」，不适合精确输入。所以它经常和输入框成对出现，不是二选一——配输入框那条建议，本质是在承认滑块自己解决不了精度。
- 范围滑块的两个数值提示会互相遮挡。解法不是「只显示一个」，而是**两个都显示、重叠时合并成一个区间**。合并后信息反而更清楚，用户关心的本来就是区间。

## 惯性：把速度差变成姿态

演示见 [惯性](惯性.html)（单文件，双击即可）：同一个拖动，三种画法——一块整体跟手、分成两个端点、分成六个端点。

拖的时候物体后仰，停下回正。看起来像"给旋转加了一层弹簧"，实际不是：**同一个物体取两个点，让它们各自跟一层弹簧，两点的水平差换算成倾角。**

```
内部差 = 顶端的位置 - 底端的位置
倾角   = atan2(内部差, 参照长度)
```

参照长度取物体的视觉高度，不是随便一个常数。这样算出来的角度和"被拖歪了多少"在几何上是对应的；换个数只是把效果放大或缩小。

### 第二个点的作用不是"慢"，是"不一样"

这是最容易搞混的一点。让第二个点更慢，本身不产生任何东西——它只产生"落后"。被看到的是两个落后的**差**。

所以，两个点落后一样多，差值是 0，一点惯性都没有。

按演示的参数（手柄跟随时间 70ms、阻尼比 1；第二点阻尼比 0.72）复算匀速拖动 2 秒的峰值：

| 第二点 | 200px/s | 400px/s | 600px/s | 1000px/s | 1600px/s |
|---|---|---|---|---|---|
| 100ms | 0px / 0° | 1px / 1° | 1px / 1° | 2px / 1° | 4px / 2° |
| 180ms | 4px / 2° | 8px / 5° | 12px / 7° | 20px / 12° | 32px / 18° |
| 260ms | 8px / 5° | 16px / 9° | 24px / 14° | 39px / 22° | 63px / 33° |
| 400ms | 15px / 9° | 29px / 17° | 44px / 25° | 73px / 37° | 117px / 51° |

（按演示参数算出的模型值，不是实测。）

两件事值得留意：

- 100ms 那一行几乎是 0。因为手柄自己就有 70ms 的落后，两者互相抵消。**手柄越跟手，第二个点越容易显出差别**——同一件事的两面。
- 同一组参数，慢速划过只剩几度，快速划过能到三十几度。惯性不是"预设的动作"，是**把速度变成看得见的量**。

### 角度天然有界

| 内部差 ÷ 参照长度 | 倾角 |
|---|---|
| 0.1 | 5.7° |
| 0.5 | 26.6° |
| 1 | 45° |
| 2 | 63.4° |
| 4 | 76° |

角度随差值单调增长但会饱和，永远到不了 90°，翻不过去。好处是不会出现失控的大翻转；代价是**慢速小幅动作几乎看不出来**，只有快速大动作才明显。这正好是它读起来像"重量"的原因：轻拿轻放不晃，猛地一甩才晃。

要让它对小动作也敏感，只能把分母改小（夸张化）；但那样大动作会顶到 76° 附近不再变化，看起来像卡住。这是同一个旋钮的两端。

### 2 个点是 N 个点的特例

把跟随时间拆成一条递增的序列，就得到拖尾：最前面跟手，越往后越慢。两个点是它最简单的版本。

`useTrail` 常被当成"多个元素依次入场"的工具，因为默认用法就是错落。但错落用 `setTimeout` 或 CSS 的 `transition-delay` 也能做，不需要运动库。它不容易替代的是：**一串物理上各自独立、又共享同一个目标的弹簧**。错落只是它们依次到位时看到的样子。

### 它必须写在 JS 里

CSS 能表达"从 A 过渡到 B"，表达不了"两个各自在动的位置相减"。所以这类效果不是换更好的参数，是换一个结构。

反过来，库在这里只是词汇。最关键的一步——两点之差怎么变成角度——和用哪个库无关，`Math.atan2` 就够了。

### 出现的那一刻要先对齐

悬停卡片出现时，如果两个点从头追起，第一步会甩一大下。原文的处理是 `mouseEnter` 先把位置直接设过去，摆动只发生在之后的移动里。

演示里也一样：鼠标进入区域或按下时，两点直接对齐到指针位置。不处理这一条，第一次移动看起来像抽搐。

### 边界

- **只对持续输入成立**。它的输入是速度：手快角度大，手停角度归零。所以只出现在拖拽、悬停这类连续输入里，不适用于点击后的固定过渡。
- **悬停只在有指针的设备上**。触摸屏没有 hover，这套交互要么改成拖动，要么不出现。
- **会把输入抖动放大成角度抖**。两个点各自滤波，差值的噪声约等于两者之和；手抖、掉帧都会变成物体在晃。
- **第二点太慢时一体感消失**。演示里 60ms 到 600ms 之间，超过某一段就看起来是"气球脱手了"。
- **参数不保证观感**。原文的配置（快：tension 1500 / friction 40；慢：mass 2.6 / tension 400 / friction 50）按阻尼比算出是 0.52 和 0.78，都低于临界阻尼，所以回弹明显。要稳就把阻尼比推到 1。

## 适用条件和取舍

- **适用**：连续输入驱动的跟随（拖拽、滚动、跟随），目标粗粒度，错误可挽回，输入确实不平（触摸屏、低帧率、手抖）。
- **不适用**：点击反馈需要立即的状态变化；固定距离的过渡用时长描述更合适；精确输入（滑块、裁剪、数值）不该用；输入本身很干净的场景，加了只剩落后。
- **惯性要两个以上独立跟随量**：一个跟随时间只买得到"慢"，买不到"歪"。两个跟随量落后相同，等于没有。
- **"时间是结果不是原因"有边界**：它适合速度驱动、距离不固定的运动；固定距离的过渡仍然可以用时长描述。
- **减少动态效果**：这里的弹簧抹的是抖动，不减少运动量。对运动敏感的用户需要的不是动得平，而是少动。
- 演示里的 100ms、0 回弹、8px 抖动、70ms 手柄、260ms 第二点都是演示值，不是推荐值。

## 例子

- 一叠卡片向下滑：第一张卡每帧位移接近 10px，看起来是跳的；接一根很硬的弹簧后约 5px 一帧，变连续，代价是几毫秒的落后。
- 转盘的横移与旋转比例：比例太大变迟钝，太小变灵敏，目标是跟手。
- 亮度滑块：需要实时看到效果，不能加这层平滑。
