# 提交边界

一个表单的边界不是页面，是**事务**：哪些字段一起生效、一起失败、一起进入下一个状态。按钮放在哪、写什么，等于宣布这个边界；但位置只是宣布，边界本身由数据模型决定。

这篇讲四件事：页面 / 表单 / 事务的区别，按钮位置，保存和提交的语义，以及分段保存到底什么时候成立。结构（顺序、列数、分组、分步、标签页、锚点）在[表单骨架](../表单骨架/README.md)；校验时机和错误位置在[填错的时机](../填错的时机/README.md)。

## 先看演示

两个页面，双击打开，不需要本地服务。

1. [提交边界](提交边界.html)：同一个 15 字段表单，切页尾 / 粘性页脚 / 顶部 / 顶部 + 页尾 / 分段保存。读数写「入口几个、提交边界是什么」；每次提交都看 payload 里有哪些字段。

   - 页尾：1 个入口，边界整张表（15 字段）。
   - 粘性页脚：1 个入口，边界整张表；滚动中一直可见。
   - 顶部：1 个入口，边界整张表；滚动后消失，错误在下面。
   - 顶部 + 页尾：2 个入口，边界还是一个；两个默认动作。
   - 分段保存：4 个入口，每次一段；payload 只含那一段。

2. [分段保存](分段保存.html)：同一组 9 个字段，切「一条记录 / 三个独立资源」。

   - 三个独立资源：每张卡一个保存（「保存个人资料」）、自己的状态（已保存 / 有未保存的修改 / 保存中 / 失败）、自己的 payload；通知保存失败不影响个人资料；安全设置只读，只有「申请权限」。
   - 一条记录：三段只是字段分组；页尾一个提交；任何改动让整张表变未保存；失败影响整张表；payload 整张表。

## 一、页面、表单、事务

「表单」被当成三种东西了：

- **页面 / 容器**：用户在哪看见、怎么找到。设置页、订单确认页、详情页。
- **表单 / 事务**：哪些字段一起生效、一起失败、一起进入下一个状态。
- **资源**：后端的一个对象/接口。个人资料、通知偏好、安全设置是三个资源。

一个页面可以有多个表单：设置页把三个独立资源放在一起，各有各的保存和状态；页面叫「设置」，不叫「一个表单」。三个资源就是三个小表单，只是共享同一个账号上下文。你看到「一个表单」，是因为它们被放在一个页面、一个 `<form>` 容器里；那是 UI 的实现，不是数据模型。

一个表单也可以跨几页：向导是同一个事务拆成几页，页面只是导航，最后只有一个提交。

所以：**页面是容器，表单是事务。** 一个页面可以有多个表单，一个表单也可以跨多页。

为什么把独立的段放一起？共享上下文、可发现性、用户一次想改几项；这是页面分组，不是事务合并。代价是必须把边界画出来：每段自己的保存、状态、范围；画不出来，就拆页面，或者把它们合成一个资源、一个提交。

订单确认页是混合的：地址、发票、优惠券各自是资源（可以单独保存/选择），最后的「提交订单」是一个新事务（创建订单）。页面把它们放一起，因为下单需要它们；但「保存地址」和「提交订单」不是同一件事。

## 二、按钮位置

| 位置 | 入口 | 边界 | 代价 |
|---|---:|---|---|
| 页尾 | 1 | 整张表 | 长表单要滚到底；错误在按钮上方 |
| 粘性页脚 | 1 | 整张表 | 常驻工具栏；少一个「填完」的时刻；fixed 要留底部空间 |
| 顶部 | 1 | 整张表 | 阅读顺序倒置；滚动后消失；错误在下面 |
| 顶部 + 页尾 | 2 | 整张表 | 两个默认动作、两把锁、两处结果；Enter 落在第一个 |
| 分段保存 | N | 每次一段 | 数据模型问题；只有独立资源/草稿才成立 |

**页尾是默认。** 按钮在问题结束的地方；表单长时要滚到底，错误在按钮上方，提交后聚焦第一个错误会把用户带回去。

**粘性页脚是长表单的折中，不是升级。** 一直可见，理论上可达性更好；但它把提交从「结尾」变成一条常驻工具栏：可达性上去了，用户少了一个「填完了」的时刻，常驻的主按钮还一直抢注意力。它多了一层：字段是文档，工具栏是另一层；fixed 版还要留底部空间，否则盖住最后一行和最后一个错误。一次性的短表单不值得；超长表单、频繁保存草稿/分段操作的工作台、移动端键盘挡住底部时，才是它的场景。

**顶部是反例。** 主提交在问题前面，阅读顺序倒置；用户可能没看完就提交，错误在下面、按钮在上面；滚动后按钮消失。顶部适合「返回 / 保存草稿」这种次要、全局动作，不适合唯一的提交。

**顶部 + 页尾是反例。** 两个入口不是「更方便」，而是两个默认动作、两把锁、两处结果；Enter 先落在第一个提交按钮上，用户不知道两个按钮是否一样。要可达性，用一个入口 + 回顶部，或者接受页尾，不要两个提交。

**分段保存不是按钮位置。** 每段一个保存，payload 只含那一段；边界是「段」，不是「从这次按钮到上次按钮之间」。详细在第四节。

**按钮文案就是边界的名字。**「提交」= 整张表；「保存个人资料」= 这一资源；「保存草稿」= 草稿（不校验）；「下一步」= 导航，不是提交。不要用「提交」去干「下一步」的事；「提交」是个弱标签，用领域动词：保存草稿 / 发起审批 / 发布 / 下单。

**边界要能被 payload 验证。** 用户应该能回答「我按这个按钮，哪些字段会被交上去」。如果按钮提交的字段和用户以为的不一致，就是边界不清。

## 三、保存 vs 提交

| | 保存 | 提交 |
|---|---|---|
| 意图 | 留住现在的状态 | 交给下一个流程/人 |
| 校验 | 可以不全；草稿允许不完整 | 全量/业务规则；必填 |
| 副作用 | 基本没有；可继续改 | 发起审批/下单/发布/通知；可能不可逆 |
| 状态 | 已保存 14:32；仍可编辑 | 已提交/审批中；可能锁编辑/可撤回 |
| 范围 | 一个资源/一段，或整份草稿 | 通常一个事务/一条记录 |
| 失败 | 没存上，重试 | 可能部分生效；要幂等/补偿 |

- **保存 = 写当前状态；提交 = 状态迁移 + 副作用。**
- 保存是「我还没交，但别丢了」；提交是「我交出去了，按这个走」。
- 保存可以是自动的；提交必须是显式的。
- 两者可以并存：订单确认页里，地址、发票是资源，可以各自保存/选择；最后的「提交订单」才是事务。设置页只有保存，没有提交；审批单是「保存草稿 + 提交审批」。
- 如果段保存本身发起了流程，它就不是保存，而是「提交本段」，边界就在这一段。
- 「保存并提交」把两件事塞进一个按钮，副作用和失败语义都混；要么分开，要么明确用「提交」并自动保存。

## 四、分段保存

分段保存不是「按钮位置」的变体，是数据模型：**每段是不是一个可以独立保存/生效的资源。**

一条记录 vs 三个独立资源：

| | 一条记录 | 三个独立资源 |
|---|---|---|
| 字段 | 三个分组 | 三个资源 |
| 保存 | 页尾一个提交 | 每段一个保存 |
| 状态 | 整张表 已保存/未保存 | 每段 已保存/有未保存/失败 |
| 失败 | 影响整张表 | 只影响那一段，可单独重试 |
| payload | 整张表 | 那一段 |
| 适合 | 跨字段校验、最后一起生效 | 设置页/权限/可重复对象/草稿 |

**什么时候成立：**

- 每段是独立资源（资料 / 通知 / 安全设置），各自有保存接口；改通知不用重交资料。
- 每段权限/可编辑性不同（一段只读、一段可编辑）；只读段没有保存，只有「申请权限」。
- 每段是可重复对象（列表里的一行/一张卡），按钮的范围是那个对象。
- 只是存草稿，最后仍有整表提交。

**什么时候不成立：**

- 几段是同一条记录的多个部分，共享跨字段校验、最终必须一起生效。分段保存就是假保存：用户以为整张表保存了，其实只存了一段；后续段的覆盖、最终提交的边界都会乱。这时只能用页尾一个提交。
- 只是「按钮太多想拆开」：那不是数据模型，是布局；拆完用户更不知道边界。

**范围由段决定，不由按钮位置决定。**「从这次保存按钮到上次那个保存按钮之间」不是范围；最后一段没有下一个按钮，范围仍是这一段。按钮写「保存个人资料」，状态写「个人资料已保存 17:02」，payload 只含这一段；范围要能被读出来，不能靠用户数按钮。

演示里：通知卡打开「下次保存失败」，保存通知只让通知卡变红；个人资料仍是已保存，payload 是「保存失败，没有提交内容」；重试只重试通知。安全设置只读，只有「申请权限」。一条记录模式里，三段只是字段分组，页尾一个提交，失败影响整张表。

## 为什么这样判断

- 按钮位置、payload、失败状态都是演示里可操作的；页尾 / 粘性 / 顶部 / 顶部 + 页尾 / 分段保存的边界是读数和按钮位置直接看的。
- 粘性页脚的「怪」来自层和常驻，不是可达性；可达性是真的，代价是叙事和注意力。这是判断，不是测量。
- 顶部 / 顶部 + 页尾是反例：阅读顺序、两个默认动作、Enter、锁和结果；不是「两个入口更方便」。
- 分段保存的成立条件是数据模型：独立资源、权限、可重复对象、草稿；一条记录拆段是假保存。演示里两种模式的 payload 直接对照。
- 演示里的 700ms / 900ms 保存延迟和「模拟失败」是演示值；真实失败来自服务端。没有做用户测试。

## 适用条件和取舍

- 页尾默认；粘性页脚给超长表单/工作台/移动端键盘；顶部只给次要动作；顶部 + 页尾不要。
- 一个表单默认一个提交边界；多入口只有同一个边界时才允许，且要按一个主入口 + 次要入口处理。
- 分段保存只在「每段是独立资源/独立动作/草稿」时成立；一条记录、共享跨字段校验、最后一起生效，用一个提交。
- 保存和提交分开：保存是写状态，提交是交出去；标签写范围/后果，不写泛泛的「提交」。
- 只读段没有保存，给「申请权限」；分段失败只重试那一段；payload 只含那一段。
- 跨页/订单确认这类混合页：资源可以各自保存，最后的提交是另一个事务；不要让「保存地址」看起来像「下单」。

## 还没定

- 粘性页脚 fixed 版的底部留白、和页面 footer 的关系。
- 顶部 + 页尾两个入口的重复提交锁、结果交代；有没有一个场景真的需要两个主提交。
- 分段保存和草稿的合并：切回恢复、未激活、清空提示。
- 跨字段校验在分段/分步里的位置；标签页每标签校验要不要做。
- 批量「全部保存」：多个资源一起保存，部分失败怎么交代；和分段保存的关系。
- 按钮顺序、主次、Enter 默认；移动端底部栏；自动保存和显式提交的关系。
- 多入口的结果提示、失败重试、幂等；R 簇会接。

**留给别的簇**：R 簇「状态提示」（提交结果、toast、撤销）、E 簇「表格与列表」（行内编辑/批量保存）、J 簇已收敛（按钮/底部栏的具体规范值不沉淀；见[约束与调性](../约束与调性/README.md)）。
