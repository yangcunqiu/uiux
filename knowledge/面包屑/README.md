# 面包屑

面包屑画的不是"路径"，是**祖先链**：这个对象属于谁。

它不回答"你怎么来的"——那是返回键的事；也不回答"这个功能在菜单的哪一格"——那是菜单高亮的事。三个问题、三个来源，所以它们经常对不起来。

## 先看演示

[三处回答](三处回答.html)：双击打开，不需要本地服务。

同一个对象（订单 0032），从三个入口进去。页面上有三个地方会说话，下面各有一行读数：

- **面包屑**：这个对象属于谁
- **返回**：我上一步在哪
- **菜单高亮**：我在哪个版块

观察重点：

- 只切"入口"，面包屑**跟路由**时三样一起变；切成**跟对象**后，面包屑不动了，菜单高亮还在变——这就是后台里常见的"对不起来"。
- "跟对象"的代价：面包屑指的不是你来的那条路，点它回去会落到"订单管理"，不是工作台。所以面包屑不能当返回用。
- 打开"权限缺一层"：菜单里整支消失，面包屑却还画着那一级。点它，403。
- 打开"改版没同步"：菜单叫"交易中心"，面包屑还叫"订单管理"。两套名字指同一个东西。

## 一、三处回答，三个来源

| 谁 | 回答 | 来源 | 换了会怎样 |
|---|---|---|---|
| 面包屑 | 这个对象属于谁 | 对象的祖先链 | 用户不知道自己在哪条链上 |
| 返回 | 我上一步在哪 | 历史栈 | 回错了地方，草稿和滚动位置跟着乱 |
| 菜单高亮 | 我在哪个版块 | 当前路由 | 用户不知道自己在哪个功能区 |

三者可以同时成立、互不一致，因为它们的真相源本来就不同。把任何一个当成另外两个用，都会出问题：

- 拿面包屑当返回：从搜索结果进来，点面包屑会回到"订单管理"而不是搜索结果。
- 拿菜单高亮当面包屑：菜单只到功能（"全部订单"），不到对象（"0032"），永远差一级。
- 拿返回当面包屑：返回是历史，同一个对象从三个入口进来会有三条不同的"上一页"。

## 二、不一致通常是故意的，但有三种是缺陷

**故意的三种：**

1. **面包屑到对象，菜单只到功能。** 菜单是"订单管理 / 全部订单"，面包屑是"订单管理 / 订单 / 0032"。多出来的那一级菜单里本来就没有。
2. **对象有多个合法入口。** 从工作台、搜索结果、客户详情都能进同一条订单。面包屑画归属，返回画来路。
3. **菜单项是"视图"不是"节点"。** "全部订单"和"我的订单"是两个菜单项，但它们是同一个列表的两种过滤，面包屑合并成一个节点。

**缺陷的两种：**

4. **权限过滤漏层。** 你没权限看中间那个模块，面包屑却还画着它：点一下 403，或者那级根本点不动，成了死链。
5. **改版没同步。** 菜单改名、搬家，面包屑还是页面里写死的旧字符串。于是出现三套名字：导航叫订单、面包屑叫交易、权限里叫 order。

**灰色的一个：** 面包屑里出现分组名（"交易"那一层只是分组，不是页面）。它占一格却永远去不了；可能是故意的（表达分类），代价是这一格是死的。

三条能当场查的判据：

- 点面包屑的每一级：能不能落到一个真实、你有权限的页面？不能 → 缺陷。
- 那个页面的菜单高亮，和你来的地方一致吗？不一致 → 两棵树在打架。
- 面包屑里的每个词，菜单里能不能找到同名项？找不到 → 命名走散了。

## 三、跟路由，还是跟对象

同一个对象有多个入口时，面包屑只能选一条链。这是设计决定，不是 bug：

| | 跟路由 | 跟对象（规范归属） |
|---|---|---|
| 面包屑 | 随入口变 | 永远同一条 |
| 菜单高亮 | 随入口变 | 随入口变 |
| 两者关系 | 一致 | 必然不一致 |
| 用户感受 | "这单到底归谁？" | "我明明从工作台来的，怎么面包屑写订单管理？" |

跟路由的好处是三个地方永远对得上；坏处是同一个对象在不同入口下有不同的祖先，用户对它的归属认知不稳定。

跟对象的好处是归属稳定（这也是"这条订单属于订单管理"这个业务事实的唯一表达）；坏处是面包屑不能当返回用，而且系统必须为每个对象选定一个**规范父**——选错了，用户会觉得归属是错的。

我的判断：**对象型实体（订单、工单、客户）跟对象；纯功能页（报表、设置）跟路由。** 理由：对象有"事实上的归属"，功能页没有。这条是判断，不是规范。

## 四、可以短，不可以骗

面包屑太长时的三种折法，判据是同一条：**被藏起来的部分，用户知不知道它存在、能不能打开。**

| 折法 | 藏了什么 | 它的"可见声明" |
|---|---|---|
| 横向滑动 | 右端 | 露出半格，可滑 |
| 两行 | 没有藏，但变高 | 占地方，容易被忽略 |
| 省略号 | 中间几级 | 省略号本身，点开可展开 |

三种都能接受，只要藏这件事露在界面上。真正不能做的是**悄悄删掉中间级**：用户会以为看到的就是全貌，从而对结构做出错误判断。

主页和末级的去留，判据是"同一个问题只需要一个地方回答"：

- **主页**：根已经在 logo 上（点 logo 回首页），面包屑里那一级是重复的。窄屏上省掉它很划算。
- **末级**：它是"你在这"，不带导航价值。如果页面标题就在上方，它重复；如果标题被顶栏占了（换成搜索、分段），它就得留。

## 五、面包屑是结构的体检报告

它长，往往不是面包屑的病，是分类有病：重复层级、过度细分、把筛选当分类。看到四五级就想压缩时，先看树是不是本来就这么深。

它出现死链，说明权限和结构没有对齐——权限树和导航树本来是两套，一边改了另一边没跟上。

它的名字和菜单对不上，说明面包屑是手写死的，不是从数据生成的。

菜单的长度反映宽度分配，面包屑的长度直接暴露树的深度。所以它比菜单更有诊断价值。

## 六、数据源：面包屑来自对象，菜单高亮来自路由

三种做法：

1. **由前端路由/菜单配置生成**：最省事，但一遇到多入口或对象树就必然对不上。
2. **由页面参数生成**（接口返回祖先链，或至少 parent）：最准；代价是每个详情接口都要带父链，或者前端要按 id 再查一次。
3. **手写死在页面里**：最容易走散；改一次菜单要改几十个页面。

判据只有一条：**一个页面只有一个真相源。** 面包屑从对象来，菜单高亮从路由来，两者不要互相推导——一推导，改一处就要改三处。

## 为什么这样判断

- 三处分工是从"它们各自回答什么问题"推的：三个问题不可能由一个数据源同时答好。这不是观察，是定义。
- "跟对象 / 跟路由"的代价表，是把两种实现的必然结果列出来：一个改面包屑，一个改菜单，总有一个要变。
- 三种折法的判据来自演示和原文的对照：省略号和"悄悄删级"的区别不在长度，在有没有可见声明。
- "面包屑是体检报告"是推论：它直接映射树的结构，所以树的病会先在这里显形。
- 权限漏层和改版走散是 B 端最常见的两种不一致，不是从数据里统计出来的，是从"权限树和导航树是两套"这个结构推的。

## 适用条件和取舍

- 面包屑适合有明确层级、需要跨级跳转的产品；扁平结构（只有一层）不需要它。
- 对象型实体跟对象、功能页跟路由，这条在"对象只有一个父"时最干净；对象有多个真实父（客户也拥有订单）时，"规范父"必须由业务定，不能由页面定。
- 省略号适合层级深、中间层不常去的情况；中间层经常要跳的，省略号会把常用路径藏起来，反而更贵。
- 移动端优先"露半格"和"省略号"，两行最差：它不藏，但把页面顶部压得很高。
- 这篇只讨论桌面与移动端的面包屑；"标签式导航"（多标签工作区）没有展开。

## 例子

- **订单从三个入口进来**（演示）：面包屑始终是"订单管理 / 订单 / 0032"，返回三句话不同，菜单高亮跟着入口变。
- **电商产品页**：有的站点把主页和当前页都去掉，只留"分类 / 子类"，页面明显清爽，因为 logo 和标题已经在回答那两件事。
- **分类过细的电商**：面包屑出现"女装 / 上衣 / 针织 / 毛衫 / 套头"，中间还有重复层级。问题不在面包屑，在分类。
- **后台的权限场景**：面包屑画着"订单管理"，而这一支对当前账号不可见。这一级点下去 403，是最典型的死链。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 面包屑 = 祖先链 | 定义 | 写死 |
| 三处回答、三个来源 | 定义 | 写死 |
| 故意的三种不一致 / 缺陷的两种 | 定义（判据） | 写死 |
| 三条当场可查的判据 | 判据 | 写死 |
| 对象跟对象、功能页跟路由 | 默认 | 可偏离：多父对象要业务定 |
| 可以短、不可以骗 | 定义（判据） | 写死 |
| 主页和末级的去留 | 条件 | 写判据，不写死 |
| 面包屑来自对象、菜单来自路由 | 默认 | 可偏离：单层结构可以都来自路由 |

## 还没定

- 对象有多个真实父时，"规范父"怎么定（业务规则？用户最近一次进入？），没有讨论。
- 面包屑在移动端的三种折法只写了判据，没有做对照演示。
- 面包屑和"多标签工作区"（同时开十个页面）怎么共存，没有讨论。
- 结构化数据的祖先链由接口返回时，深链的接口要不要一次返回全部祖先，没有比较成本。
- 权限树与导航树如何对齐（是否一一对应），只有一句判断，没有方法。
