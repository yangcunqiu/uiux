# 操作受理与结果反馈

对会产生业务结果的操作，用户需要辨认能否发起、当前指向哪个目标、请求是否已被接受，以及业务是否已经完成。处理很快且结果就在原处时，一次明确的状态变化可以回答后两项。发送请求、服务端接受任务、业务最终成功是可能分开的事件，提示的确定程度应与已知事实相符。

## 处理中与重复执行

转圈或改变底色只改变外观。对一次创建、一次付款等只应生效一次的意图，需要验证连点、重新打开和重试后实际产生的业务结果。短请求期间让当前按钮显示“提交中”并拦住再次触发，可以减少同一页面的重复请求。按钮锁定不能处理响应丢失后的重试，也不等同于服务端去重。若允许重复添加多个独立项目，先定义每次操作表达的意图，再判断应拦什么。

原生禁用按钮会退出键盘 Tab 顺序。若要保留焦点，可以使用可说明当前不可用的方式，并在处理动作时实际阻止重复执行。切换为较长的“保存中”文案时可预留宽度，避免邻近目标移动。悬停与按下的表现另见[按下反馈与点击动效](../按下反馈与点击动效/README.md)。

## 结果应该出现在哪里

- 单个对象的结果已经确定，且用户无须核对详情，可以在原按钮或对象旁显示“已保存”。操作后列表已明确体现结果时，也可以用列表本身反馈。
- 用户要核对对象、数量、范围或时间时，在相关区域给出足够持久的结果说明。仅恢复按钮的原文案，成功和失败可能看起来完全相同。
- 服务端明确拒绝时，保留可纠正的输入，指出出错位置和下一步。网络超时只能说明尚未拿到结果。对可能已经生效的写入，先查明原操作或使用能安全重试的接口，再引导重试。
- 长任务允许用户离开时，先显示“已受理”及可回看的位置，完成和失败在任务记录或对应对象上更新。仅关闭等待窗口不会撤销已开始的业务操作。

验收可以使用安全的测试数据，分别让请求变慢、明确失败、在已生效后丢失响应。对比页面显示、服务端状态和重新进入后的结果。是否能减少使用者的重复尝试，则需要另行观察实际行为。
