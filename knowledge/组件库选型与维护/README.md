# 组件库选型与维护

组件以依赖包交付时，项目通过公开接口、主题配置和样式扩展使用它。默认表现符合需求、时间紧、界面差异并非产品重点时，这种方式节省实现成本。定制越依赖组件未保证的内部结构，升级后的维护风险越高。更换颜色和圆角与改变焦点、提交、撤销等行为，是两种不同深度的定制。

将组件源码纳入项目，可以直接调整结构和行为，适合视觉语言或交互能力确实需要自行控制的部分。项目相应承担合并上游变更、修复缺陷和检查兼容性的成本。两种方式可以在同一产品并存。例如内部工具采用成熟默认组件，对外的主要交互保留源码控制。选型要看具体改动能否通过公开接口稳妥实现。

## 哪些规则适合提前落实

对明确的共同行为，可选择能表达所需取值的组件接口、共享状态处理、自动校验或验收用例。例如多个页面都应避免同一次提交产生两个业务结果，把已约定的语义落实在接口和集成测试中，比让每个页面重复解释更可靠。从强到弱，可以通过类型或组件接口使错误值无法表达，通过测试发现不符合条件的结果，在设计前用文字说明要求，并由人或 AI 核对实现。它们覆盖的风险和维护成本不同。对齐、层级和风格等问题中，只有前提与失败后果清楚的部分适合转成自动约束。即使某种样式值来自统一配置，也仍需检查它是否用在合适的位置。

相同缺陷反复出现时，值得比较一次实现共享约束与逐次人工检查的成本。低频问题可在相关流程中验证，后果严重的单个失败也值得提前防止。具体检查放在能观察真实结果的层级。组件能阻止单个按钮的连续触发，服务端才能保证跨页面重试后最终写入几份。对可读性、输入行为和真实感受，分别采用实际界面检查或适当的用户观察。
