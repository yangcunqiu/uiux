# 拆组件：问题、判据与取舍

这不是组件规范，是一组用来拆组件的问题、判断和取舍。每一条都写了收益、成本或代价，以及它在什么条件下失效。

前面的六节是抽象出来的判断；第七节是例子，不是结论本身。

## 一、四个问题

拆一个组件时，先问四件事：

1. 它替用户回答哪个问题？
2. 值从哪来，由哪一处决定，错了改哪？
3. 用户能不能在界面上证实它？错了能不能退回来？
4. 它出现、消失、切换之后，用户的位置和视线回到哪？

每个问题对应一类具体的错：

| 问题 | 它对应的错 |
|---|---|
| 1. 它替用户回答哪个问题？ | 一个控件同时表示多种语义，用户不知道它在筛什么、选什么 |
| 2. 值从哪来，由哪一处决定，错了改哪？ | 来源或生命周期不同的值放在同一个字段，出错时不知道改哪里 |
| 3. 用户能不能在界面上证实它？错了能不能退回来？ | 用户无法核对结果，或者无法撤回错误 |
| 4. 它出现、消失、切换之后，用户的位置和视线回到哪？ | 焦点、位置或上下文在切换后丢失 |

这四个问题不产生唯一答案，也不解决冲突（稳定还是反馈、密度还是可读）。它们只保证你看见会出事的点。问题 3 包含两件事：能不能核对、能不能撤回；问题 4 也包含两件事：进来时从哪来、出去后回到哪。

## 二、两条判据

### 判据 1：一个字段只装同一类值

一个字段里的值，来源要相同、生命周期要相近、变化方式要一致。身份（“我”）不写进状态名，它是另一个字段。

- 收益：值之间可以比较、筛选、解释；出错时知道该改哪里。
- 成本：可能要把一个字段拆成两个，或者把一个值挪进视图，界面会变复杂。
- 失效条件：两个值确实同来源、同生命周期、同变化方式时，拆开是过度设计。

### 判据 2：打断的收益要大于成本

打断的成本是一次点击、一次注意力切换、流程变慢。它能换来的收益有五类：防误触、让用户知道后果、核对对象、留痕、让重要动作慢下来。

如果收益只有“防误触”，用撤销或重做通常成本更低。通用确认框只能防误触，防不了理解错误——用户以为自己对，就会直接点“确定”。

判断三个变量：能不能恢复、错了多久会发现、多久发生一次。

- 撤销只对“立刻会发现”的错误有效。
- 高频操作上的确认会变成习惯性点击，防不住什么。
- 不能恢复、又会影响他人的动作，可能需要比确认更高的成本，比如输入名称或审批。
- 失效条件：高频、能立刻发现、后果低的错误，确认的收益通常低于成本。
- 代价：可恢复性需要软删除、撤销窗口，以及窗口内的一致性。

## 三、一个区分：页面动作与状态补救

动作至少分两类：

- **页面动作**：新建、导入、导出、刷新。在同一个上下文里，它们的入口应当稳定、可预期；能不能用由权限和上下文决定，不由“列表有没有数据”决定。布局变化时（比如窄屏收进“更多”），位置可以变，但要仍然找得到。
- **状态补救**：重试、清除筛选、导入示例数据。它们只在对应状态出现，不需要在别处常驻。

两种失败：

- 把页面动作做成状态补救：只在空状态里有“新建”，有数据时找不到；或者在空状态复制一个和工具栏一样的“新建”，同一屏出现两个同级入口。
- 把状态补救当成页面动作：工具栏一直放“重试”，大部分时间不可用。

- 收益：同一动作只有一个入口，用户不用猜两个按钮的区别；页面动作在有没有数据时都能找到。
- 成本：状态补救需要额外实现；布局变化时要保证入口仍然可预期。
- 失效条件与例外：
  - 权限、角色、上下文可以决定页面动作是否显示。所以“所有新建动作都在同一位置”这个说法不成立；能说的是“在同一个上下文、同一套权限下，入口稳定”。
  - 空状态里的动作如果是**不同**的下一步（导入、模板、示例），它不是复制，是另一条路。
  - 如果页面动作在当前布局里不可见（抽屉、弹窗、窄屏折叠），本地入口可能是唯一路径，可以放。
  - 有些补救同时也是页面动作（比如申请权限），可以两处都有，但标签和范围要一致。
  - 行内动作跟着行出现（比如某一行的“新建版本”），不属于页面动作；它的位置由行的上下文决定。

## 四、层级与过渡

1. **层数由内容决定。** 一个字段的取值（日期、状态）留在当前界面；一件有独立导航、选择、提交边界的任务（选对象、编辑内容）值得单独一层。
2. **每多一层，通用控件（取消、确定、返回）的作用对象就多一个候选。** 用户要靠记忆判断这个按钮作用于哪一层。缓解只有两种：减少层数，或让按钮带上对象（“选好了/取消选择”）。
3. **过渡要让用户看得出“之前的内容还在”。** 第二层覆盖在第一层上、同一界面里的横移、把页面留在后面（缩小、变暗）都能提供这种信息；透明度交叉提供不了。方向只是其中一种方式。
4. **结构、视觉、运动、行为四种表达要一致。** 两个抽屉的做法一致，但用户要记两套退出按钮；透明度看起来轻，但和结构不一致；同一个抽屉里的横移一致，用户只需记一套。
5. **模态性由行为决定，不由形状决定。** 模态：后面的内容暂时不能用（遮罩、焦点锁在层内、背景不可点不可滚）；非模态：后面的内容继续可用。同一个抽屉可以两种都做：目录抽屉通常非模态，筛选抽屉通常模态。取舍：模态保护注意力、避免和后面冲突；非模态保留上下文、可对照，但容易和后面操作打架、焦点乱、背后状态变了面板可能过期。需要先做决定、交易、不可逆操作时用模态；参考、预览、辅助时用非模态。

同一个“取消”，在单层里清楚，在多层里模糊。这种清楚来自层数，不一定来自动效。

## 五、可中断性、惯性与阻尼

拖拽类交互常被混成一件事。至少拆成四个机制：

1. **可中断性**（必须）：松手后的运动，随时能被新的输入接管。
2. **惯性**（可选）：松手速度是否继续影响目标和运动。
3. **越界阻力**（可选）：拖过边界时有没有阻力。
4. **回弹**（可选）：松手后是否回到范围内、是否过冲。

可中断性不是缓动参数，是状态机：静止 → 拖拽 → 回弹。回弹中按下，要停在当前值并转成拖拽，不是等它走完，也不是跳回起点。

通常说的橡皮筋是第 3 和第 4 项的组合。**回弹不是越界阻力的必然结果**：两者可以分别选。演示里的“越界阻尼”只控制第 3 项，回弹一直在，所以两个模式都有回弹。

### 惯性

**收益**
- 手势延续：松手的力被兑现，松手后的动作和拖拽阶段一致。
- 效率：一甩可达远目标，减少拖拽距离。
- 表达：速度成为一个输入维度（轻推和重甩不同）。
- 符合触摸平台的习惯。

**成本**
- 落点不确定，快速释放会过冲。
- 误触发：关闭、翻页、提交。
- 精确停靠变难。
- 实现要处理速度采样、投影、可中断、旧速度、指针取消。
- 部分用户对运动敏感。

**适用**
- 有连续位移的拖拽对象。
- 目标是粗粒度（吸附点、页、档位）。
- 错误可恢复。
- 触摸或直接操纵为主。
- 高频使用。

**不适用**
- 目标是连续精确值（滑块、裁剪、数值）。
- 后果不可逆。
- 非拖拽（点击、步进、切换）。
- 位移很短。
- 用户要求减少动态效果，且没有非运动替代。

**改选信号**
- 过冲和误触发变多。
- 精确调节需求上升。
- 输入从触摸转为鼠标或键盘。
- 后果从可恢复变成不可逆。
- 对象从“甩”变成“定位”。

### 阻尼（越界阻力 + 回弹）

**收益**
- 边界可感知：到头了，但输入仍被接收。
- 吸收小的越界，手势不硬断。
- 承载信号：刷新、露出、阈值、松开触发。
- 和弹性材料的运动一致。
- 暴露边界存在。

**成本**
- 边界位置变模糊。
- 越界可能露出或裁切内容。
- 多一套越界和回弹状态。
- 越界像“还有更多”的假信号。
- 部分用户运动敏感。

**适用**
- 边界常被撞到。
- 边界本身承载信号或动作。
- 越界可恢复，回弹快。
- 弹性材料（面板、列表、轮播）。
- 触摸或直接操纵为主。

**不适用**
- 边界是硬约束（数值、配额、法律限制）。
- 边界外没有内容或动作。
- 需要精确找到边界。
- 很少撞边界。
- 鼠标或键盘为主。
- 用户要求减少动态效果。

**改选信号**
- 用户反复越过边界找内容，却找不到。
- 边界必须精确。
- 越界成本变高。
- 边界被撞的频率下降。
- 平台习惯是硬停。

### 只选一个时

- 惯性每次松手都发生，阻尼只在撞边界时发生。高频拖拽、目标粗、错误可恢复时，惯性的收益和成本之比更高。
- 优先级由条件决定：
  - 粗目标 + 可恢复 + 触摸 → 惯性优先。
  - 边界承载信号或常被撞 → 阻尼优先。
  - 边界只是“内容到头” → 硬停 + 惯性足够。
  - 目标精确或不可逆 → 两个都不要，先保证可中断性和非拖拽路径。

### 两个都不选

- 非拖拽交互（点击、步进、切换）。
- 精确、不可逆、代价高的操作。
- 位移很短，惯性和阻尼没有发挥空间。
- 键盘或读屏为主；拖拽本身需要替代路径。
- 用户要求减少动态效果，且没有非运动替代。

即使惯性和阻尼都关，可中断性仍然必须：松手后的运动要能在当前值被新的输入接管。

### 一致性

三种自洽的组合：

- **惯性 + 硬边**：有质量，边缘刚性。
- **惯性 + 阻尼**：有质量，边缘弹性。
- **无惯性 + 硬边**：工具型直接操纵，没有“甩”的语义。

运动表达要和结构、视觉、行为说同一件事。把回弹当成阻尼，或者把“没惯性”当成“更可预测”，都会让某一层和另外三层对不上。

演示里的阻尼系数、投影时间、弹簧参数是演示选择，不是推荐值；换对象、换输入方式要重调。

## 六、禁用与说明文字

### 禁用不是一种状态，是三种原因

没权限、条件不满足、正在处理。一种灰色表达不了三种；用户不知道为什么，也不知道该等、该改、还是该申请。禁用还会拿走可聚焦性和解释。

顺序：

1. **先别禁用**：条件不满足 → 保持可用，点击或提交时解释；处理中 → loading；没权限 → 隐藏，或换成“申请权限”。
2. **让原因成为状态的一部分**：必填标记、已选 0 项、缺哪一步、权限状态。用户看界面就知道，不需要注释。
3. **实在要禁用**：原因要放在一个不禁用的载体上（区块状态、步骤、权限说明），在用户需要它的时刻出现；不要指望禁用控件自己的悬停、聚焦、点击——它可能收不到这些事件。而且这是最后手段。
4. 目标不是“解释这个禁用按钮”，是消除解释它的需要。

### 说明文字：解释控件是设计债，解释规则是内容

自解释不等于没有文字。按钮文案、字段标签、选项名本身就是文字。问题出在**控件之外的注释**：它替控件解释，而不是成为控件的一部分。

- **解释控件本身**（这个按钮是什么、在哪、为什么不能点）：设计债；应该改标签、位置、状态、流程。
- **解释系统规则、后果、当前状态**（密码至少 12 位、文件最大 10MB、删除后 7 天可恢复、当前筛选是“待人工处理”）：是内容，不是对控件的注释。

测试：删掉这句话，用户会做错什么？

- 错在“不知道控件是什么、在哪、为什么不能点” → 改界面，不要加字。
- 错在“不知道规则或后果” → 文字是内容，但要放在需要它的时刻（输入时、提交时、确认框里），不要常驻在每个控件旁边。

目标：让界面自己说明；文字只承载界面无法显示的信息。

## 八、适用条件与边界

- 这些是条件判断，不是规则。每一条都写了失效条件；不写失效条件的条目，还没被认真用过。
- 不产出组件清单、状态枚举、尺寸和取值规范，也不是一套能让人排列组合出设计的通用结构。
- 判据 1 的前提是“值确实属于不同维度”；如果两个值共享来源和生命周期，拆开是过度设计。
- 判据 2 的“打断”不只指弹窗；按住、输入名称、二次确认、延后执行都是打断，成本不同。
- “页面动作 / 状态补救”的前提是“这个动作在当前上下文成立”。权限、布局、上下文变化时，位置和可用性都可以变；它不是一条“所有新建动作位置固定”的约束。
- 空状态的权限例外：如果安全要求不能暴露资源是否存在，统一“暂无数据”是对的，也不能提供“申请权限”。
- 无障碍：成本低的部分（焦点可见、可点区域、语义控件、错误就近、不只用颜色）默认要做，不列为取舍；成本高的部分属于产品投入决定，不在这篇的判断范围里。
- 惯性、阻尼、回弹是材料选择，不是默认值；具体参数要按对象和输入方式调，不能从演示里抄。
- 禁用和说明文字：禁用是最后手段；小字只承载界面无法显示的规则、后果或状态，不承载控件解释。

## 九、还没定的

这一节只放框架层面还没解决的问题，不放某个产品里的具体取舍。

- “可挽回”要不要独立成第五个问题，还是留在判据 2 里。
- “值/事”的边界还没有阈值：一块内容什么时候值得单独一层，目前只能按“有没有自己的草稿和提交边界”判断。
- 状态的来源（设备、业务、任务）与状态叠加的优先级，还没有展开。
- 过渡中保留一个不动的参照物，还没有展开。
- 移动端和堆叠：内容高度变化、抽屉上再开抽屉、底部面板和页面的关系；这一块还没有讨论。
