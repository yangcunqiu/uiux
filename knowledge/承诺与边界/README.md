# 承诺与边界

单选、复选、开关，常被当成三种外观。它们是三种说法，各自宣布不同的事。这一簇真正的主线比「形状」更宽：

**一个控件只宣布一件承诺。当它宣布的和系统实际解释的不一致、而这个不一致在界面上又看不出来时，用户会按宣布行动，系统按解释记账。**

## 先看演示

两个演示，双击即可，不需要本地服务。

### 一、形状与承诺

[打开](形状与承诺.html)

同一个设置——深色模式——四种做法：单选 / 开关 × 立即生效 / 需保存。每张卡片底部有一行灰色读数，是演示用的。顶部可以把效果挪到「另一个页面」，那时预览和读数一起消失。

观察重点：

1. A、C 里控制区和预览永远同步；B、D 里有一个时间差。
2. B、D 的时间差本身不稀奇——B 的保存按钮在明说「还没提交」。
3. D 里开关停在「开」，系统是关的。看得见预览时，你会说「这功能很怪」；把效果挪到另一个页面，就只剩开关一个说法。
4. 点「离开这个页面」：A、C 回来和离开前一样；B、D 回来时改动丢了。
5. A、C 用「撤销」换掉了「保存」：少一步确认，欠一个反悔窗口。

### 二、半选与级联

[打开](半选与级联.html)

同一棵树，三种父节点模型：只是分组 / 自己有值 / 继承。右边读数分成「提交的数据（显式授权）」和「有效权限（含继承）」。

观察重点：

1. 「只是分组」：父框是纯动作，三态只表示「全选 / 部分 / 没有」，提交叶子集合。
2. 「自己有值」：点父框连它自己也一起改。再单独取消一个子项——父框变半选，它自己的那个值被藏起来了。
3. 「自己有值 +『全选』动作」：字段和动作分开，两边互不冒充。
4. 「继承」：父框勾上，子项变灰、标「继承」，不能单独改；取消父框，子项回到各自的授权。
5. 同一张半选画面，可能对应两份数据。

## 主判断：宣布、解释、能不能看出来

拆一个控件，问三件事：

1. 它对用户**宣布**了什么？——用户从这个控件的样子读出的承诺。
2. 系统实际按什么**解释**？——数据和行为上真正按什么记账。
3. 两者不同时，用户能不能在界面上**看出来**？

第三问决定后果：

- **看得出来**：用户会说「这功能怪 / 坏了」。缺陷是可见的，至少能被发现。
- **看不出来**：用户按宣布行动，系统按解释记账。这才是「骗」的结构。

四个例子：

| 场景 | 宣布 | 解释 | 看得出来吗 |
|---|---|---|---|
| 开关 + 保存 | 位置就是当前状态 | 等提交才生效 | 通常看不出，靠旁证 |
| 圆点做多选 | 一组里只有一个 | 多值集合 | 看得出（两个点同时实心）→ 只是「怪」 |
| 父框兼有自身值 | 我管下面 | 还藏着一个父自身的值 | 看不出 |
| 全选 | 选眼前这些 | 整个范围，含未来的子项 | 看不出，树变了才知道 |

「看得出来吗」不是控件的固定属性，要按动作现场问：同一个开关，旁边有预览就看得出，效果在另一页就看不出。同屏有旁证时，最坏是「怪」；证据不在场，才会变成「我以为已经开了」。

三种改法，按代价排：

1. **让解释服从宣布**（改行为）：开关改成立即生效，配撤销。
2. **让宣布说清解释**（改文案、读数、标签）：全选改成「选择整个分组」，或者把范围写在横幅里。
3. **拆成两个槽位**（各自宣布）：父框拆成本身 + 全选。

如果两个承诺都必须存在，又都不能宣布，那就别用这个控件。这不是妥协，是它在撒谎。

## 三种说法

- **单选**：这些里面，我挑了哪个。
- **复选**：这个集合里，包含哪些；只有一个选项时是另一句——我确认这件事。
- **开关**：它现在是这样。

前两句的主语是「我」，第三句的主语是「它」。单选旁边永远摆着别的选项，圆点在说「我的选择」；开关不摆选项，它的位置就是它的全部内容。

由此得到这一簇最紧的一句话：**在同一段「还没生效」的时间里，单选说的是真话，开关说的是假话。** 单选声称「我选了它」，这是真的；开关声称「它开着」，这是假的。

### 承诺能被覆盖多少

单选承诺「我记下了你的选择」，什么时候算数由上下文给：设置页里可以点了就生效，表单里可以等提交，两种都成立。

开关承诺「位置就是当前状态」，上下文不能覆盖。一旦它停在「开」而系统是「关」，它不是慢半拍，是在报一个假的状态。

所以不是「开关不能进表单」，而是：**开关只能承担当前值。** 它只有一个位置，没有第二个位置放「待提交」。要批量提交，就让别的东西承担——保存条、未保存计数、明确的提交区。

一个可见的例外：成组的开关加底部保存，在管理后台并不罕见。它成立的条件是成组，加上明确的未保存提示；只有一个字段也要按一次保存，就只剩仪式感。

## 五项拆解

任何控件都能这么拆，选择类控件只是第一个完整用它的家族。这一套可以看成[拆组件](../拆组件/README.md)四问在选择类控件上的具体化，补的是符号、角色、行为这一层。

| 项 | 问什么 | 单选 |
|---|---|---|
| 值模型 | 能表示哪些值，值之间什么关系 | 组内恰一个 |
| 外观 | 什么符号预告这个模型 | 环 + 实心点 |
| 行为 | 操作怎么改值，键盘怎么走 | 点选替换；方向键组内移动 |
| 角色 | 对辅助技术和表单提交声明的类型 | radio / radiogroup，单值 |
| 承诺 | 它什么时候算数 | 记下选择；时机由上下文给 |

五项的稳定性不一样，写下来时不能混成一张表：

| 项 | 稳定性 | 写法 |
|---|---|---|
| 值模型 | 跨平台不变 | 定义，写死 |
| 操作语法 | 跨平台基本不变 | 默认；键盘细节随平台 |
| 承诺核心 | 不变 | 定义 |
| 承诺时机 | 场景变 | 参数，每次看上下文 |
| 外观 | 平台变 | 标注来源，别混用 |
| 数量、布局、默认值 | 场景变 | 检查项 + 偏离信号 |

所以每次不必重问五项：三项是默认（值模型、语法、承诺核心），两项每次要看（承诺时机、值域会不会长），一项按平台适配（外观）。三个已知，两个变量。

## 三张卡

### 单选

- **定义**：一组里恰有一个。角色 radio / radiogroup，单值。
- **默认**：选新的，旧的自动取消；Tab 进组一次，方向键在组内走。
- **外观**：环 + 实心点（Web、Android）。iOS 常用勾选列表，那是另一套约定，别混着用。
- **承诺**：记下你选的那个，不等于已经生效。
- **每次要看**：什么时候算数（立即 / 随表单）；值域会不会长出第三档；选项数量和要不要互相比；给不给默认值。
- **停下重想**：要「同时选中多个」→ 复选；要「跟随系统」→ 列表或分段；组里只有一个成员 → 组不存在，用勾；用户要回到「未选」→ 单选回不去。
- **不成立时**：需要「未选」是一个有名字、可返回的状态。

### 复选

- **定义**：一个集合里包含哪些成员，组内各项独立。角色 checkbox，多值；单用时是布尔。
- **默认**：点一项切换一项；整组共用一个标签。
- **外观**：方框 + 勾（Web、Android）；iOS 也用勾，常在行末。
- **承诺**：记下你勾了哪些，不等于已经生效。
- **每次要看**：有没有组级动作（全选、半选）；半选是算出来的还是存下来的；有没有「至少选一个」的要求；单个复选是不是在问「确认」。
- **停下重想**：选项互斥 → 单选；组里只有一个成员 → 它是确认，不是集合；父框会清空用户已有的选择 → 加撤销，或改成显式按钮。
- **不成立时**：半选只表达状态，表达不了「部分选中过」的意图。

半选是子项算出来的，不存字段。父框的点击语义是约定（原生是 mixed → 全选），任选一种都要写清楚。

### 开关

- **定义**：一个二元状态，位置就是当前值。角色 switch，布尔。
- **默认**：点一下翻转，立即生效，不需要确认。
- **外观**：轨道 + 手柄；标签在外，写功能名（深色模式），不写状态（开 / 关）。
- **承诺**：位置就是它现在的样子。没有「待提交」的中间态。
- **每次要看**：是不是真的立即生效；关闭态是不是不言自明；两个状态是不是「常态 / 被打开的模式」。
- **停下重想**：要随表单提交 → 别用它，或者让保存条承担待提交；关掉是什么说不清 → 单选；两个值是对等的两套主题 → 单选；要表达「跟随」「自动」→ 列表或分段。
- **不成立时**：需要「未选 / 未设置」作为合法状态。

## 半选与级联

### 半选是汇总，不是值

它由子项算出来，不能被单独设置，也不该进提交数据。取消一个子项，父框半选；取消全部，半选消失。

### 父框是槽位

树里父行那个勾选框，不是随便一个位置，是一个槽位：它的形状在说「我管下面」。

| 模型 | 父框是什么 | 点它做什么 | 数据里有什么 | 取消父框时 |
|---|---|---|---|---|
| A 只是分组 | 动作，没有值 | 子树全选 / 全清 | 叶子集合 | 子项全清 |
| B 独立字段 | 自己的值 | 只改自己 | 每个节点一个布尔 | 子项不变 |
| C 继承 | 自己的值（显式授权） | 改自己，子孙有效值跟着变 | 显式授权集 | 子项回到各自授权 |
| D 叠加 | 字段 + 批量动作 | 写整棵子树 | 物化的树 | 子项全清，原授权丢失 |

A 兑现槽位的承诺；C 靠让子项显示「继承」来兑现；B 落空；D 两个都只兑现一半。

演示里能直接对比 A、C、D，以及 D 的修法（自己有值 +「全选」动作）。纯 B 没有单独放——它没有全选动作，实际很难用；表里留着它，是为了说明「字段占了槽位、却不兑现承诺」这一格。

B 和 D 的别扭不在语义，在摆放：它们把「字段」放进了「批量动作」的槽位。要保留字段又要干净，只能把它挪出去：

- 动作上移组头；
- 字段下移成「本级」一行——每样可授权的东西都是叶子，父节点只是容器，数据回到平铺集合；
- 动作收进悬停或菜单（代价是可发现性）。

### 点半选：全选还是全不选

两种都会把「原来的分布」抹平，差别在抹平之后剩下什么：

- 全选：原来的选中项都还在，只是分不出哪些是原来就选着的。少的是历史。
- 全不选：原来的选中项没了。少的是结果。

历史可以靠撤销补，结果只能靠回忆重建。所以原生选「全选」，破坏性的那一步被放在第二次点击上。

### 全选的范围

没有标准，是业务约定。但它决定三件事：新增子项要不要自动包含、是不是最小权限、「已选 N 项」会不会自己变。

默认按「当前这批」实现；要「范围」，换名字和控件，不要复用「全选」。判断依据：集合会不会增长、是不是最小权限、用户能不能在提交前看见范围。

两个边角：**禁用项**——「全」是「全部可选」，不是「全部」；**未加载的树**——未知不是未选，要么先加载，要么显式问。

要范围就学 Gmail：横幅写「已选择本页 50 项，选择全部 2,341 项」。

## 形状是预告，不是定义

形状不决定语义，它预告语义。预告错了，用户要用一次点击去纠正；代价不是「看不懂」，是「每次都要试一下」。

圆点说的是「只能选一个」吗？不是圆说的，是三件事合流：

- **图形**：环 + 实心点。它来自老式车载收音机的机械预置键——按下一个，其余弹起，[radio button](https://en.wikipedia.org/wiki/Radio_button) 这个名字就从这来。它的隐喻是「被按下去的那一个」，天然唯一。
- **构图**：同样的图形排成一列，共用一个组标签。
- **行为**：选新的，旧的取消。这是最终的定义者，图形只是预告。

圆、环点、环勾是三套隐喻，不是同一个形状：

| 符号 | 隐喻 | 排斥别处也有吗 |
|---|---|---|
| 空心圆 | 一个待占的位置 | 不表态 |
| 环 + 实心点 | 这一格被按住了 | 排斥 |
| 环 + 勾 | 这一项被做了记号 | 不排斥 |

容器不携带语义，记号携带。iOS 外观选择那个例子用的是勾，所以它没有说「只能一个」，只是恰好用在一个只能一个的场景里。

## 控件、组件、角色

三个词不在一个层面上，混用会让判断变形。

| 层 | 词 | 单位 |
|---|---|---|
| 用户侧 | 控件 | 一个可操作单元 |
| 实现侧 | 组件 | 一套可复用代码或资产 |
| 机器侧 | 角色 | radio / checkbox / switch |

用法：谈用户怎么理解、怎么操作、什么约定 → 控件；谈怎么造、怎么复用、怎么进设计系统 → 组件；谈对辅助技术和表单声明的类型 → 角色。

单选框作为交互对象是控件，作为设计系统里的条目是组件。两个说法都对，回答的是不同问题。

## 几条被收窄的说法

**「绝对不行，用户会认知混乱」。** 这个理由太软，也太难反驳。用圆点做多选，真正的错是三样东西最多对齐两样：值模型是多值，角色要是多选，外观却在说互斥。它和「用户会不会困惑」无关——即使所有用户都看懂，这个符号在系统里也已经一义两用。

「认知混乱」这个词下面至少混了四件事：数据模型装不下（不是认知问题）、画面自相矛盾、点击预期落空、习惯违背。前两条当场可判，第三条能描述出具体动作，第四条才需要测量。用一个没测量过的第四条去支撑「绝对不行」，重量不匹配。

**「总是给默认值」。** 预选赚一次点击，代价是删掉「没选」这个状态：用户分不出是他选的还是系统替他选的。无后果的偏好可以预选；有后果的留空加校验；同意类不能预填（[Planet49 案 C-673/17](https://merlin.obs.coe.int/article/8699)）。

**「≤3 用单选、>5 用下拉、>7 换标签、5±2」。** 三套阈值互相打架；5±2 还是对 Miller 那篇的误用——他讲的是分辨和记住多少个不同刺激，不是屏幕上能同时摆几个选项。判断换成三问：能否一眼看全、要不要互相比较、多一次点击值不值。

## 硬约束

- **整行可点**；目标至少 24×24 CSS px（[WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)，AA），增强级 44×44（2.5.5，AAA）。
- **选项竖排优先**：标签与控件的对应关系明确，支持长标签和本地化。短而等长的少数选项才考虑横排——阈值还没定。
- **语义与角色一致**：radio 的互斥、组内方向键、Tab 只进组一次，是浏览器按语义给的。把单选改成多选，错在可验证的语义，不在「用户会困惑」。

## 为什么这样判断

- 主判断来自四次对照：开关 + 保存、两个点同时实心、父框的隐藏值、全选范围。前两个的差异看得见，所以只是「怪」；后两个看不见，所以会变成错误信念。
- 「证据距离」来自一次讨论：看得见预览时，点开关不生效只会被评价为「怪」，不会被评价为「被骗」。
- 圆点的机械来源是词源事实；「记号携带语义、容器不携带」是推论。
- 读屏是放大器，不是核心理由：即使用户不用读屏，预告与行为不一致仍然存在。
- 数字阈值和「总是给默认值」是经验建议，不是标准；WCAG 的尺寸是标准，界面约定不是。

## 适用条件和取舍

- 适用于单个选择控件和简单树；复合组件（日期选择器、表格批量选择）要拆到子控件再看。
- 不产出控件清单，不给没讨论过的控件补格子。每张卡的行都该来自一次真实讨论和一次真实失败。
- 「父框是槽位」依赖「同一列是同一类东西」这个视觉前提；字段挪到另一列，B 不一定别扭。
- 「本级」方案要求后台接受平铺的授权项集合，而不是一棵带继承的树。
- 范围约定要写进标签或读数；只写在后台的约定，用户会按自己的理解用。
- 「场景变」的那几行会随产品变，不能当答案抄；「停下重想」才是卡片最该被读的部分。
- 三个控件的默认值可以直接用；偏离要有理由。反复出现且有效的偏离，才升级成新的默认；只出现一次，留在项目里。

## 还没定

- 选择的其他形状——分段控件、下拉、标签——和 C 簇的边界：同一个值模型，不同的空间处理，该在哪一簇讲透。
- 横排在什么条件下成立。目前只有「短而等长」，没有阈值。
- 禁用节点和未加载子树的具体交互：禁止全选、先加载，还是显式确认。
- 「本级」作为一行的命名，以及它在多层树里的表现。
- 「未选」作为合法状态时，怎么在界面上表达：占位、提示，还是提交时校验。
