# 行与列

表格同时卖两件事：**列同质**（同一列是同一字段、同一单位、同一量纲，才能上下比较）和**行并置**（一个对象的多个字段在同一视野里，才能横向对照）。破一个，表格就开始骗人。

表格、列表、卡片不是三个类别，是同一条尺子的刻度。分界只有一句：**字段要不要被提到全局。**

## 先看演示

[三种排法](三种排法.html)（双击打开，不需要本地服务）

同一批 8 个订单，切表格 / 列表 / 卡片；再切「标出」，把同一个字段框出来，看它在屏幕上留下什么形状。

观察重点：

1. 表格标**金额**：八个框连成一条竖线（1000px 下左边缘都在 488、右边缘都在 598），扫一列就比完；左边那一列同时告诉你是谁。
2. 列表标**金额**：金额在右端对齐——这是列表唯一保住的那一列。
3. 列表标**状态**：框跟着商品名长短走，左边缘散在 177–247 之间（差 70px）。想数「有几个待付款」只能一行一行看。
4. 卡片标**金额**：每块各一个，块内还压着标题和标签；比一轮要在块之间跳。
5. 切回表格看第一列：客户名在每行同一位置（左边缘都在 129），所以「最大金额是谁」不用换屏就能回答。
6. 三块的唯一变量是排法，数据一条没变。差别的来源是字段有没有被提到全局，不是数据。
7. 把窗口拉窄：表格只能横向滚动（它不能折行，这是列的结构决定的），列表和卡片会跟着变窄。

## 一、表格的承诺

**列同质**：同一列同字段、同单位、同量纲，才能排序、找极值、看分布、按值筛。
**行并置**：一个对象的多个字段在同一视野里，才能横向对照、一次看完；也是「最大金额是谁」不用换屏就能回答的原因。

两个条件破一个，症状不一样，改法也不一样：

| 症状 | 破的 | 先做什么 |
|---|---|---|
| 列太多，要横向滚动 | 行并置 | 把行身份、行操作钉住；否则换控件 |
| 同一列单位或格式混用 | 列同质 | 先统一，再谈对齐 |
| 每行内容差异大、要读全文 | 列同质 | 换成列表或卡片 |
| 树形缩进很深 | 列同质 | 缩进吃列宽，层级深就该换控件 |
| 单元格塞标签、图标、进度条 | 列同质（部分） | 承认它是「展示」列，别再指望它可排序 |
| 行高不一致（换行、多行文本） | 行并置 | 横向扫视会串行；行高与分隔在后面单独讨论 |

这是模型，不是标准：每一行只说明「破的是哪一边」，具体怎么补在后续条目里单独讨论。

## 二、一条尺子：字段在不在全局

- **表格**：有一份**列定义**——列宽、对齐、类型、排序器、筛选方式。数据结构是「对象数组 × 字段 schema」。字段是第一公民。
- **列表**：字段留在**每行的模板**里。数据结构只是「对象数组 + 一个行模板」。对象是第一公民。
- **卡片**：连行都拆了，每个对象一块；块内自由排布，块与块之间没有对齐承诺。

这一条差别会滚出其他所有差别：

| | 表格 | 列表 | 卡片 |
|---|---|---|---|
| 行内能放什么 | 一格一个值 | 头像、两行文本、标签、进度都可以 | 块内随便排 |
| 能比几个字段 | 任意列 | 只有左右两条边 | 块与块之间不比 |
| 能按几个键排序/筛选 | 任意列 | 一个（最多再加一个） | 一个 |
| 加一个字段的成本 | 改 schema 一处 | 改行模板，可能把行撑高 | 改块模板 |
| 用户的主要动作 | 比较、排序、筛选、批量 | 认出、读一条、点进去 | 挑选、浏览 |

**列表其实是一个只能有两列宽的表格。** 它保得住左边界（身份）和右边界（数值、操作），中间的东西是流式的：位置由前面文字的长度决定。演示里列表的金额还在右端排着，换成状态就散了。

反过来说：如果你在列表里不断给字段加固定宽度、右对齐、调间距，那它已经在长成表格了，不如直接换。

## 三、判据：三个问题

按顺序问：

1. 用户要**在同一个字段上跨行比较**吗——找最大、看分布、数「有几个待付款」、按金额排序？
   要，这个字段就必须提到全局，用表格。
2. 用户主要是**认出一条、读一条、点进去**吗？
   是，字段留在行内，用列表。
3. 一条内容的**形状**差得远吗——头像、多行描述、缩略图、进度条？
   差得远，表格会被撑坏（列同质破了），用列表或卡片。

第一条是主导项：既要比较又要进入时，先满足比较——表格里点「详情」也能进入，反过来不行。

两个都不对时：对象性极强、不需要跨行比 → 卡片；只有一条 → 描述列表；比的是趋势或占比，不是逐字段 → 图表。

## 四、混合是常态

- **表格第一列放头像 + 名称 + 副文本**（列表化的表格）：让「这是谁」更好认，代价是这一列不再是同质的值——排序和筛选要另外说明按哪个值。
- **列表右端放一个右对齐金额**：最小的一列，只能有一条。
- 所以问「这是表格还是列表」没有意义，该问的是**哪些字段值得变成全局约定**。

## 为什么这样判断

- 列是一条共享的 x 位置和一份宽度预算，这是结构事实；「能顺着扫」不是风格偏好。
- 列表只能保住两条边，因为行内是流式排版：中间字段的位置由前面文字的长度决定。演示里量到的是状态标签的左边缘（177–247，差 70px）。
- 表格里 8 个金额的左边缘都在 488、右边缘都在 598，是量出来的，不是评价。
- 字段契约决定可自动化的操作集合：没有 schema，排序、筛选、列宽持久化、列自定义、导出都得逐条手写。这是工程事实，不是设计偏好。
- 三个判据来自「用户在这一屏要做什么」，不是来自视觉喜好。
- 这是模型，不是标准。8 条数据时三种排法都好用；差别要到规模、多字段比较、批量操作时才显出来。演示没有测时间，只呈现结构。

## 适用条件和取舍

- **判据 1 主导。** 既要比较又要进入，先满足比较。
- **表格里塞非值内容**（头像、多行文本、标签、进度）：这一列不再是同质的值，不能再假设它能排序或比较；要承认它是「展示列」。
- **列少（2–3 列）时，表格的结构优势很薄**，列表往往更省高度。
- **移动端**：表格会被挤压，常见做法是「卡片化的行」。那不是表格——别指望它还能逐字段比较。这一点留给后续关于横向滚动的条目。
- **卡片和描述列表**只在这里点到，不展开。
- **演示不测人**：没有测完成时间、错误率、偏好。

## 例子

- **订单管理**：比金额、按状态筛、批量发货 → 表格。
- **消息、文件、通讯录**：认出、读一条、点进去 → 列表。
- **商品挑选**：认图认价 → 卡片。
- **列表右端金额**：唯一保住的那一列。

## 还没定

- 一份列定义要不要跨页面共享（列表页、导出、报表用同一份 columns）。
- 表格退化成列表的阈值：几列以下该换，没有数据。
- 移动端的表格形态（横向滚动 vs 卡片化）没有讨论，留给后续关于横向滚动的条目。
- 表格第一列做「头像 + 名称 + 副文本」时，排序和筛选按哪个值，没有定。
- 卡片与描述列表的分工没有展开。
- 数据量对选型的真实影响没有测；现在只有「8 条时三者都够用」这个观察。
