# 接缝

两段状态相邻的那一点，叫接缝。连续性不是到处都要——**看得见的接缝必须对齐，看不见的接缝免费。** 判据只有一句话：改判那一刻，有没有像素同时属于改判前和改判后的账。

## 先看演示

[打开演示](demo.html)（双击即可，不需要本地服务；脚本在同目录 demo.js）

两个对照：

1. **时序接缝**：脚本动画把卡生成到位，再交给用户拖动。只改交接那一刻的位置是否重合。对齐时看不出交接；错位时交接瞬间跳一下（错过就重播一次）。
2. **看不见的接缝**：一张卡从舞台左侧离开、右侧回来。只改传送发生在画内还是画外。画内传送看得见断点；出画传送的断点在没人看得见的地方，免费。

空间接缝（深度改判只能发生在无人区）见[卡片堆叠](../卡片堆叠/demo.html)演示第一部分。

## 我们的理解

**接缝是零时长处的一致性。** 编排管「先后」（有时间差的变化怎么排），接缝管「同一时刻」：在两段状态的交界处，同一批像素的账不能同时记在两个人名下。它有三种常见形态：

1. **时序**：脚本动画的首帧必须与当前交互状态重合。生成的最后一帧停在哪儿，拖动就从哪儿开始。
2. **空间**：遮挡与深度关系的换账必须发生在无人区。z 轴不能过渡，重叠区里换深度必然穿帮；要换到第 n 层，就先离开前 n 张的区域。
3. **状态**：一个元素从「被脚本摆布」变成「被用户摆布」（或相反），交接点的位置、速度、透明度都要接上。

**看不见的接缝免费。** 出画之后传送、被完全遮挡时换状态、无人区换深度——断点只要没被看见，就不需要对齐。这给了实现一条便宜的出路：与其在画内做艰难的连续换账，不如先把对象带出视野，在看不见的地方改判，再带回来。

**对齐不等于「用户会觉得更好」。** 首帧对齐是接缝正确性：两段状态在衔接点必须重合，否则切换瞬间跳变——用户是否归因不重要。它引申不出「用户会因此觉得更好」的证据；成本失控时不值得。这条边界是讨论中定下的。

## 为什么这样判断

- 判据是「有没有像素在账上」：可见区域内的改判，观众看得见同一批像素的归属突变；不可见区域内的改判，没有像素见证。
- z 轴不能过渡是机制事实：z-index 与 3D 深度都是离散的，所以「连续的深度变化」不存在，只能把跳变藏起来。
- 范围通式（要离开跨越的那几层）是「跨越谁就先离开谁」的直接后果。
- 首帧对齐来自原文案例（评委卡的脚本动画与交互衔接）；对齐与错位的可见差异在演示里可复现。

## 适用条件和取舍

- 接缝要求只作用在「变化被显示出来」的那一帧；接缝之外可以跳变——换页、弹出、瞬时就位都正常，不需要为了「平滑」给所有变化加过渡。
- **先问这两段是否声称是同一个东西。** 声称连续（同一张卡、同一个空间）→ 接缝必须对齐；声称替换（两个对象）→ 跳变本身就是信号，加过渡反而把替换说成了连续。
- 代价：把改判赶出可见区会让总时长变长（先出画、再进场）；对齐脚本与交互的首帧需要设计与实现配合。
- 例外：完全被遮挡时换状态是免费的，但遮挡的边界要算准——露出 1px 就进入可见区。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 看得见的必须对齐、看不见的免费 | 定义 | 写死 |
| 判据（有没有像素在账上） | 判据 | 写死 |
| 范围 = 跨越的那几层 | 定义 | 写死 |
| 首帧对齐 | 要求 | 有案例与演示支持 |
| 对齐 ≠ 用户感知更好 | 边界 | 写死（讨论中定下） |
| 具体时长、距离 | 演示值 | 不是推荐值 |

## 还没定

- 半透明遮挡、模糊、快速运动下的「看得见」如何界定：1px 边缘露出算不算看见；极快的可见跳变（人眼可能捕捉不到）算不算穿帮。
- 接缝对齐的成本与品质收益如何权衡，没有可量化的口径（原文案例是品质目标下的投入，不是对比实验）。
