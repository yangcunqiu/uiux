# 感受与论据

「感受」在设计判断里常被说成两个相反的论断。一边说它不值钱：说「这个动画感觉有点快」，不如说「这个动画看起来是 100ms，有点快」专业（[一位做 UI 的工程师的年度自述](https://wxad.design/abc/2023)）。另一边把它当护城河：体验的核心「很难通过解释获得」，能感受而无法言说的部分恰是价值所在（[同一位作者的品质自述](https://wxad.design/abc/quality-of-ui)）。两条各对一半，因为它们管的不是同一件事：发现问题时感受是探测器，交付判断时感受必须翻译。

## 我们的理解

> **发现环节，感受是探测器；交付环节，感受必须翻译。**

- **探测器**：灵敏、廉价、不可交付。「感觉不对」「感觉快」标记一个值得检查的位置，它启动检查，但不是检查结果。
- **论据**：要说服他人时，感受必须翻译成可检验的形态——参数（「看起来是 100ms」可以打开检查）、对照（去掉颜色还能不能分辨选中）、行为证据（错按集中在改版后两周）。翻译可能失败：查出来实际是 300ms，暴露的是你的校准偏差。可检验的价值正在于失败能被发现。
- **翻译不出参数的不需要硬翻**：调性类判断（「苹方更适合这个品牌」）拿不出可检验的对错，它本来就是**立场声明**，诚实标注即可。走哪条路由判据决定——见[约束与调性](../约束与调性/README.md)：违反它，坏的是功能还是只是味道。
- **感受可以是原因，不能冒充论据**：交付物可以只是一个选择（调性评审选了 A 方向），选择的原因留在感受里没有问题；把原因包装成论据才是问题。
- **用户报告的感受是数据，你的感受降级为「我的观察」**——这是[假想人](../假想人/README.md)三个坐标在感受上的用法。

一句话：**感受可以在场，论据栏里只能出现翻译后的形态。**

## 为什么这样判断

- 本条来自讨论：两种相反说法出自同一位作者前后两年的自述，按「发现/交付」两个环节拆开后互不矛盾。
- 「探测器/论据」的可检验性在于用法可执行：每条要交付的判断都能被问「依据是哪种形态」，答不上翻译的自动归入立场声明或「我的观察」。
- 「看起来是 100ms」的原文对照值得注意：它依然只是感受估计，数字可能错——专业的不是数字本身，是把判断放进了能被检查的位置。

## 适用条件和取舍

- **翻译不总是可能**。说不清差在哪、又拿不出对照时，先降级为「我的观察」，不要硬凑一个归因错误的参数——硬凑的参数比诚实的立场声明更糟，因为它假装可检验。
- **本条管用法，不管灵敏度**。探测器的准头靠接触和实践积累（原文作者给过「5–6 年」的经验值，标注为个人感受）；本条不改准头的账，只管用法的账。
- **用户测试报告的感受不在此列**：访谈里「用户觉得乱」走数据通道，进[假想人](../假想人/README.md)的三个坐标；只有评估者自己的感受才需要翻译。

## 例子

- 「这个动画感觉有点快」→「这个动画看起来是 100ms，有点快」：同一感受，后者可以被打开检查证伪。想练这个翻译：下次觉得「有点快」时，先写下估计的毫秒数再去查——查出来的偏差就是校准练习。
- 「这界面不像我们家的」→查是哪根轴被拨了（[约束与调性](../约束与调性/README.md)的调性轴）：翻译成「圆角从 4 拨到了 8」就是论据；查不出轴，就只是观察。
- 「我觉得乱」→排队等翻译的观察；「三个用户都说找不到入口」→数据，可以直接当论据材料。

## 还没定

- 探测器的灵敏度能否刻意练：原文作者从「很多开发者没有这种惯性」走到「教不来的东西，你也不用学」，自己收回过一遍，没有结论。
- 翻译失败又拿不出对照时的处置只定了「降级为观察」，没有更细的流程。
