# 叠层与返回栈

第二层不是默认解。每多一层，就多一个"取消"的作用对象、多一层蒙版、多一次父子状态同步。先问能不能不叠，再问怎么叠，最后问关掉之后回到哪。

## 我们的理解

三个问题，按顺序问：

1. **不叠行不行？** 就地展开、同容器的一步、锚定浮层，都比开第二层便宜。
2. **叠的话，A 要不要留在眼前？** 要 → 堆叠；不要 → 隐藏 A 再开 B。
3. **关掉之后回到哪？** 焦点、滚动、状态、以及"取消到底取消了什么"。

### 一、从便宜到贵：五档

| 档 | 做法 | 代价 |
|---|---|---|
| 1 | **就地展开**：在 A 的正文里展开一段 | 只适用于字段级的补充，撑不起有提交边界的任务 |
| 2 | **同容器的一步**：A 换内容、换底栏，返回 = 上一步 | 有独立提交边界的子任务放不进来 |
| 3 | **锚定浮层**：气泡、下拉，不遮 A | 只装得下选择和短内容 |
| 4 | **隐藏父层再开 B**：同一时间只有一层可见 | 失去"从哪来"的线索，要靠标题和返回补 |
| 5 | **堆叠**：A 可见（变暗），B 压在上面 | 两层蒙版、注意力分散、父子状态要同步 |

判断是从上往下问"能不能停在这一档"，不是直接跳到第 5 档。

**第 2 档有一条硬边界：只用于没有独立提交边界的子任务。** 选一个已有的部门，可以在 A 里换内容、换底栏；但"先新建一个部门再选它"有独立的成功和失败，必须开第二层——否则 B 的失败没有地方交代，A 的底栏也不知道该说"取消"还是"创建"。

### 二、容器大小随层级递减

页面 > 抽屉 > 对话框 > 气泡。

从对话框里开出一个抽屉，视觉上是"往上加了一个更大的东西"，层级反了。所以"别从弹窗跳抽屉"和"要更大的地方就改成抽屉"其实是同一条：**需要更大的容器，说明第一层选错了**，该改的是第一层，不是往上叠。

反过来，抽屉里开对话框是成立的：下层大、上层小，符合"越往上越具体"。

### 三、三种叠法，三种承诺

| | A 还在吗 | A 的状态 | 代价 |
|---|---|---|---|
| **堆叠** | 可见（变暗） | 保留 | 两层蒙版、注意力分散 |
| **隐藏—恢复** | 不可见 | 保留（不能卸载） | 失去"从哪来"的线索 |
| **替换** | 销毁 | 丢失 | 最简单，但 A 的草稿没了 |

- 需要**读** A 才能做 B 的决定 → 堆叠。
- A 不用看，但 A 里有没提交的编辑 → 隐藏—恢复。
- A 是只读详情，或者本来就是同一任务的另一个视图 → 替换。

### 四、返回栈

1. **Esc、浏览器返回、×、取消，作用对象都只是最上面一层。**
2. **成功可以一次关掉多层**（结果已经交代完），**取消只能关一层**。混在一起，就会出现"点取消把整个流程退了"。
3. 关掉 B 之后，焦点回到 B 的触发器，A 的滚动位置不动。
4. 浏览器返回：层在 URL 里就自然；不在就拦 `popstate` 弹一层，别无脑 `history.back()`，那会把整个页面退掉。

### 五、父层要活下来，也要更新

1. **草稿不能卸载。** 隐藏父层时把它留在内存里，否则 A 里的编辑状态没了——那和"取消"没区别。
2. **子层提交后要回填。** B 选完部门，A 里那一项要更新；不回填，A 显示的就是旧值。回填不是重载整层，是替换那一项。

第 2 条是[拆组件](../拆组件/README.md)里"背后状态变了，面板可能过期"的另一种形态：分层之后，过期发生在下面那层。

### 六、蒙版：最多一层可见的暗度

堆叠时 B 的蒙版会把 A 再压暗一次，看上去就是两层暗度。要么让 B 的蒙版覆盖全部、A 不再单独变暗，要么改用隐藏—恢复。原文说"两层蒙版让人觉得负担很重"，重的不是蒙版数量，是**两个不同的暗度**在说"这里有两层"。

## 为什么这样判断

- 五档的代价是结构性的（多一个取消对象、多一层蒙版、多一次同步），可以直接数；哪一档够用要靠任务性质判断。
- "容器大小递减"是从视觉层级推的，没有实测；它解释的是"为什么从弹窗里开抽屉别扭"，不是一条测量结论。
- "第 2 档只用于没有提交边界的子任务"来自[拆组件](../拆组件/README.md)的层级判据：有独立提交边界的任务值得单独一层。这是讨论里定下来的分界，不是测出来的。
- 返回栈四条是行为约定；"成功可跨层、取消只一层"是从"结果已经交代完"推的。
- "两层蒙版重在两个暗度"是观察，不是测量。

## 适用条件和取舍

- **堆叠不是错，只是贵。** 需要同时读两层时才值得；只是"想保留上下文"的，隐藏—恢复更轻。
- **替换会丢 A 的草稿**，只适合 A 没有未提交内容、或草稿可弃的场景。
- **隐藏—恢复要求 A 不被卸载**，对组件实现有约束；如果框架把隐藏当成销毁，这个模式会退化成"替换"。
- 移动端的底部面板堆叠、手势返回是另一套习惯，这篇没有展开。
- 这轮没有做演示：叠层要看清"两层暗度"和"返回栈"，得做成可切换的对照页，还没排。

## 例子

- 抽屉里编辑员工，点"选择部门"开对话框：抽屉在下、对话框在上，尺寸递减，成立。
- 对话框里点"选择部门"想开抽屉：层级反了；正确做法是把第一层做成抽屉。
- 新建用户组 → 添加成员：隐藏第一层，成功后恢复；比叠两层蒙版轻。
- 在 A 的正文里展开部门树，选完收起：同容器一步，没有第二层。
- B 提交成功且流程结束：一次关掉 B 和 A，落到列表并刷新；取消只关 B。

## 和其他主题的关系

- [拆组件](../拆组件/README.md)：层数由内容决定、多层让通用控件变模糊；这里是它的下一步——第二层怎么开、关回哪。
- [关闭的承诺](../关闭的承诺/README.md)：Esc 是栈的那一节；四条关闭通道在多层里各自只作用于最上层。
- [尺寸与容器](../尺寸与容器/README.md)：壳的选择（对话框 / 抽屉 / 整页）；本层的"容器大小递减"是它的补充。
- [状态共享](../状态共享/README.md)：那里讲多条消息压成一条缝的"层叠"，不是嵌套的层，别混。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 五档的顺序（从便宜到贵） | 定义 | 写死 |
| 同容器一步只用于无提交边界的子任务 | 定义（判据） | 写死 |
| 容器大小随层级递减 | 默认 | 可偏离：移动端底部面板另算 |
| 三种叠法及各自代价 | 定义 | 写死 |
| 成功可跨层、取消只一层 | 默认 | 可偏离：明确标注"全部取消"的流程 |
| 最多一层可见暗度 | 默认 | 堆叠时统一暗度即可偏离 |
