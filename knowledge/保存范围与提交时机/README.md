# 保存范围与提交时机

一次操作的提交范围，由该任务中哪些内容应一起生效、一起失败或共同进入下一业务状态决定。页面分区可以帮助使用者理解这个范围，数据模型和接口能力决定实现代价。一个页面可以编辑多个独立资源，一个共同提交的表单也可以跨越几个页面。

## 保存、提交和导航

“保存草稿”保留当前进度，可允许资料不完整。“发起审批”“发布”“下单”会引起新的流程或外部影响，应让使用者明确发起并能核对结果。“下一步”通常只移动到下一段，并按需校验当前步。若其中还包含保存或正式生效，应明确显示发生了什么。自动保存草稿和显式提交可以并存。

按钮名称、位置、未保存标记和结果提示共同表达哪些内容会生效。线性短表单通常在页尾提交，使用者可先答完问题。超长表单、频繁保存或移动键盘影响操作时，固定底部操作栏能让入口常驻，代价是占用空间、可能遮住末项错误并持续吸引注意。把唯一提交放在顶部可能导致滚动后入口消失。顶部与页尾都设入口时，要核对两处的作用范围、处理中状态、结果和 Enter 默认动作。这两种顶部方案均不宜作为线性表单的默认。确实需要两个入口时，应共用一个提交范围和处理状态，并让人能辨认主要入口。

## 何时分段保存

个人资料、通知偏好和只读的安全设置可以放在同一设置页。如果它们能独立生效、失败和重试，每段可以有自己的保存及状态。只读段可说明所需权限。保存通知失败时，已经成功保存的个人资料应仍显示正确结果，重试只针对通知。反过来，同一条业务记录的几段若共享校验且最后必须一起生效，可以在中途存草稿，正式提交仍以整笔操作为单位。仅按视觉卡片拆出多个“保存”会误导使用者。

订单确认页中，单独保存一个地址和最终创建订单是两个动作，即使它们相邻。核对时同时看请求包含的业务值、实际生效的对象和重新进入后的状态。只验证发出的字段不足以证明一次跨资源保存满足共同生效要求。

## 体验对接口的要求

产品若决定“这些修改全部生效或全部不生效”，接口需要能兑现这一保证。几个现成的独立接口可能会部分成功，前端的统一成功提示无法补足该能力。可以共同设计支持整体结果的接口，也可以在业务允许时明确采用分段生效，向用户显示各段的结果和可重试范围。这两种方案对用户的含义不同，更换保证须由项目明确决定。

接口契约写清可依赖的行为，例如哪些值生效、重试是否重复产生副作用、失败后能否确认已处理部分。具体端点、字段名和存储组织由项目选择。与业务类型有关的失效值和草稿保留见[表单结构与条件字段](../表单结构与条件字段/README.md)。
