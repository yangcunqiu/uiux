# 尺寸与容器

弹窗多大，不由"效率打分"定，由"你承诺支持多小的屏"定。内容多的时候，先动布局——分组、常用、搜索；别急着换容器。宽度换的是滚动，不是"找到"。

## 先看演示

[打开「尺寸对照」](尺寸对照.html)（双击即可，不需要本地服务）

框里是一块模拟屏幕：屏幕宽度 1024 / 1280 / 1440 可切，弹窗宽度 600 / 800 / 1200 可切，原因数 10 / 30 / 100 可切。表格实时给出滚动比、主按钮可见比例、两段指针距离。

观察重点：

1. 1024 屏 + 1200 宽 + 100 个原因：弹窗两侧各出屏 88px，标题只剩半个字，右下角的确定按钮整个在屏幕外，屏内只剩"取消"（确定可见 0%）。
2. 同一宽度切到 1440 屏：确定 100% 可见、滚动比 1.00、100 项一屏放完。同一个 1200，在一种屏上不能用，在另一种屏上是正常选择。
3. 1024 屏、100 个原因：600 / 800 / 1200 的滚动比是 2.11 / 1.47 / 1.00。宽度确实换得来滚动。
4. 但首屏完整选项只是 43 / 64 / 82——1200 宽时 100 个都在屏内，找那一个还是得扫 100 个。

## 我们的理解

### 一、尺寸规范能规定的四件事

1. **最小支持屏**（比如 1280×720）。它决定宽度上限，是唯一有硬约束的量。
2. **宽度档位**，每档一句话说清装什么内容。
3. **越界行为**：超过屏幕时收缩、内滚，还是换容器。没有这一条，任何固定宽度都会在某个屏上出事。
4. **高度与滚动**：max-height、正文内滚、底栏固定。这是结构，不是尺寸。

它规定不了"最优宽度"，因为不存在。

### 二、上限是算出来的，不是打分打出来的

1024 屏两侧各留 32 边距，上限大约 960。800 是留了 112px 余量的整数——这不丢人，规范本来就该是整数加余量。

丢人的是给这个整数补一个撑不住的理由。常见的一种是拿菲茨定律算"从选项到确定按钮的距离"，得出"越宽越慢"。菲茨里的 D 是"指针当前位置到目标"，由用户上一个动作决定，不由弹窗宽度决定；宽度只是通过布局间接改变 D。量级上，宽度从 600 翻到 1200，估算多一百多毫秒，而"在 100 个原因里找到对的那个"是秒级。用一把量毫秒的尺子去给一个秒级的任务打分，打出来的 ⭐ 只是装饰。

真正的分界是二值的：在屏内 / 不在。

### 三、宽度换滚动，不换"找到"

1024 屏、100 个原因：

| 宽度 | 滚动比 | 首屏完整项 | 确定可见 |
|---|---:|---:|---:|
| 600 | 2.11 | 43 / 100 | 100% |
| 800 | 1.47 | 64 / 100 | 100% |
| 1200 | 1.00 | 82 / 100 | 0% |

加宽能把"要滚两屏"变成"不用滚"，这是真的。但它不改变"100 个里找一个"：候选还是 100 个，只是不用滚了。找的成本由排序、分组、搜索决定。

### 四、内容量定布局，任务形状定容器

"100 个"这一个事实会以四种不同的方式坏掉，各自要动的杠杆不同：

| 症状 | 真正的问题 | 该动的 |
|---|---|---|
| 要滚两屏，底栏被挤走 | 装不下 | 限高 + 内滚 + 固定底栏，或更大的容器 |
| 都在屏内，还是找不到 | 定位不到 | 排序、分组、搜索 |
| 选的时候要回看凭证 | 接不上 | 抽屉（保留父页） |
| 一条要填很多附加信息 | 任务变长 | 抽屉 / 整页 |

容器不由"有多少项"决定，由任务多长、能不能中断、要不要和背后的页面并置决定。

任务太长的时候，拆开比加宽更值：把"基本信息"和"配置信息"分成两步，保存后跳到配置页——第一步用轻弹窗，第二步用整页。弹窗只承担"当场能做完"的那一段；做不完的，交给页面。

### 五、大集合的三层结构

- **常用置顶**（5–10 个，由使用数据生成）：给熟手。代价是位置会变、肌肉记忆失效——所以常用区固定，全量区不跟着重排。冷启动没有数据时它是空的，得靠分组兜底。
- **分组**（按分类体系）：给生手。不知道有哪些、也不会搜的人只有这条路。代价是多一次"它属于哪组"的判断；组名必须一看就懂，否则更慢。
- **搜索**：给熟手找长尾。代价是得知道词——自定义的词，新人搜不到；中文还有别名问题（"证件"和"身份证"）。

三层对应三种用户状态。只做一层，另外两种人就慢。

### 六、什么时候必须换容器

1. 选的时候要对照父页（凭证、合同）→ 抽屉；
2. 一条要填很多附加信息 → 抽屉 / 整页；
3. 要连续处理多条 → 批量流程；
4. 大到连"搜索 + 几个组头 + 一屏结果"都放不下（几百项、深层级）→ 抽屉 / 整页 + 树。

四条都跟数量没有直接关系。第 1 条最容易被忽略：审核员常常要边看证件边选原因，模态弹窗会把证件盖住——这时换抽屉的理由是"并置"，不是"100 个"。

### 七、同类任务用同一种壳

哪怕某个短表单用弹窗更合适，如果同类任务都在抽屉里，它也该在抽屉里。用户不用每次判断"这次从哪弹出来"。

这是团队约定，不是普遍规律：它买的是可预期，代价是个别任务会笨重一点。边界是"同类任务"，不是"所有弹窗必须一样大"。

### 八、结构件：底栏、内滚和锁背景

- **头和尾固定，中间滚。** 弹窗高度由可用高决定，不由内容高决定；内容少时高度跟着内容走，别让底栏浮在半空。
- **去掉滚动条会让页面抖一下。** 锁背景滚动（`overflow:hidden`）会让滚动条消失，正文宽度变化十几像素；用 `scrollbar-gutter: stable`，或者补一段同宽的内边距。
- **全屏容易出现双滚动条。** 锁了页面又让内容滚就是两个；要么只让内层滚，要么别全屏。

## 为什么这样判断

- 尺寸那条链（内容量 → 候选宽度 → 效率 / 适配打分 → 定值）里，真正起作用的只有"1024 屏放不下 1200"这一条二值事实；其余是给结论补的依据。
- 菲茨的量级估算，公式和演示取值都写在演示页脚，只说明量级，不是测量结果。
- 滚动比、首屏完整项、确定可见都是演示里量的真实渲染尺寸，不是估的。
- "宽度换滚动不换找到"是推理：候选数量没变，变的是滚动次数。没有做用户测试。
- 三种人、三层结构是模型，不是测过的结论。"常用置顶有效"依赖使用分布是偏的——这应该用数据验证（前 10 个原因占多少次选择）。
- 换容器的四个信号来自任务属性（长度、可恢复、并置、批量），不是数量阈值。
- 一致性是团队约定，不是普遍规律：它买的是"不用猜从哪弹出来"。
- 结构件的抖动来自滚动条占位，不是滚动本身；`scrollbar-gutter: stable` 是这一条的现成修法。

## 适用条件和取舍

- **演示假设弹窗是固定宽度、没有写 `max-width`。** 真实组件库多半会加收缩规则——那正是"越界行为"要规定的东西。加了之后问题从"出不出屏"变成"收缩后布局还成不成立"。
- **常用置顶依赖分布偏斜。** 每个原因使用频率差不多时，置顶买不到什么，还让位置不稳。
- **分组依赖分类体系对用户可见且易懂。** 分类是内部编码、名字含糊时，分组会把"找不到"变成"不知道归哪组"。
- **搜索依赖用户知道词。** 客户自定义的词、别名多的场景，搜索只能兜住熟手。
- **反例：如果每个决定都是新的、必须逐条读完才能选**（法务条款、风控规则），那它不是"选"，是"读"。按频率置顶反而有害——没读过的那些被排到下面。这时要换的是任务形态（文档式、分组阅读、整页），不是宽度，也不是把弹窗改成抽屉。
- 这篇只有尺寸部分有演示；布局与容器那部分（第四到第八节）是讨论得出的判断，没有做对照演示。
- 不涉及：关闭方式与遮罩见[关闭的承诺](../关闭的承诺/README.md)；第二层怎么开、关回哪，见[叠层与返回栈](../叠层与返回栈/README.md)。

## 例子

- 审核不通过原因：100 项、单选、高频 → 弹窗 + 分组平铺 + 常用置顶 + 搜索；不需要换抽屉，除非要看凭证。
- 同样 100 项，但每个原因要附金额、证据、说明 → 任务变长，换抽屉 / 整页。
- 20 条一起处理 → 不是把弹窗加宽，是列表页的批量操作。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 最小支持屏决定宽度上限 | 定义 | 写死 |
| 越界行为必须有 | 默认 | 可偏离：容器本身不会溢出时不需要 |
| 宽度换滚动不换找到 | 定义（候选数不变） | 写死 |
| 四类失败与对应杠杆 | 定义 | 写死 |
| 换容器的四个信号 | 条件 | 写信号，不写数量阈值 |
| 常用 / 分组 / 搜索三层 | 模型 | 不是标准；按使用分布和分类质量取舍 |
| 同类任务同一种壳 | 约定 | 团队约定，不是规律 |
| 结构件：尾固定、体滚、锁背景 | 默认 | 内容永不超一屏时可省 |
| 具体档位（600 / 800 / 1200） | 经验值 | 由最小屏和内容预算算，不照抄 |

## 还没定

- 最小支持屏取多少（1280 还是 1024）是产品决定，不是设计能定的；这篇只给了算法。
- "前 10 个原因占多少比例"才值得置顶，没有数据阈值。
- 分组平铺与"可折叠分组"的差别没有讨论。
- 多选（一次勾几个原因）时三层结构怎么变，没有展开。
