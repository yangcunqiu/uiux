# 取回与放置

选项一多，麻烦就不在"太长"，在**怎么取回**。取回方式定了，放哪儿、什么时候生效，才有得谈。

## 先看演示

[四种摆法](四种摆法.html)（双击打开，不需要本地服务）

同一份预约时段数据，四种摆法：横向摊开（分段）、竖向摊开（列表）、就地折叠、藏进浮层。上面的滑杆改选项数量（3–24）和标签长度（短/长），看每种摆法先在哪坏。

观察重点：

1. 数量从 12 拉到 24：竖向摊开长到 1000px 以上，把下面的内容整个推下去；横向摊开把多出来的选项裁在滚动条右边；浮层和折叠的闭合高度基本不变。
2. 切到长标签：横向摊开只剩几个可见，其余被裁掉，没有任何"还有更多"的提示。
3. 浮层里选一个，它会立刻收起：其余选项连同"剩几位"一起消失，只剩触发器上的一行字。
4. 折叠可以同时展开两段，两组选项同时在场；浮层做不到，一次只能开一个。
5. 每张卡底部的"可见 / 总数"数的是此刻完整落在卡片里的选项，不是代码里存在几个。

这个演示只覆盖"放哪儿"和"数据变大时怎么坏"；取回方式（搜索/扫描、置顶、最近使用）和拉取时机在正文里，没有演示。

## 我们的理解

**四种取回方式。** 用户怎么在长列表里找到想要的：

| 用户知道 | 取回方式 | 例子 |
|---|---|---|
| 知道名字 | 搜索 | 输入"杭州" |
| 知道类别 | 分组 | 华东 → 杭州 |
| 知道位置 | 排序（字母、时间） | A 开头往下翻 |
| 什么都不知道 | 都不管用 | 换控件，不是优化下拉 |

"超过 10 项加搜索"只在"知道名字"时成立。10 个已知选项加个搜索框反而更慢——输入比扫一眼贵。阈值不是数量，是两件事：要不要滚，以及用户知不知道名字。

**搜索型与扫描型。** 用户靠输入找的列表，可以加"最近使用"；靠结构找的列表（分组、排序），在顶部插一块会变高的区域，会把"华东是第三个组头"这种空间记忆打乱。

当前值置顶的高度恒定（0 或 1 行），偏移可以学；最近使用的高度会变（0–N 行），偏移学不了。所以：

- **当前值置顶**：恒定、用复制、单独分隔。几乎总是可以加。
- **最近使用**：只加在搜索型列表；扫描型不加，或者加到别处（搜索框的联想、首屏推荐），而不是列表顶部。

置顶几乎总是"复制"而不是"剪切"：剪切会让"杭州不在 H 里了"，而最近使用一变，项还会在两个区之间跳。复制要配区标题（"当前"、"最近使用"），两处选中态要同步——同步失败就是假回执。

**置顶 vs 默认值。** 两者都是"替用户省一次"，但置顶只改位置、不改语义；默认值改的是"未选"这个状态，用户事后分不清是自己选的还是系统替的。值下拉里优先置顶；默认值只给"没后果的偏好"，筛选器不要默认收窄结果。

**禁用项。** 短列表里留着禁用，是在教能力边界（这个世界有什么）；长列表里，永远不可用的直接隐藏，别占扫描；暂时不可用的留在原位并配一句原因。位置一挪，预期就废了。

**容器：锚定还是不锚定。**

- **锚定浮层**（下拉、popover）保住因果（东西是从这个按钮出来的）和返回（点外面 / Esc 一步回去），代价是空间小，容易和页面滚动、键盘打架。
- **不锚定的容器**（底部抽屉、侧边、全屏、页面）空间大，但切断因果，必须自己重新交代"我在改什么、改了几项、改完点哪"。

选容器的两个判据：

1. **上下文要不要同时可见。** 要 → 浮层或半高抽屉；不要 → 全屏/页面。
2. **这个选择值不值得占一条历史记录、一个地址。** 有名字、会回来、要分享的（保存的视图、报表配置、收货地址）用页面或 URL；顺手调一下、调完就走的（排序、单条件筛选）用浮层。页面还有个隐藏好处：返回键天然是"撤销这次筛选"，浮层没有。

移动端选底部抽屉，主因不是空间，是触达和键盘：上半屏够不着，键盘弹起会把浮层顶走；底部抽屉把操作放在拇指区。

**拉取时机。** 它不是"什么时候发请求"，是"用户什么时候看到结果、什么时候承担后果"：

- **同屏就实时。** 桌面侧边面板、不遮表格的浮层，改一下就能看见结果，没有承诺点最好。
- **不同屏、且应用一次有副作用，才要"确定"。** 副作用指重置分页、丢选中、重排列表。没有副作用时，确定是多余的一步。
- **遮挡时的"实时"只剩实时发请求。** 用户看不见，请求白花，还可能把他正在看的列表冲掉。想保留实时，唯一的补法是把回执搬进面板——一个实时计数。

**计数是后端能力。** 面板里的"预计 24 条"要求一个便宜的 count，而且和列表同源、同时；不同源就是假回执（面板说 24，应用后列表 23）。它还有一个成本错位：同屏时列表本来就要拉，count 顺带、免费；遮挡时不想拉列表，count 才要单独查——它最贵的地方，正好是最需要它的地方。没有这个能力就接受"提交后才知道"，那是批量模式的诚实版本。

**关闭语义与草稿。** 有"确定"就必须和它一致：点外面关闭不能偷偷提交；如果点外面也提交，那个按钮就是装饰。两种模式的默认正好相反：

- 批量 + 确定：关闭 = 放弃（想保留就点确定）。
- 实时 / 关闭即应用：关闭 = 保留（想重来就点重置）。

草稿只在"改起来很贵"（十几个条件的构建）时值得留，而且要标"未应用"——否则面板里是"待应用"、列表里是"已应用"，两个真相会互相打脸。

## 为什么这样判断

- 取回方式决定优化对象：搜索优化输入，分组优化结构，最近使用优化历史。用错对象，加再多控件也不解决。
- 顶部动态区与结构取回天然冲突：变高的区域让组头位置每次不同。
- 复制解决"杭州不在 H 了"，代价是两处同步；这是演示之外的结构推论。
- 容器的因果和返回是可观察的：浮层点外面就回去，页面要按返回且可能丢状态。
- 确定的价值来自副作用：没有副作用时，多一步就是纯成本。
- 计数：同源同时是正确性要求；成本错位是接口结构决定的。
- 本文的容器判据和拉取判据是讨论中形成的模型，不是标准；四种摆法的演示只覆盖"放哪儿"和"数据变大时怎么坏"。

## 适用条件和取舍

- 阈值不是数量：要不要滚 + 知不知道名字。
- 最近使用：看重复选择率；扫描型列表不加。
- 默认值：只给没后果的偏好；筛选不要默认收窄。
- 容器：浮层适合顺手调；页面适合有名字、会回来、要分享。
- 计数：没有便宜的 count 就不承诺"预计 N 条"；有的话也要防抖、取消、缓存，并和列表同源同时。
- 草稿：只在改起来贵时；必须可见、可重置。
- **演示缺口**：四种摆法只覆盖"放哪儿"和"数据变大时怎么坏"；"搜索/扫描、置顶、最近使用"和"拉取时机"还没有演示，先按文字记录。没有验证的部分不当作已经演示过的结论。

## 例子

- **城市列表**：搜索型，可加"最近使用"；字母分组是结构取回，顶部动态区要克制。
- **日期、金额**：打开时滚到当前值，适合"找附近值"，不适合"从头扫"。
- **筛选**：侧边面板同屏 → 实时；全屏或模态 → 计数或确定。
- **批量删除**：跨页范围写"全部 128 条匹配结果"，不是"128"。
