# 对齐的对象

对齐不改变值，只决定这一列的值排在哪条竖线上。所以它只服务一件事：**让要比较的东西对上**。

它有三个前提——同单位、同格式、放得下。破一个，位置排得再整齐也没有意义。选哪种对齐是最后一步，不是第一步。

## 先看演示

三块各破一个前提：金额（同单位）、日期（同格式）、列宽（放得下）。

观察重点：

1. 切「左对齐」：起点排齐、终点参差；切回右对齐，每个数字的最后一个字符都压在虚线边上。
2. 两个金额列是同一组数字，只有小数位不同。**统一两位**那列红色小数连成一条竖线；**原样**那列只对齐了最后一位——12,800.5 的小数点紧贴末位，98.75 的小数点离末位还隔着两位。
3. 表头跟着内容走：金额列表头也右对齐，和数字贴同一边。
4. 切「大额用万」：1.28万、16.8万 和 98.75、45.6 排在同一条线上。眼睛只看到 1.28 和 98.75，会以为 98.75 更大——差 130 倍。**单位一旦进了格子，右对齐对齐的是单位，不是数字。**
5. 日期三种对齐：格式统一时，这一列内部完全一样齐（都是十个字符），差别只在列的空白落在哪；切「破掉前提」，年、月、日的位置错开，三种一起失效。
6. 切「列宽紧」：168,000.00 变成 168,00…，右边缘仍然齐——但那条线上是省略号。

## 一、右对齐在对齐什么

**右对齐对齐的是最后一个字符，也就是最低位。** 同单位、同精度时，最后一个字符就是小数点后最后一位，右对齐才等于「把小数点排齐」，位数和量级才能一眼读出来。

小数位不统一时，它只对齐了末位：12,800.5 和 98.75 的末位都在线上，小数点却在两条不同的竖线上。这时「右对齐方便比大小」不成立——它只对齐了最后一个字符。

**左对齐对齐的是前缀**：起点一致，读的时候每行开头在同一位置。适合日期、编号、名称这类「读」的值。

还有一个常被忽略的条件：**等宽数字**。比例数字的字体里，1 比 8 窄，右对齐也排不齐各位。这是字体层面的事实，不是排版选择——演示环境的系统字体里，1 和 8 都是 8.22px（14px 字号），本来就等宽；换成比例数字的字体才会失效。

## 二、三条前提

前提不成立时，选哪种对齐都没有意义。这三条不是「设计选项」：

| 前提 | 破了会怎样 | 演示里 |
|---|---|---|
| 同一列同单位 | 右对齐把单位排到线上，数字反而离开线；眼睛比较的是数字部分，结论相反 | 1.28万 和 98.75 差 130 倍 |
| 同一列同格式 | 日期各段不再落在相同位置，三种对齐一起失效 | 2026-11-02 / 2026/11/3 / 11月4日 |
| 值放得下 | 截断后右边缘齐的是省略号；保住高位、丢掉低位 | 列宽 78px 时 168,00… |

所以顺序是：**先清数据（单位、精度、格式），再定列宽，最后才选对齐。** 把「格式混用」当成一种排版方式，是本末倒置——它是数据缺陷，不是设计选择。

## 三、一张映射表

主键是**值的类型**，不是这一页的任务。金额就是金额，在哪一页都右对齐。

| 值的类型 | 对齐 | 前提 |
|---|---|---|
| 有量纲的数值（金额、数量、比例、时长、容量） | 右 | 同单位、同精度 |
| 时间点、日期 | 左 | 同格式 |
| 标识（编号、手机号、身份证、SKU） | 左 | 同格式 |
| 名称、描述、地址 | 左 | —— |
| 状态、枚举 | 左；标签宽度固定时可居中 | 同一套标签 |
| 布尔（是/否） | 居中或左，一列统一 | —— |
| 操作 | 跟按钮的放置，通常在末列 | —— |

「这一列用来比什么」是**发现类型**的方法，不是判据本身。用任务当判据会引出真正的问题：同一个金额列，在这页要比较、在那页只是展示，就可能被排成两样。

## 四、一致性：规则一致，不是外观一致

系统里该统一的是上面那张映射表，不是「所有表格都用一种对齐」。

- **规则一致**（必须）：同一类值、同一个字段，在任何页面用同一种对齐。用户能感知的不一致是「同一个东西在两处不一样」。
- **外观一致**（不存在）：所有表格长得一样。列的内容本来就不同，强行统一只会让金额列比不了、日期列难读。

可检查的一条：**同一个字段跨页面必须同一种对齐**。不同字段用不同对齐，不算不一致。

## 五、比 / 读不是两个类别

同一列经常两个都要：金额既要知道这单多少钱（读），又要比大小（比）。所以不是分类，是**哪个需求不能被牺牲**：

- **有量纲的数值：右对齐支配。** 读也是从高位读起，右对齐不挡读；左对齐却牺牲比。所以数值列没有真正的二选一。
- **无量纲的值：自由。** 日期、编号怎么排都不影响「比先后」——那靠格式统一和排序。左对齐留住一致的起点，是附带的偏好，不是效率理由。
- **居中：只在列宽富余时是选项。** 它把空白分到两边，代价是每行起点不同；属于视觉选择，不是效率手段。

所以「比 / 读」压缩成一句话：**这个值有没有量纲。** 有量纲 → 右（右不牺牲读）；无量纲 → 左或自由（怎么排都不影响比）。

## 六、表头跟随内容

表头和这一列的值贴同一边，列看起来像一个整体。这是默认做法；没有发现必须让表头统一左对齐的情况，所以不设例外。

## 为什么这样判断

- 对齐的功能是位置共享：同一列的值共用一个横向位置。所以判据只能是「这个值有没有量纲」，而不是「这页要干什么」。
- 右对齐支配是推理：读一个数从高位开始，右对齐不改变阅读方向；比大小靠位数和最低位，只有右对齐提供。两边都不牺牲。
- 三条前提来自演示里能直接看到的三次失效：单位、格式、截断。它们不是风格问题，是「对齐这个动作能不能成立」的问题。
- 等宽数字是测量：14px 字号下该系统字体里 1 和 8 都是 8.22px。
- 截断后的行为是观察：右边缘仍然对齐，但排在那条线上的是省略号；保住的是高位，丢掉的是低位。
- 映射表和数据缺陷的判断是模型与约定，不是标准；没有做用户测试。

## 适用条件和取舍

- **状态、枚举**：标签宽度固定时居中可接受；宽度不固定时左对齐更好扫——居中的标签两侧都参差。
- **混合类型的列**（如「3 件」）：按文本左对齐，或者拆成数值列 + 单位列。
- **窄屏**：列宽压缩会先触发截断，对齐随之失效；先解决截断，再谈对齐。
- **表头跟随内容**是默认；表头很长、列很窄时，右对齐的表头可能先被截断，那时要单独处理。
- **只谈列**：表单里单个金额输入框、卡片里的数字，不适用这一套；它们没有列，也就没有「同一列对齐」这回事。
- **演示不测人**：没有测读表速度或出错率，三块只呈现结构。

## 例子

- **订单金额**：右对齐，统一两位、统一用元。
- **下单日期**：左对齐，统一 YYYY-MM-DD。
- **订单号、手机号**：左对齐，它是要念出来、抄下来的标识。
- **状态**：左对齐，标签宽度不一。
- **反例**：一列里「1.28万」和「98.75」混排——右对齐把「万」排到了线上。

## 还没定

- 千分位在窄列里要不要省；省了之后位数怎么读。
- 负数括号、百分号、货币符号的符号位对齐，没有演示。
- 全角字符和多语言下「等宽数字」失效怎么办。
- 表头比内容长时的处理（截断、换行、缩字），没有展开。
- 同一个字段在不同密度（紧凑/宽松）下是否要改对齐，没有讨论。
