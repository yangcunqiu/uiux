# 徽标的账

小红点看起来是一个装饰件，实际在替用户记一本账：这里有几件没处理的事。账记给谁、什么时候销、销的是什么——这些决定比徽标长什么样重要。本条来自一篇徽标设计细节的文章（R 簇）：文章按「长什么样」把徽标分成四类，按「回答什么」重新归类之后，才接得上真正的设计判断。

## 一、按「回答什么」分四类

文章按视觉形式分（圆点、数值、文字、图标），混了两种性质。按回答的问题拆：

| 类型 | 回答什么 | 性质 |
|---|---|---|
| 圆点 | 这里有你没看过的东西 | 提醒：指路，不定量 |
| 数值 | 有 N 件 | **两个变体**：未读数是要清账的债；购物车数是当前状态的计量，结账才清 |
| 图标 | 状态如何（在线、认证、成败） | 状态指示，不是提醒 |
| 文字（秒杀、立减） | —— | 角落里的小广告，什么都没回答，跟前三个不同类 |

数值的两个变体最容易被混：同是 N，未读数说「你欠着」，购物车数说「你现在有」。后面整套清账规则只对前者成立。

颜色因此背了第二种职责。头像上同一个点，可以是未读也可以是在线，用户全靠颜色约定分：红=找你有事，绿=状态正常。[受理与交代](../受理与交代/README.md)里颜色只回答「指到的是它吗」；徽标给它加了「是提醒还是状态」这层新约定——设计时要意识到自己在用两套约定。

## 二、三个技法（可直接观察验证）

- **描边**：徽标不贴宿主，隔一圈与背景同色的描边，压在照片、头像上都读得出来。演示里无描边版本压在暖色头像上会直接看丢。
- **透明度当优先级**：100% 填充与 15–20% 半透明（原文经验值，代理的是醒目程度）分主次——把不透明度当音量旋钮。跟[行的边界](../行的边界/README.md)「亮度表程度」同一思路。
- **数字封顶**：99+ 是惯例：防容器撑爆，也防义务感无限膨胀。

原文还有「加阴影得微妙优雅的悬停感」一条，是调性描述、不是问题答案，没有纳入。

## 三、债务语义的三前提

未读数是一份债务清单的投影。债务语义成立要三个前提：

1. 内容有看的价值密度——漏看一条真的损失什么；
2. 数量级还得清——个位数到几十；
3. 用户自己有还的意愿——这些内容跟他的目标一致。

崩掉任何一个，徽标就从待办清单变成羞辱源（inbox shame：未读数大到用户放弃列表、只靠搜索）。三前提也是泛滥判据的入口：**徽标用在用户自己会想知道的事上（他发起的事有回音），别用在你想让他看的事上（运营推送）**。前者点开是收信，后者点开是看广告，第二次就不点了。

## 四、清账三决定

比「给不给『全部已读』」更靠前的三个决定。

### 1. 什么算「已读」（契约的定义）

| 定义 | 适合 | 代价 |
|---|---|---|
| 打开即销（会话类） | 绝大部分该看、漏看后果即时可发现（私聊） | 「看」定义得太宽，扫一眼也销账 |
| 逐条销（邮件类） | 条条可能有事、漏看后果滞后（工作邮件） | 契约严，配高到达率必然堆积 |
| 见到即销（信息流类） | 漏看无所谓（动态流） | —— |

见到即销已经不是债务，是**游标**：不记「欠了多少」，只记「读到哪了」——跟消息队列的消费位点是同构的。宽严要跟内容的价值密度匹配；错配的典型事故：给营销推送用逐条销，是系统在替用户立假债。

### 2. 销的是什么（义务感的真正所在）

- **真销毁**：连单条的未读状态一起清。代价是义务感消失，加上误伤——该看的也清了。
- **假清零**：只把徽标数字归零，单条未读高亮保留，进列表还能找回。便宜得多，但**措辞必须跟销账范围一致**：「清除角标」和「全部已读」是两个不同的承诺。这是[承诺与边界](../承诺与边界/README.md)的老问题在徽标上的形态：宣布的和系统实际做的记账，必须是同一件事。

### 3. 谁来销（系统可以替你减债）

- **过期**：超过 N 天的未读自动转已读，是单方面减债——债务有保质期。通知中心、社区消息合理（三天前的「新」消息已不是新闻）；用在私人消息上是替用户扔信。
- **封顶（99+）**：记账从精确降为量级，等于系统承认「这些账不值得逐条还」——它本身已是半销账。

### 全部已读是破产出口

「全部已读」救的不是那几千条未读，是**徽标机制本身的可信度**——别让一个永远清不掉的红点教会用户「红灯可以无视」，之后所有徽标一起失效。所以按来源语义分三档落位：

| 来源 | 用法 | 批量清除的位置 |
|---|---|---|
| 对人（会话、@我） | 打开即销 | 放列表操作区，不进徽标——太顺手的清零会把清债变成习惯动作 |
| 对流（通知、动态） | 游标语义，进入即清 | 批量清除、自动过期都合理 |
| 对运营（推送） | 不该立账 | 解法是「不再提醒」，不是「债清了下次接着立」 |

由此修正一个容易压扁的说法：义务感的代价不在「给不给批量清除」，在**销什么、放哪、多顺手**。真销毁式、顺手到点一下的清零会教用户把清债当日常；假清零式、放在操作区当破产出口的清零，义务感不受伤。

徽标不清账比没有徽标更糟：它属于[藏起来的代价](../藏起来的代价/README.md)里的**假回执**（两处数字不同步、角标没更新）——无痕会让人去查，假回执让人按错的前提行动。

## 五、两个补充观察

- **用户会挪用已读当「新旧分界线」**：邮件里一键已读的常见动机不是「处理完了」，是「把旧的加粗消掉，新来的才看得见」。你把它设计成债务清单，用户拿它当时间戳标记——这个挪用是信号：用户要的语义层可能是「新/旧边界」，不是「债的余额」。
- **Inbox Zero 不是一键已读**：它的本义是收件箱里没有未处理项——处理或归档掉；用一键已读达到的 zero 是假 zero。

## 默认值

经验建议，可偏离：

- 会话类：打开即销；批量清除放列表操作区，不进徽标。
- 通知流类：徽标 = 自上次清点以来的新增，进入即清；给自动过期。
- 跨类通用：措辞跟销账范围一致；批量销账给回执（「已将 N 条标为已读」）；真销毁式的给撤销。
- **过期天数写成条件**：信号是「这条内容多久之后还配叫『新』」，半衰期由内容类型定。通知类约一周、文档评论类约一个月，是经验值，代理的是新鲜度衰减——不写成通用数，按自己产品的内容半衰期定。

## 为什么这样判断

- 按形式分类回答不了「什么时候用哪个」；按「回答什么」分，选择变成需求问题。数值的两变体（债 / 计量）是同一个 N 语义不同的直接证据。
- 清账三决定从「给/不给」的压扁二分里拆出来：义务感的代价重新定位到「销什么、放哪、多顺手」，三个动作都能在「销账规则」演示里逐个复现。
- 债务三前提与泛滥判据互为表里：前提崩掉的地方，就是「你想让他看」不该立账的地方。
- 描边、透明度、封顶是可直接观察的技法，演示里能看见差别；阴影一条因是调性描述未纳入。
- 「挪用当分界线」是观察到的常见动机，不是测量结果。
- 过期天数只给信号不给数值，因为数值依赖内容半衰期——写死一个数在任何别的内容上都错。

## 适用条件和取舍

- 债务语义崩掉时，先别急着调徽标样式：先看是不是立错了账（运营推送在用未读数）或定义错了「已读」（营销推送用逐条销）。
- 假清零救的是「不再催」、不销债；进列表还看到一片加粗是它诚实的代价，措辞一致是唯一补救，没有找到更好的解法（见「还没定」）。
- 对运营推送，「不再提醒」把问题还给[运营位](../运营位/README.md)那套喊的规矩，而不是把账立到徽标上。
- 见到即销（游标）模式下，数字大不构成压力——它只说「有多少你还没划过」。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 按「回答什么」分四类 | 定义 | 写死 |
| 数值的两变体（债 / 计量） | 定义 | 写死 |
| 颜色的第二种职责（红=提醒、绿=状态） | 约定 | 全站一致即可；换约定连着换 |
| 描边、封顶 | 技法 / 惯例 | 写死；样式细节项目自定 |
| 15–20% 半透明 | 经验值 | 代理醒目程度，可调 |
| 债务三前提、泛滥判据 | 条件 | 写信号，不写数量阈值 |
| 清账三决定 | 定义 | 写死；三档搭配是默认 |
| 全部已读=破产出口 | 判断 | 三档落位表为默认 |
| 过期天数 | 条件 | 只给「还配叫新」的信号，不给数 |

## 还没定

- 红点疲劳的恢复：用户已经学会无视之后，怎么重新挣回注意力，没有讨论。
- 假清零的措辞除「清除角标」外有没有更好的解法，只定了「措辞跟范围一致」方向。
- 提醒与状态同色系的色弱可用性（红绿之外的第二载体），没有展开。
