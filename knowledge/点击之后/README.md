# 点击之后：一次点击的三个时刻

点赞、投票、收藏、关注、加入购物车——都是一次离散动作，加一个状态变化，再加一段可选的庆祝。看起来是"给按钮加个动画"，实际要先决定一件事：**这次点击里，哪些时刻需要有人负责。**

`click` 事件只在松开时触发。只监听它，等于把全部反馈压在最后一个时刻上。

## 先看演示

[打开演示](点击之后.html)（单文件，双击即可）

三列，每列只是一个动作的不同编排：

| | 悬停 | 按下 | 松开 |
|---|---|---|---|
| **A 只有结果** | 无 | 无 | 数字立刻 +1 |
| **B 有按下态** | 改底色和边框 | 红心缩一档，保持到松手 | 数字立刻 +1 |
| **C 加蓄力** | 同 B | 红心压下去，保持到松手 | 红心飞向数字，到了才 +1 |

C 下面还有三档开关，切换「压缩发生在哪个时刻」：按下 / 松开后 / 按住累积。中间那一档是反例，留着对照用。

每列下面有一行输入状态（`—` / `悬停` / `按住 0.31s`），和一行「数字在松开后多久变化」。

## 一、一次点击是三个时刻

| 时刻 | 谁在等 | 该给什么 |
|---|---|---|
| 按下 | 用户想知道按上了没有 | 立即的确认：变暗、缩一档、下沉 |
| 按住 | 用户在想"还按着" | 只有"按住有含义"时才给（进度、蓄力、长按菜单），否则应该安静 |
| 松开 | 用户想知道结果 | 结果 + 氛围 |

按下到松开之间可能几百毫秒，尤其在触摸设备上。这段时间如果没有任何变化，用户会怀疑没按到，于是松开重按一次——而那会触发两次动作。

演示里 A 列就是这个状态：按下到松开毫无变化。它的输入状态徽标会变，按钮纹丝不动——**状态存在，和状态被表达，是两件事。**

## 二、悬停和按下不是两个确认态

它们回答的不是同一个问题：

- **悬停**：我的目标在哪（这东西能点、我指的是它）
- **按下**：输入被接收了没有

每种输入方式都有这两件事，只是拆法不同：

| 输入方式 | 目标在哪 | 按下了没有 |
|---|---|---|
| 指针 | 悬停 | 按下 |
| 键盘 | 焦点 | 回车/空格按住 |
| 触摸 | 没有这个阶段 | 按下（目标和动作同时成立） |

触摸没有 hover，不是它不需要「目标」，而是**手指本身就在目标上**。所以在触摸上你只看到两段里的一段，不觉得繁琐；在指针上它被拆成两个可见阶段，看起来像两个确认态。其实是**一个动作的两个阶段**。

### 走不同通道，不是减状态

让人觉得繁琐的不是"有两个态"，是"两个态用同一种视觉"。

- **悬停**改「这是什么」：背景、边框、光标。轻、快、低对比——它是"路过"。
- **按下**改「发生了什么」：缩放、下沉、亮度压一档。要快（跟手），幅度要明显——它是"到达"。

同一个通道连做两次变化才显得重复；换到两个通道，读者读到的是两层信息。

### 按下是叠加态，不是并列态

按下的时候指针一定还在上面。所以按下的视觉要**压过**悬停：在悬停的基础上再走一档，而不是从基础态重新开始。否则底色已经提亮过了，按下再提亮一点点，看不出按下去了。

### 一个动作只让一个元素按下去

点复选框，行不该按下去；点行，复选框不该按下去。容器只承接悬停（"这一块是一体的"），按下只给被直接操作的控件。

### 什么时候可以省

- 目标很大、形状本身已经说明一切：悬停可以很轻，甚至只有光标变化。
- 动作极短、按下即完成（开关、分段控件）：按下和结果重叠，可以只做一个。
- 触摸优先：悬停本来就不存在，别把信息挂在它上面。

两条不能省：

- **悬停不能承载必要信息**。它是锦上添花，触摸设备读不到。「这个能点」「点了会怎样」必须由形状、文案、颜色本身说明。
- **焦点必须始终可见**。那是键盘用户唯一的定位手段，和悬停是同一个角色，只是换了输入通道。

## 三、蓄力属于按下，不属于松开

演示里 C 的三档可以直接比较。

**「松开后」（反例）**：按住只缩一点点，真正的压缩发生在松手之后。它有两个问题：那一下不属于你的手；而且按钮要在同一时刻把压缩收回去。

**「按下」**：按下去的瞬间就压住，保持到你松手，松手直接起飞。压缩是你做的，释放也是你做的。

**「按住累积」**：按住越久压得越扁，到头亮一圈。这一档看着最符合"蓄力"的直觉，但它在投票上不成立，原因见下。

### 时间累积需要一个可兑换的输出

按下一个按钮，你的力气是恒定的。形变取决于力，不取决于时间——按住三秒和按住零点二秒，按钮该一样扁。

"越按越扁"的直觉来自拉弓，但弓的输入是**位移**：拉得越远，张力越大，到顶是"拉不动了"。距离是输入，时间不是。

游戏里的蓄力条（按住时间）是另一套约定：**资源累积**。它成立的前提只有一个——积累能换输出。拉得远飞得远，蹲得深跳得高。没有这个兑换，蓄力条只是一个进度条，而"满了"那个信号会变成空头承诺。

一票就是一票。所以演示里这一档没有接任何结果，"满了"之后松手仍然只是 +1——你可以按住试一下值不值这个等待。

反过来，只要输出能随投入变化（录语音、长按连拍、拉弓），时间累积就成立，那时候蓄力不是装饰，是输入。

## 四、形变的载体就是被释放的那个物体

压缩压谁？压按钮的圆圈，还是压里面那颗心？

**压圆圈**的时候，松手瞬间圆要从压扁恢复原尺寸，而心已经飞走了——按钮位置上有一团东西在变形，但它对应的物体不在了。看起来是抖了一下。

**压红心**就没有这一步：心和心是同一个东西，压缩和飞出去是它的两个阶段，松手时它自己离开，不需要任何东西留在原地还原。

顺带一条：起飞点要从**红心自己的中心**算，不是从按钮中心。红心压缩时会下移几像素，用按钮中心会让它在交接时瞬移。

## 五、交接：重合，不要藏起来

按钮要把心让给飞行体。三种做法：

| 做法 | 看到的 |
|---|---|
| 藏起来，再淡入 | 空窗 → 一颗浅粉色的心 → 变红，三段变化 |
| 藏起来，直接出现 | 空窗 → 突然出现一颗心 |
| **不藏，尺寸重合后再分开** | 一颗心分成两颗，没有空窗 |

有效的做法让按钮那颗心和飞行体**起始尺寸完全一致**（用同一条衰减曲线），第一帧完全重合，然后飞行体快速离开，留下的那颗自己松开。

配套的两件事：

- **起飞要快**。飞行体在按钮上方磨蹭，重叠的那两颗就分不开，看起来是重影。
- **不要让按钮的心淡入**。半透明的红心在白色圆里是一颗粉色的心，比直接出现更怪。

还有一个反证：「松开后」那一档不得不把按钮的心藏起来才不穿帮，因为飞行体要当着它的面变成一张更扁更大的心。**需要遮掩本身就说明压缩放错了位置。**

## 六、有空间距离时，运动就是因果

同一个点赞，数字在按钮里（按钮自己变成"已赞"）和数字在别处（票数在页面上方），要的东西不一样：

- **数字在按钮里**：同一个位置，立即 +1 就够。多余的运动反而是噪音。
- **数字在别处**：中间有一段空间距离，必须有运动把两边连起来，而且顺序是**先到，后变**。

反过来的做法（数字先变，心还在飞）会读成两件事：先是数字自己跳了一下，然后有个东西飘过去。

2024 评选的三次迭代就是这个过程：最初只有爱心动画（氛围不足）→ 把爱心加大（还是不足）→ 加一段"汇聚到上方，汇聚后票数增加"（成立）。前两次都在调氛围层的力度，问题其实在结果层和动作层之间缺了一环。

演示里三列都是数字在上、按钮在下，A 和 B 的数字在 0.00s 变，C 是 0.42s——差距只有这一个量。

## 七、延迟的三种用途

同一个词，可以是成本，也可以是信息。

| 类型 | 例子 | 归零后会怎样 | 该怎么处理 |
|---|---|---|---|
| **成本型** | 悬停 200ms 确认意图 | 要重新确认一遍，变啰嗦 | 能共享就共享，能缩短就缩短 |
| **节奏型** | 列表项依次入场 | 什么都不丢，只是变平 | 随意，是风格选择 |
| **因果型** | 爱心和它撞出的背景，背景晚 0.1s | 丢了"谁推谁"，变成两个同时发生的事 | 必须保留，方向不能反 |

判断方法只有一条：**把延迟归零，看丢了什么。**

还有一条更硬的边界：**延迟只能存在于两个东西之间，不能存在于一个东西内部。** 共享运动是一个东西（一个背景块在 tab 之间移动），它内部不能各自延迟，有延迟就散架；因果型延迟是两个东西，才有"谁先谁后"。

因果型延迟的方向不是自由选的，由物理决定：被推的那个后动。反过来（背景先动、爱心后动）读成"背景推了爱心"，或者"两件无关的事，其中一件早了"。

而且这是个窗口不是点：太短分不出先后，等于同时；太长读成两件独立的事。

[状态共享](../状态共享/README.md) 里那个「第一个弹层延迟、之后立即」是成本型的典型处理——延迟本身没有含义，共享的目的是只付一次。两处正好是同一个词的相反用法。

## 八、进场减速，离场加速

两个词先说清楚，中文译名容易混：

- **减速**（ease-out）：一开始最快，慢慢停下来。对应"缓缓退出动作"。
- **加速**（ease-in）：从静止慢慢加速，结尾最快。对应"缓缓进入动作"。

规则是：**元素进入可见区域用减速，离开可见区域用加速。**

理由都是注意力。从外面进来，减速停下 = 落定、自信；加速进入看起来像没停住、冲过去了。离开时加速 = 我不重要了，走；减速离开会停在边缘附近，还在争取注意力。

这条出自 Material 的动效规范（[Duration & easing](https://m1.material.io/motion/duration-easing.html)）：进入用 deceleration，离开用 acceleration。它是平台规范，不是物理定律。

演示里红心的飞行就是这条的直接应用：离场快，接近数字时慢下来。

**边界**：它只在"进出可见边界"时成立。屏幕内部的移动用标准曲线（两头慢、中间快）。把它扩成"ease-in 不能用"，就是把一条有场景的规则变成通用禁令。

顺带一个检验：材料里没有这条禁令。《制作点赞与投票动画》自己就在用加速——上升加速、下落加速，只有"撞到卡片后继续上移"用减速。它按事件分工：加速是"被甩出去"，减速是"撞上了、顶不住"。所以问题从来不是选哪条曲线，是这一段在讲什么事件。

## 为什么这样判断

- 三个时刻、按下必须立即有反馈，来自演示里 A 列按住不放的判断；更一般地，来自"按住期间用户的唯一疑问是按上了没有"。
- 悬停和按下分通道，是在 C 列反复改形变对象之后定下来的：只改背景色的两档读不出差别。
- 蓄力归属按下、载体是被释放的物体、交接要重合——这三条是同一个问题的三次返工，每次都是先做出一个"看起来不对"，再定位到具体是哪一层错了。它们的共同点是：**一个视觉变化必须有对应的物体和对应的时刻**，否则就会读成抖动。
- 时间累积那条是从物理类比推出来的（力恒定则形变恒定），没有实验支撑；它更稳妥的表述是"时间累积需要一个可兑换的输出"，这是必要条件，不是充分条件。
- 延迟三种用途是我提的框架，还没有拿更多案例验证过；目前只和共享延迟做了一次对照。
- 进场减速、离场加速这条是平台规范（Material），不是从演示里推出来的。演示只验证了它在"从按钮飞到数字"这个短距离场景里读起来顺；长距离、跨屏的场景没有试过。

## 适用条件和取舍

- **适用**：一次离散动作，之后有一个可观察的结果，用户会看结果。
- **不适用**：连续输入（拖拽、滑动，那是 [跟手与平滑](../跟手与平滑/README.md) 的问题）；动作本身是错误或破坏性的（删除、失败），庆祝会读成嘲弄；高频动作，每一次都加完整的三段是噪音。
- **代价**：把压缩放到按下，意味着按下态要更明显（压缩幅度更大），这在密集的工具栏里会显得吵。
- **氛围层没有信息价值**。它不帮用户做决定，只影响感受。所以它可以被关掉，而且关掉之后功能必须完全不变。
- **减少动态效果**：这类动画的信息量是 0，运动本身就是内容。所以不是"减弱"的问题，是"能不能关"。演示保留了运动，因为这个页面就是用来观察它的。
- **演示里的 A 列完全不做悬停**，是为了让对照最刺眼；真实产品最低限度会改光标。别把它当成推荐做法。
- 演示里的 120ms 压缩、420ms 飞行、500ms 累积上限都是演示值，不是推荐值。

## 还没定的

- 键盘激活的按下态没有做（空格和回车的 `click` 时机不同，要分别处理）。演示里键盘路径直接跳过压缩。
- 「按住累积」在真实长按场景（录音、连拍）里的具体参数和失败态，还没有讨论。
- 连点的处理：演示里每次点击开一条独立的时间线，各自到账；但多次点击的视觉密度有没有上限，还没测。
- 数字在按钮内部、但需要表达"正在处理"时，该怎么和立即 +1 共存，没有展开。
