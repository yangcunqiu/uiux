# 位置与路径

一级导航有两个问题：**放在哪**，和**什么不能动**。

第一个问题有答案——顶部、侧边、混合，各有它成立的条件。第二个问题更值钱，因为它决定了用户能不能靠记忆操作：位置动了、路径变了、名字换了，用户脑子里那张图就作废了。

## 先看演示

[三种排布](三种排布.html)：双击打开，不需要本地服务。

同一棵树（7–12 个版块，每个带 3 个二级），三种摆法，内容区放同一张数据表。表是尺子：它被挤窄多少、要不要横向滚，直接反映导航吃掉了多少地方。

控件下面有一行实时读数：**内容区宽度 · 顶栏高度 · 表格宽度 · 要不要横向滚**。所有数字都是从页面上量出来的，不是写死的。

观察重点：

- 只切"排布"：内容区直接跳 240px，横向滚动条跟着出现或消失。
- "一级项 12 + 名字长"：顶部换行，顶栏从 50 变 118，内容区矮一截；侧边只是往下滚。
- 点侧边栏左下角"收起"：240 变 64，内容区 818 变 994，横向滚动消失——但名字没了，二级整列消失。
- "二级"切常驻和手风琴：常驻时点任意一项，它不动；手风琴时点下面几项，整列往上跳（演示里 98px）。
- 点"改版"：顺序换了、一个名字改了。下面的变化清单会列出每一条。

## 一、形态不是三选一，是四个变量

|  | 顶部 | 侧边 | 混合 |
|---|---|---|---|
| 增长方向 | 横向：挤、换行、折进"更多" | 纵向：滚动、分组 | 两级各占一处 |
| 每页都要付的代价 | 高度（本来就要的） | 宽度（一列数据） | 两笔都要付 |
| 能撑几层 | 两级 | 三级以上 | 三级以上 |
| 能不能同时看见两层 | 不行 | 能 | 能 |

真正的判据是下面四个，不是"官网还是后台"：

1. **要几层？** B 端常见深度是三级（版块 → 模块 → 对象）。侧边能展开、能分第二列，顶部只到两级。**这是侧边成为 B 端默认的真正原因**，不是"后台比较专业"。
2. **一级有几项、名字多长？** 顶部是横向排，2–4 字舒服，5 个字以上开始换行；侧边是纵向，名字长只影响行高。
3. **同一时刻要不要看见两层？** 要，就付两笔空间。
4. **页面是不是数据密集？** 侧栏常驻 240px，等于每张表少一列。这条可以直接看见。

"顶部适合官网、侧边适合后台"是相关性，不是原因。照它选，遇到"后台但只有 4 个一级、名字都两个字"就会选错——那种情况顶部完全够用，还省下 240px。

## 二、收起是 240 → 64，不是 240 → 0

侧边栏有三档，每档付不同的代价：

| 档 | 宽度 | 代价 |
|---|---|---|
| 展开 | 240 | 每个页面少一列 |
| 收起 | 64 | 名字没了，只剩图标：从"读名字"变成"认图标"；二级整列消失 |
| 抽屉 | 0 | 关着时回答不了"有几个版块" |

收起按钮把固定成本变成了可让出的成本，这是真的改进——它把"这一页要不要占 240"的决定交给用户，而用户比自己更清楚此刻是在填表还是看表。

但它没有让侧边栏变免费，只换了成本：

- **识别成本**：图标能不能单独认出来是有门槛的（猜错一次，用户就不再点）。
- **记忆成本**：收起状态要不要记住？记住，下次进来面对一列图标；不记，每次都要再收一次。
- **重排成本**：收起会改内容区宽度，表格列宽、折行、图表尺寸全变。用户正在对比两行数据时，重排比省下的宽度更贵。
- **64 不是 0**：真要吃满的地方（详情页、全屏看板）要的是临时全屏，那是另一个机制。

## 三、二级怎么放，决定位置动不动

这是最容易被忽略的一条：**二级嵌在一级下面，位置就一定会动。**

| 放法 | 一级列 | 代价 |
|---|---|---|
| 嵌在下面（inline） | 会动 | 手风琴为了紧凑，点击时把上面的分组收起，被点的项往上跳 |
| 全部常驻展开 | 不动 | 列表变长，要滚 |
| 浮层（悬停/点击弹出） | 不动 | 触屏没有悬停；它是第二层 |
| 独立一列 | 不动 | 宽度从 240 涨到 300 以上 |

演示里把前两种做成了开关。常驻时点同一项，位移是 0；手风琴时，点第七项，它往上跳 98px——刚好是上面那个分组收起的 3 个子项高度。

判据是这一列的用途：**用户是在一个版块里深挖，还是在版块之间来回切？**

- 深挖（客服在一个工单里待很久）→ 二级常驻或独立一列，位置别动；
- 来回切（运营在几个模块间看数）→ 浮层更省地方，因为每次只需要看一眼二级。

手风琴差在哪：它同时想要"紧凑"和"就地展开"，代价就是把位置变化挪到了点击那一刻。点得越靠下，跳得越厉害。

## 四、稳定性：三层，每层都能查

| 层 | 是什么 | 怎么查 |
|---|---|---|
| 位置稳定 | 同一功能总在同一处 | 改版前后并排：把"退款"从第 3 项挪到第 5 项，原位置换成了"库存" |
| 路径稳定 | 到同一目标的层级链不变 | 数从首页到目标的路由段数，改版前后应该相等 |
| 命名稳定 | 同一功能不换名字 | 旧名字还搜不搜得到；面包屑里还是不是那个词 |

"清晰稳定的路径比少点击一次更重要"这句是对的，但要把理由换掉：**点击次数不是成本，可预测性才是。** 成本在"我猜它会去哪"和"我记住的位置还准不准"。多一次确定的点击，比少一次要靠猜的点击便宜。

对后端背景的人来说还有一层：**改导航结构 = 改路由表 + 改权限树 + 改面包屑。** 位置动一个，这三个地方都得跟着动。不跟着动，就会出现"导航里叫订单、面包屑里叫交易、权限里叫 order"——三套名字，同一个东西。

## 五、破层级要先付代价

把高频功能提到一级是合理的，但它必须是**附加入口**，不能替换结构。判据是：这个入口在树里**还有没有一条能走到的路**？

- 有 → 它是捷径（工作台、快捷入口），用户学到的地图没变；
- 没有 → 那是改结构。面包屑、返回栈、权限树都要跟着改，旧路径会失效。

这也是为什么"常用功能前置"和"把一级导航改浅"是两件事：前者加一条边，后者改整张图。

## 六、7±2 不该拿来当依据

米勒的 7±2 是工作记忆的容量，不是菜单项的上限。

演示里 12 个两字的一级项，顶部仍然是一行（顶栏 50px）；把名字换成长版，立刻变三行（118px）。**顶部的上限是总宽度（项数 × 名字长度），不是项数。** 侧边的上限是一屏放不放得下，大约 10–14 项，取决于行高。

按"不超过 7 个"设计，遇到长名字照样会挤；按"总宽度"设计，才知道什么时候该换形态。

## 为什么这样判断

- 形态的四个变量是从"增长方向、宽度代价、层级深度、数据密度"推的，不是从"官网 / 后台"的相关性。相关性解释不了反例（后台但只有 4 个一级）。
- 收起的三笔代价是结构性的，可以直接在演示里看到：识别（图标没有名字）、记忆（状态要不要留）、重排（宽度变、表格列变）。
- "二级嵌在下面位置一定动"是布局事实：列表总高度变了，被点项的位置就变了。演示里量到 98px。
- 三层稳定是判据，不是实测结果；"怎么查"那列是可执行的结构检查，不是用户测试。
- 7±2 的批评来自它的原始出处：那是短期记忆，不是视觉搜索或菜单容量。
- 改结构要付三处代价，是从"面包屑、路由、权限都依赖同一棵树"推的。

## 适用条件和取舍

- 侧边是 B 端默认，但它在数据密集页面上不成立——那时要么收起、要么抽屉、要么把表做成横向滚动。三个都是取舍，没有免费的。
- 混合只在"一级少而稳定、二级多"时值得。只有一级的产品用混合，顶栏空一半、侧栏也空。
- 顶部适合层级浅、名字短、需要沉浸的页面；名字一长就换行，换行就等于每页少一行内容。
- 二级常驻适合深挖型任务，代价是列表长、要滚；缩进一多，扫描成本也跟着涨。
- 演示里的 240 / 64 / 1060 / 890 都是演示参数，不是规范值。
- 这篇只处理桌面端的一级导航；底部标签栏、平板 rail、抽屉属于窄窗口的形态，没有展开。

## 例子

- **云控制台类产品**：左侧一级常驻，二级或嵌在下面、或另起一列。一级项多、名字长，正好是顶部撑不住的情形。
- **编辑器类工具**：最左一条图标栏（一级，永不移动），旁边一列是当前版块的内容（二级）。二级换内容，一级列不动——这是"独立一列"的典型。
- **官网**：顶部横排 5–7 项，名字两三个字，层级只有两级。换成侧边反而空。
- **数据密集的后台**：侧边 240px 常驻，表格常年横向滚动；收起按钮就是为这种页面准备的。

## 稳定性

| 内容 | 稳定性 | 写法 |
|---|---|---|
| 形态的四个变量 | 定义（判据） | 写死 |
| 侧边能撑三级、顶部两级 | 默认 | 可偏离：顶部 + 面包屑也能表示三级 |
| 收起的三档（240 / 64 / 0） | 定义 | 写死 |
| 收起会带来识别、记忆、重排三笔成本 | 定义 | 写死 |
| 二级嵌在下面，位置必然动 | 定义（布局事实） | 写死 |
| 二级常驻 / 浮层 / 独立一列的取舍 | 条件 | 写判据，不写答案 |
| 三层稳定（位置、路径、命名） | 定义（判据） | 写死 |
| 破层级要有附加通路 | 判据 | 写死 |
| 顶部上限是总宽度 | 定义 | 写死；具体数字随字号和边距变 |
| 侧边一屏 10–14 项 | 经验值 | 标为经验，取决于行高 |

## 还没定

- 底部标签栏、平板 rail、抽屉三者的选择，没有讨论（留给"同一棵树换壳"）。
- 双列侧边的具体宽度（一级栏多宽、二级栏多宽）、以及一级栏收成图标的时机，没有测。
- 混合导航里"顶部一级"和"侧边二级"的比例，没有讨论。
- 权限树和导航的一致性只有一句判据，没有具体方法（比如权限节点该不该和导航节点一一对应）。
- 改版时旧路径怎么处理（重定向、保留旧入口、还是直接 404），没有展开。
- 演示只做了 1280 宽的一档，窄窗口下三种形态如何退化（汉堡、抽屉、底部栏）没做。
